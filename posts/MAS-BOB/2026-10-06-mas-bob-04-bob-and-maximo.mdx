## 🔥 The Demo That Skips the Hard Part

Picture the vendor demo. A developer types: *"Close out all the work orders for pump P-1001 that have been in COMP for more than thirty days."* The agent thinks for a moment, calls a tool, and a green check appears. Applause.

Now picture the same sentence at 2 a.m. in your production estate, where nobody is clapping.

*"Which API key did it use?"* — *"The admin one. It was already in the environment."*
*"Which work orders did it touch?"* — *"We think forty. Maybe four hundred."*
*"Was there a dry run?"* — *"There was a plan."*

Every Maximo shop that has stood up an AI agent against a live instance has had some version of this conversation. In [Part 3](/blog/mas-bob-03-governance-pricing-bobcoins) we covered the controls around Bob: policies, identity, audit, and cost. This part is about the other side of the connection. **What does Bob actually touch in Maximo, through which door, and under whose authority?**

There is real substance here. IBM shipped a native Maximo MCP server in MAS 9.2. IBM's Build Engineering team published Bob skills for Maximo automation scripts. A Maximo Application Framework extension supports the Bob IDE as a first-class editor. An independent consultant has tested Bob against real Maximo chores and written down what happened. And we run three open or semi-open tools of our own that any agent can use.

But the substance comes with caveats, some of which IBM's own pages disagree on, and we found one where a file path in IBM's own README no longer matches the repository. We will show our work.

<aside>

💡 **Key insight:** "Bob works with Maximo" is four different claims. Reading and rewriting files in a repository is one. Calling Maximo APIs through MCP is another. Using an IBM skill is a third. Previewing app XML in Local Dev Mode is a fourth. Each has a different risk profile, a different credential, and a different evidence trail. Never let anyone merge them into one sentence.

</aside>

## 📊 The 69% Claim, With Its Caveat Attached

IBM's April 2026 GA announcement contains the sentence every Maximo conversation about Bob starts with. The IBM Maximo development team used Bob for code generation, refactoring, and updates that "normally take days," finished them in hours, and IBM calls the result "an **estimated 69% time savings**."

Read it again, slowly, the way you would read a vendor performance claim in an RFP.

| What a number needs | Does the Bob sentence provide it? |
|---|---|
| A defined task mix | **No.** "Code generation, refactoring, and updates" is a category list |
| A baseline | **No.** "Normally take days" is not a measured control |
| A sample size | **No** |
| A measurement method | **No.** "Estimated" tells you it was not timed |
| Whether review, test, and rework time were counted | **No** |
| Who did the work | Partly: IBM's own product team, who know the codebase |
| Whether it transfers to a customer estate | **No.** Product engineering is not configuration, integration, data, or upgrade work |

None of that means the number is false. It means it is **unusable for planning**. A product team with deep codebase knowledge doing greenfield-adjacent refactoring is the best case for any coding agent. A customer team doing the third rework of an integration against an undocumented ERP endpoint is a different animal.

### How to cite it

| Do | Don't |
|---|---|
| "IBM reports an estimated 69% time savings on internal Maximo product development tasks (IBM-reported, no published method)" | "Bob makes Maximo development 69% faster" |
| Put it in a footnote next to your own pilot metric | Put it on the slide as the headline |
| Ask IBM for the task mix and measurement method | Extrapolate it to upgrade projects |
| Use it to justify running a pilot | Use it to justify a seat count |

[Part 5](/blog/mas-bob-05-pilot-playbook) builds the replacement: a scorecard of Bobcoins per task, review hours, and defect escapes that you collect yourself. For now, hold the number at arm's length and read on, because the interesting material is not the percentage. It is the plumbing.

## 🗺️ Four Doors Between Bob and Maximo

Before the deep dives, here is the map. Everything Bob does with Maximo goes through one of four doors, and the doors have very different consequences.

```
╔══════════════════════════════════════════════════════════════════════╗
║  DOOR 1: THE REPOSITORY            files on the developer's machine  ║
║  Bob reads/edits autoscripts, app XML, BIRT, Java, integration code  ║
║  Credential: none needed.   Blast radius: the working tree           ║
╠══════════════════════════════════════════════════════════════════════╣
║  DOOR 2: IBM SKILLS                packaged instructions + tools     ║
║  maximo-code-optimization / maximo-java-conversion                   ║
║  Credential: API key (optimizer fetches scripts).  Blast: scripts    ║
╠══════════════════════════════════════════════════════════════════════╣
║  DOOR 3: MAF LOCAL DEV MODE        editor extension for app config   ║
║  OAuth/OIDC sign-in, live preview, offline cache, XML diff/merge     ║
║  Credential: your MAS login.   Blast: app configuration             ║
╠══════════════════════════════════════════════════════════════════════╣
║  DOOR 4: MCP                       the agent acts on LIVE Maximo     ║
║  MAS 9.2 native server  |  TMG Max_mcp  |  any MCP server            ║
║  Credential: API key / JWT.   Blast: whatever the key can do         ║
╚══════════════════════════════════════════════════════════════════════╝
       Doors 1 to 3 change files or previews. Door 4 changes data.
```

| Door | Agent changes | Needs a Maximo credential? | Review artifact | Where Part 3's controls apply |
|---|---|---|---|---|
| 1. Repository | Files in a working tree | No | Git diff | Approval groups `edit`, `execute` |
| 2. IBM skills | Files, plus a fetch from Maximo by the optimizer | Yes for the optimizer | Diff, skill's before/after report | `skill` group |
| 3. Local Dev Mode | App configuration in preview, local files | Yes (your login) | Maximo XML diff | `edit` group |
| 4. MCP | Live Maximo records and configuration | **Yes, and it is the dangerous one** | Maximo-side API logs, Plan output | `mcp` group, key scope |

A useful rule: **move up the table only when the evidence above you is boring.** Run Door 1 for a month before you open Door 4, and run Door 4 read-only before you ever give it a write key.

## 🔌 The MAS 9.2 Maximo MCP Server

MCP, the Model Context Protocol, is the open standard that lets an AI agent discover and call tools on another system through a uniform interface. If you have not met it, think of it as a typed, self-describing API catalog an agent can read at runtime. MAS 9.2 puts one in front of Manage.

### What IBM documents

Everything in this section comes from IBM's "Maximo MCP server overview" documentation for MAS 9.2 unless stated otherwise.

| Aspect | What IBM states |
|---|---|
| Deployment | A pod on Red Hat OpenShift, named `instance_ID-mcp` |
| Readiness | The pod stays unready until Manage is ready, then performs a full tools refresh |
| Tool sources | **AI configurations** (`mcc`, `pcc`, `similarity`, `nl2oslc`, `docsearch`, `insightsgenerator`), plus **custom tools** from automation scripts, object structures, workflows, and API routes |
| Tool registry | AI configuration tools are governed through the `MAXAICFGTOOL` table |
| Transport to Manage | "All Maximo Manage-based tools are Maximo REST API POST calls." Not all Maximo APIs are tools |
| Refresh | Pulls the tool list on startup, re-checks every `POLLING_FREQUENCY` (default 10 minutes) |
| Timeout | `TOOL_RESPONSE_TIMEOUT`, default 10 minutes |
| External access | Public-facing OpenShift route; `apikey` header or JSON Web Token |
| Protocol | JSON-RPC 2.0 `tools/call`; responses via Server-Sent Events (SSE), per DOC16 |
| Annotations | MCP annotations can be applied after deployment, for example marking a tool as destructive |
| Built-in consumer | In MAS 9.2 the agentic Maximo Assistant runs on the ALM-agent, which chains tool calls through this server |

A practitioner write-up from Naviam adds two details worth knowing. The server refreshes tool definitions from OpenAPI specifications using ETags, so polling is cheap. And for built-in agents the call carries an `x-access-token` JWT validated through Core IDP, while external agents authenticate with API keys or JWT, with internal MCP-to-Manage-to-Core traffic protected by MAS certificates. Naviam also notes that only non-interactive workflows are supported, meaning workflows built from nodes, condition nodes, and actions. A workflow that opens a dialog for a human cannot be a tool in this release.

### The architecture in one picture

```
 ┌──────────────┐   apikey / JWT     ┌────────────────────────┐
 │  Bob IDE or  │ ─────────────────► │  OpenShift route        │
 │  Bob Shell   │   JSON-RPC 2.0     │  (public-facing)        │
 │  (MCP client)│ ◄───────────────── │                         │
 └──────────────┘   SSE responses    └───────────┬─────────────┘
                                                 │
 ┌──────────────┐                    ┌───────────▼─────────────┐
 │  Maximo      │   tool call        │  instance_ID-mcp pod    │
 │  Assistant   │ ─────────────────► │  tools list synced from │
 │  (ALM-agent) │                    │  Manage every 10 min    │
 └──────────────┘                    └───────────┬─────────────┘
                                                 │ REST POST (as a Manage user)
                                     ┌───────────▼─────────────┐
                                     │  Maximo Manage          │
                                     │  security groups, rules,│
                                     │  validation, workflow   │
                                     └─────────────────────────┘
```

### Why the REST-POST detail matters for governance

The single most important sentence in IBM's documentation, for a Maximo person, is that tools are REST API calls. It means an agent action is not a side door. The call goes through Manage's security layer, so the agent can only do what the user behind the API key could do in the product. It also goes through business rules, validations, and workflow, so an agent cannot, for instance, put a work order into a status your status-change rules forbid.

That is good news. It is also a trap if you stop reading there.

| Protection | Provided by the MCP server's design? | Provided by you |
|---|---|---|
| Agent cannot bypass Manage security | **Yes** | Choosing the key's security group |
| Agent cannot skip business rules | **Yes** | Writing good business rules |
| Agent cannot do more than the key allows | **Yes** | **Making the key small** |
| Agent cannot be tricked into a legal but harmful action | **No** | Read-only keys, destructive annotations, human approval |
| Agent actions are attributable | Partly (key identity in Maximo logs) | One key per use case |
| Tool set is small | By default; grows as you expose scripts and object structures | Curating what you expose |

A legal but harmful action is the interesting category. "Cancel all open work orders at this location" is a valid, authorized, rule-compliant call for a planner's account. The agent did not break any rule. It did the wrong thing. Only a narrow key, a destructive annotation, and a human approval step stop that.

### Which tools exist, and how to read them

The AI-configuration tools are Maximo's own AI building blocks surfaced as MCP tools. We do not have IBM's per-tool descriptions, so treat the following interpretations as our reading of the names, to be verified against `tools/list` on your server.

| Tool | Likely purpose (our reading; verify with `tools/list`) |
|---|---|
| `nl2oslc` | Turn a natural-language question into an OSLC query against Manage |
| `docsearch` | Search documentation or attached document content |
| `similarity` | Find similar records, for example similar work orders |
| `mcc`, `pcc` | AI configuration categories used by Manage's AI features |
| `insightsgenerator` | Produce condition insights summaries for assets |

The custom tools are the part that matters to a developer, because **you decide what the agent can call**. IBM's own Assistant announcement gives the examples of changing work order status, creating follow-up work orders, and executing custom automation scripts as tools. In other words, an automation script with a clear input and output contract can become an agent-callable tool without you writing an MCP server at all.

### Exposing your own capability, the right way

Here is the design pattern we recommend for custom tools. The principle is that a tool should be **a narrow verb with a validated input**, not a generic "run anything" door.

| Good tool | Bad tool |
|---|---|
| `wo_set_failure_class(wonum, failurecode)` | `wo_update(any_field, any_value)` |
| `asset_get_last_5_downtimes(assetnum)` | `run_sql(statement)` |
| `sr_add_worklog(ticketid, text)` | `execute_script(name, args)` |
| Read-only by construction | Write capability hidden behind a read-sounding name |

If you build tools from automation scripts, put the validation in the script. Here is a minimal Jython example of a script that is safe to expose, because it checks its own input and refuses to act outside a narrow lane. The script name, object, and message keys are illustrative.

```python
# Illustrative: an action-style script intended to back a narrow agent tool.
# Verify implicit variable names and launch point configuration in your version.
from psdi.mbo import MboConstants

ALLOWED_STATUSES = ["WAPPR", "APPR"]

# "params" stands for whatever input mapping your action launch point provides.
if mbo.getString("STATUS") not in ALLOWED_STATUSES:
    service.error("wo", "agentstatusnotallowed")   # custom message you create in MAXMESSAGES

mbo.setValue("FAILURECODE", params["failurecode"], MboConstants.NOACCESSCHECK)
```

The detail worth stealing is the pattern, not the exact syntax: **an allow-list, a hard refusal, and a custom message key** that appears in the agent's tool result so the failure is legible.

<aside>

💡 **Key insight:** The MCP server decides how a tool is invoked. **You** decide how narrow the tool is. A permissive tool behind a careful server is still a permissive tool.

</aside>

### What we could not verify: Bob to this server

Here is the honest part. IBM's documentation and a third-party summary both say external agents such as Bob, Claude, and OpenAI can connect through the supported route and authentication model. But we found **no published end-to-end write-up of Bob calling this server in production**. DOC16 records the same gap, and the independent Bordelanne evaluation we discuss below explored MCP only as a future possibility.

There is also a transport detail worth a sandbox test. Bob's documented remote transport is `streamable-http` with custom `headers`. IBM's Maximo server is described as accepting JSON-RPC 2.0 `tools/call` and responding over SSE. Streamable HTTP and SSE are related, and many clients handle both, but we have not seen that exact pairing confirmed. Test it.

## 🔧 Connecting Bob to Manage Without Handing It the Keys to the Plant

Bob stores MCP server definitions in two places, per IBM's Bob documentation: globally in `~/.bob/settings/mcp.json`, or per project in `.bob/mcp.json`, where the project file takes precedence and can be shared through version control. Both use a JSON object named `mcpServers`. Each entry can set `command`, `args`, `cwd`, `env`, `alwaysAllow`, and `disabled` for local (stdio) servers, or `type: "streamable-http"`, `url`, and `headers` for remote servers.

That last field is the one to be careful with. `alwaysAllow` is a list of tools Bob will run **without asking**. In [Part 3](/blog/mas-bob-03-governance-pricing-bobcoins) we recommended locking the `mcp` approval group through group policy. If you do that, `alwaysAllow` entries in a project file do not defeat your policy. If you do not, a single `alwaysAllow` line in a repository you cloned from somewhere can turn a read tool into an unattended one.

### A project file, step by step

This is an illustrative `.bob/mcp.json`. The server name, URL path, and header handling are placeholders. IBM's page for the Maximo server does not publish a sample for Bob, and we have not tested this against a live route. Check the route URL in your own OpenShift console, and **do not commit a real key**.

```json
{
  "mcpServers": {
    "maximo-native-readonly": {
      "type": "streamable-http",
      "url": "https://<instance_ID>-mcp.<your-apps-domain>/mcp",
      "headers": {
        "apikey": "<paste a READ-ONLY key from your secret manager, never commit>"
      },
      "alwaysAllow": [],
      "disabled": false
    }
  }
}
```

Three habits protect you here.

1. **Keep `alwaysAllow` empty at first.** Make every call a human click until you understand what the agent calls and how often.
2. **Keep the project file out of git, or keep the key out of the file.** Add `.bob/mcp.json` to `.gitignore` for any repository that holds client code, and add `.bobignore` entries for key files. (Part 2 explains why `.bobignore` is a courtesy, not a sandbox.)
3. **Prefer a key per use case and name it for the use case.** When the agent does something odd, `BOB_READONLY_ANALYSIS` in the Maximo log tells you what it was meant to be doing.

For the pre-flight check, use MCP Inspector or plain `curl` before you involve Bob. IBM notes MCP Inspector can be used for debugging the server. A raw JSON-RPC call looks like this (illustrative, adjust the route and confirm the exact path and required `Accept` headers in your environment):

```bash
# List available tools (read-only metadata call), illustrative
curl -sS -X POST "https://<instance_ID>-mcp.<your-apps-domain>/mcp" \
  -H "apikey: $MAXIMO_READONLY_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

If `tools/list` works from `curl` and fails from Bob, you have a client transport problem. If it fails from both, you have a route, key, or TLS problem. That binary split saves an afternoon.

### The API key ladder

Maximo's own guidance is the foundation here. In Manage, API keys are created in the **API Keys** application and are registered to a user; the key value is shown once and cannot be recovered later, and API key authentication depends on the `mxe.oslc.webappurl` system property pointing at your Manage server. What the key can do is defined by the security groups of the user that owns it. That makes the **service user and its security group** your real control surface.

Climb this ladder one rung at a time, and only when the previous rung has been boring for long enough to trust.

| Rung | Service user (example name) | What the security group allows | Environment | Promote when |
|---|---|---|---|---|
| 0. Files only | none | n/a | none | Always start here |
| 1. Read-only analysis | `BOB_READONLY` | Read on a short list of object structures (for example `MXAPIWODETAIL`, `MXAPIASSET`) | Non-production, or masked data | Two clean weeks, no surprise calls in the Maximo log |
| 2. Draft writes | `BOB_DRAFT` | Create and change on **draft** records only; no approving status changes | Test | A named owner and a rollback script exist |
| 3. Dev configuration | `BOB_DEV_SCRIPTS` | Autoscript and deploy signature options | Dev only | Reviewed script diffs, tests in CI |
| 4. Production write | **None for agents** | Humans, through your normal change path | Production | Never delegate this to an agent |

Notice that rung 4 is empty on purpose. Our position, consistent with Part 3, is that the agent drafts and a human executes in production.

### Marking tools as destructive

IBM states that MCP annotations can be applied after deployment, for example to mark a tool as destructive. Use that. A destructive annotation tells a well-behaved client to ask for confirmation. But remember the layering: an annotation is a hint to the client, not an access control. **The security group is the enforcement.** Do both.

| Layer | Mechanism | Strength |
|---|---|---|
| Tool design | Narrow verbs, validated inputs | Prevents whole classes of misuse |
| MCP annotation | `destructive` marking | Hint to the client; depends on client behavior |
| Bob approval | Group policy locks `mcp`; no `alwaysAllow` | Human gate per call |
| Maximo security group | Object structure and operation permissions | **Hard enforcement** |
| Environment | Non-production endpoint | Limits blast radius regardless of the above |

### A read-only session, annotated

Here is the kind of session we recommend as the first MCP experiment. Every step is a read.

| Step | Prompt to Bob | What should happen | What you verify |
|---|---|---|---|
| 1 | "List the tools the Maximo server exposes and tell me which ones can modify data." | Bob calls `tools/list` and classifies | Compare against your own tool inventory and annotations |
| 2 | "How many work orders for asset 11450 are in status COMP in the last 90 days?" | One query-style tool call | The Maximo-side request log shows a single read under `BOB_READONLY` |
| 3 | "Summarize the open service requests for location BEDFORD." | One or two read calls | Count matches a query you run yourself |
| 4 | "Close those work orders." | Bob should refuse, ask for approval, or fail on permission | **The security group blocks it.** If it succeeds, your key is too wide. Stop and fix it |

Step 4 is the test that matters. A pilot that never tries a forbidden action has not proven the control.

### Worked example: Java MBO to automation script

This is the task where an IBM skill, a testable outcome, and a real Maximo need line up. Suppose you have a custom `WO` subclass from a 7.6 era customization that enforces a failure code before completion.

The Java, simplified:

```java
package com.acme.app.workorder;

import java.rmi.RemoteException;
import psdi.app.workorder.WO;
import psdi.mbo.MboSet;
import psdi.util.MXApplicationException;
import psdi.util.MXException;

public class AcmeWO extends WO {
    public AcmeWO(MboSet ms) throws MXException, RemoteException { super(ms); }

    @Override
    public void save() throws MXException, RemoteException {
        if ("COMP".equals(getString("STATUS")) && isNull("FAILURECODE")
                && "CM".equals(getString("WORKTYPE"))) {
            throw new MXApplicationException("acme", "failurecoderequired");
        }
        super.save();
    }
}
```

The equivalent Jython automation script, as an Object launch point on WORKORDER (Save event, before save). The structure is what the converter should produce; your exact launch point settings and message setup need to be checked in your environment:

```python
# Script: ACME_WO_FAILURECODE_REQUIRED   Object launch point: WORKORDER, Save, Before Save
if mbo.getString("STATUS") == "COMP" and mbo.getString("WORKTYPE") == "CM" \
        and mbo.isNull("FAILURECODE"):
    service.error("acme", "failurecoderequired")   # the message must exist in MAXMESSAGES
```

The conversion is short, which is why it is dangerous: it **looks** obviously right. Here is what a human reviewer must check and what a good skill run should surface on its own.

| Check | Why it matters | How to test |
|---|---|---|
| The message group and key exist in Maximo | A missing message produces an unhelpful error at runtime | Create the message; trigger the rule in dev |
| Event semantics differ from `save()` | A Java `save()` override and an Object Save launch point do not fire in identical circumstances, for example around child MBOs and non-user saves | Test UI save, REST save, workflow-driven status changes, and MIF inbound |
| Status check uses the right value | Java compared an internal value; synonym domains (internal vs. external status) need care | Test with a synonym status in your environment |
| Entry conditions | `WORKTYPE` filter and `isNull` semantics preserved | Unit-style test cases: CM with code, CM without, PM without |
| Performance | An autoscript on a hot object runs on every save | Check the launch point condition field; add one rather than testing in the body |
| Deployment and rollback | Autoscripts deploy through different paths than JAR classes | Keep the Java class until the script is proven, then retire it deliberately |

IBM's converter skill advertises business-logic preservation and a conversion report. Treat the report as a **checklist for your review**, never as a pass certificate. The test matrix above is yours.

### Using the optimizer skill responsibly

The optimizer targets patterns Maximo practitioners know well: unreleased `MboSet` handles, missing error handling, string-built SQL, repeated `getMboSet` calls inside loops, and logging gaps. We have not benchmarked its findings, so here is how we would review them.

| Finding class (typical) | Auto-accept? | Reason |
|---|---|---|
| Add logging or comments | Yes, after a skim | Low risk |
| Close or release MboSet resources | Review | Easy to introduce use-after-close errors |
| Replace string-built queries with bind parameters | Review and test | Security win; check the semantics of the filter |
| Restructure loops for performance | **Never auto-accept** | Behavior changes hide here |
| Change transaction or save behavior | **Never auto-accept** | Data consequences |
| "Fix" security by deleting functionality | Reject | Not a fix |

Feed it your house rules. TMG's [Max_autoscripts](https://github.com/themaximoguys/Max_autoscripts) ships a standards file and an `AGENTS.md`, and IBM's own README says the patterns apply to any AI coding assistant. Put your standards in `.bob/rules/` or an `AGENTS.md` at the repository root so the skill's generic advice is overridden by **your** conventions. The [house rules post in our vibe-coding series](/blog/evc-11-teach-ai-house-rules) covers how to write them.

### The companion web app, and a data-egress question

The same IBM directory includes a **Maximo Modernization Asset**, a Node.js and React web application for script optimization, Java conversion, batch conversion, impact analysis, and pushing optimized scripts back to Maximo via REST `PUT`. The README lists an **OpenAI API key** as a prerequisite for its AI-powered optimization.

That is a governance fact you cannot skip. If you run the web app, your automation script source goes to the model provider you configure, which is a different data path from Bob. [Part 2](/blog/mas-bob-02-models-security-self-hosted) covers Bob's own data handling. The web app is a separate trust decision. It also offers a write-back path. Our recommendation matches rung 4 of the key ladder: **do not give a tool with write-back a production key.**

Independent evidence matters more than vendor sentences, and there is little of it. The best Maximo-specific piece we found is by **Yann Bordelanne**, a Maximo consultant at Sopra Steria, summarized on DEV Community by Abhay Rao. Note the layering: it is a **secondhand summary** of Bordelanne's work, so we cite the summary and treat finer detail with care.

### What was tested

| Scenario | What Bob was asked to do |
|---|---|
| Maximo SQL | Generate and explain queries (per DOC16's summary) |
| **BIRT reports** | Identify components, understand logic, suggest changes |

### What was concluded

The headline finding is about context. Two more points matter for readers of this series:

| Gap | Why it matters |

| No quantitative results | No time savings, defect rates, or cost per task |
| Single practitioner, single environment | Not a sample |
| Secondhand summary | Details may be compressed |
| No MCP result | The most strategic capability is untested here |

So read it as **directional evidence** that context quality drives output quality, and as a map of scenarios worth including in your own pilot. It is not a benchmark.

## ⚖️ Where Bob Fits in Maximo Work

Now to the table most readers want. This is our assessment, built on DOC16's task-fit framework, IBM's skill scope, and the Sopra Steria scenarios. "Fit" means the combination of how well agents do this kind of work, how testable the outcome is, and how contained the failure is. It is **not** a measured result.

| Maximo task | Fit | Why | Door | Credential | Review artifact |
|---|---|---|---|---|---|
| Java MBO to autoscript conversion | **High** | IBM skill exists; pattern-heavy; outcomes are testable | 1, 2 | None to read-only | Diff, test matrix |
| Autoscript review and refactor | **High** | IBM skill exists; house standards can be fed in | 1, 2 | Read-only for fetch | Diff, skill report |
| Integration code (OSLC, REST, MIF, Kafka) | Medium to high | Needs an accurate API catalog in context | 1, 4 (read) | Read-only key | Diff, API call log |
| BIRT report changes | Medium | Works with context; layout and SQL need human QA | 1 | None | Rendered report, SQL review |
| App Designer XML edits | Medium | Local Dev Mode diff helps; review before import | 1, 3 | Your MAS login | XML diff |
| Upgrade analysis (7.6 to MAS 9) | Medium | Good at inventorying customizations; **verify every finding** | 1 | None | Inventory with sampled verification |
| Read-only operational Q&A | Medium | Valuable and low-risk via MCP, but only as good as the tools | 4 (read) | `BOB_READONLY` | Maximo request log |
| Draft record creation (test) | Low to medium | Acceptable with draft-only keys and review | 4 (draft) | `BOB_DRAFT` | Records in test |
| Production data fixes | **Do not** | Use scoped API tools through a human-run path, never direct database access | n/a | None for agents | Normal change process |
| Security group or access changes | **Do not** | A privilege escalation path | n/a | None | Security process |

### Reading the table

**High fit** means a bounded input, a known output shape, and a way to check. A Java class has behavior you can characterize. An autoscript either passes your tests or does not.

**Medium fit** means the agent is useful but the result depends on context it may not have. A BIRT change needs the report's data model and a human to look at the rendered output.

**Do not** is not about whether the agent *can*. It is about whether the cost of a mistake is too high for the evidence you can gather. Production data goes through the API layer under a human's hands, with a dry run.

### Anti-patterns we have seen

| Anti-pattern | What goes wrong | Fix |
|---|---|---|
| "Let it fix the data directly" | Direct database writes bypass business rules, audit fields, and integration events | API layer only; agent drafts the payload |
| One shared admin key in `.env` | No attribution, maximum blast radius | Key per use case, scoped group |
| Agent summarizes a customization without the source | Hallucinated behavior | Give it the script or class; require citations to lines |
| "Convert everything in batch" | Review debt piles up | Convert by launch-point group, with test evidence per batch |
| Treating the skill's report as acceptance | Lulls reviewers | Reports are checklists; tests are acceptance |
| Letting Bob author the rule that guards Bob | Circular control | Humans write policy and security groups |

## 🧭 Three Worked Scenarios

Abstractions are cheap. Here are three scenarios, each with a door, a credential, a prompt, a review, and a stop condition. These are our recommended experiments, not reported results. Replace our assumptions with your pilot data.

### Scenario 1: Convert a legacy Java customization

| Element | Choice |
|---|---|
| Door | 1 and 2 (repository plus `maximo-java-conversion`) |
| Credential | None |
| Environment | A sandbox repo holding the Java class and a dev Maximo for testing |
| Mode | Plan first, then Agent with `edit` approved per action |
| Prompt | "Using the maximo-java-conversion skill, convert `AcmeWO.java` to an automation script. Produce the script, the launch point settings, the list of message keys I must create, and a test matrix." |
| Evidence | Plan, diff, conversion report, test matrix results from dev |
| Stop condition | Any difference in behavior between Java and script in a test case |
| Rollback | Keep the Java class deployed until the script is proven; retire it as a separate change |

### Scenario 2: Review a folder of existing autoscripts

| Element | Choice |
|---|---|
| Door | 2 (`maximo-code-optimization`), optionally with a read-only fetch |
| Credential | `BOB_READONLY` with read on `MXAPIAUTOSCRIPT` only, in dev |
| Prompt | "Review these scripts against `TMG_AUTOSCRIPT_STANDARDS.md` and the skill's security guidance. Report findings by severity. Do not modify files." |
| Evidence | Findings list; a human triages and then asks for fixes in a second, separate prompt |
| Stop condition | Any finding the reviewer cannot reproduce by reading the code |
| Why two prompts | Separating "find" from "fix" gives you a review artifact before any edit |

### Scenario 3: Read-only operational questions over MCP

| Element | Choice |
|---|---|
| Door | 4, read-only |
| Credential | `BOB_READONLY` on a non-production instance with masked data |
| Prompt | "Using the Maximo tools, list the five assets with the most corrective work orders in the last 180 days, and show the query you ran." |
| Evidence | The tool calls Bob made, the Maximo request log, and your own query to cross-check |
| Stop condition | Any numeric disagreement between Bob's answer and your own query |
| What to measure | Calls per question, wall-clock time, Bobcoins per question, and answer accuracy |

The measurement lines feed [Part 5](/blog/mas-bob-05-pilot-playbook). Bobcoins per completed task is the number IBM does not publish, and these three scenarios are small enough to produce it.

## ⚠️ Pitfalls and Troubleshooting

| Symptom | Likely cause | What to do |
|---|---|---|
| Download from the old `build-and-deploy/asset-management` path returns 404 | IBM restructured `building-blocks` on 2026-09-30 | Use `automation/operate/asset-management/bob-skills`; pin a commit |
| Skill panel shows `maximo-script-optimizer`, not `maximo-code-optimization` | Frontmatter name differs from folder and file name | Cosmetic; search by either name |
| You enabled `maximo-modernization-java` and Bob talks about Spring Boot | It is the generic `code-modernization-expert` skill | Use `maximo_java_conversion.zip` for MBO conversion |
| Optimizer skill asks for a Maximo URL and API key | By design: it fetches scripts from `MXAPIAUTOSCRIPT` | Supply a read-only dev key; protect the generated `.env` |
| `tools/list` empty after you deploy a new script tool | Tool list refreshes every `POLLING_FREQUENCY` (default 10 minutes) | Wait for the poll, or restart the MCP pod; check Manage readiness |
| Tool call fails with a timeout | `TOOL_RESPONSE_TIMEOUT` default is 10 minutes, or the underlying script is slow | Profile the script; do not raise the timeout first |
| Pod never becomes ready | MCP pod waits for Manage readiness | Check Manage health before debugging MCP |
| Works in `curl`, fails in Bob | Transport or header handling mismatch (streamable HTTP versus SSE) | Test with MCP Inspector; check the Bob server entry type and headers |
| 401 or 403 from the route | Wrong header name, expired key, or `mxe.oslc.webappurl` not set for API key auth | Re-check the key, the header, and the system property |
| Agent "can't find" a Maximo API | Not all Maximo APIs are tools | Expose a custom tool through an object structure or script |
| Agent did something you thought forbidden | Key's security group is wider than you intended | Audit the service user's groups; revoke and re-issue the key |
| Local Dev Mode will not authenticate | Self-signed certificate, or MAS version below 9.1.21 or 9.2.1 | Check the version floor and the certificate setting |
| Max_mcp shows write tools on a "read-only" setup | The tool list is broad; only the key limits writes | Use a read-only security group; consider disabling the server's write modules if supported |
| Converted script behaves differently from the Java class | Event semantics, status synonyms, or non-UI save paths | Expand the test matrix; test REST, MIF, and workflow saves |
| Reviewer cannot tell what Bob changed | No plan or diff attached | Make Plan mode output and the git diff mandatory attachments |

## 🔎 Open Items and Discrepancies

We verified what we could. These remain open or conflict across sources, and they are the backlog for the next pass.

1. **Bob to MAS 9.2 MCP end-to-end.** No IBM or community write-up shows it in production. Treat as a sandbox experiment.
2. **Transport match.** Confirm streamable HTTP from Bob works against the server's SSE responses, or whether a different client mode is needed.
3. **Per-tool schemas.** IBM's overview names the AI configuration tools; the full tool schemas and descriptions come from `tools/list` on your server.
4. **Route URL format and path.** Take it from your OpenShift route, not from our placeholder.
5. **Repository path drift.** DOC16's `build-and-deploy/asset-management` is now `automation/operate/asset-management`. We updated our text; DOC16 needs a correction.
6. **Skill naming.** `maximo-modernization-java.zip` is a generic skill; the Java-to-script converter is `maximo_java_conversion.zip`.
7. **Max_mcp version support.** README says MAS 9.x; DOC16 says across Maximo versions. Test and document.
8. **The 69% method.** Ask IBM for the task mix and measurement approach, or leave the figure out.
9. **Skill code review.** We listed package contents but did not audit the converter and fetch scripts. Read them before you run them.
10. **Optimizer data path.** The companion web app's use of an OpenAI key is a separate data-handling decision from Bob's.

## 🧭 What to Take Away

### The Ten Commandments of Connecting an AI Agent to Maximo

1. **Never repeat the 69%** without the words "IBM-reported internal estimate."
2. **Open the doors in order:** repository, skills, Local Dev Mode, then MCP, and read-only first.
3. **Agents go through the API layer, never the database.** No exceptions.
4. **One key per use case,** named for the use case, owned by a service user with a small security group.
5. **The security group is the enforcement.** Annotations and approval clicks are hints and gates, not walls.
6. **Keep `alwaysAllow` empty** until you have watched the agent for weeks.
7. **Pin the commit** for every IBM asset you depend on, because IBM moves paths.
8. **Read every skill before you run it.** A skill is instructions plus code with your privileges.
9. **Convert in testable batches,** and treat a conversion report as a checklist, not a certificate.
10. **Write down what you do not know,** especially the transport match, the tool list, and the model.
