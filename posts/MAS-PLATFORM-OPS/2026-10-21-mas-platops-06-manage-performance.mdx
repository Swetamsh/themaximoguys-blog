# Maximo Manage Performance Tuning on MAS: Bundles, JVMs, Pods, Cron and Integration Load

<aside>

🎯 **Who this is for:** MAS administrators and platform engineers who own a Manage workspace on OpenShift and have been handed the sentence "it's slow" with nothing else. You will leave with a bundle layout, a sizing method with a worked example, JVM guidance that matches how Manage actually runs, a playbook for cron and integration load, and a triage order that finds the real cause before you change a setting.

</aside>

> **"Manage is slow" is a symptom with at least nine possible causes, and only two of them are inside the JVM.**

You have been here. The ticket says the work order screen takes eight seconds. Someone proposes doubling the heap. Someone else proposes another pod. A third person points at the database. Every theory is plausible, nobody has a number, and the change that gets made first is whichever one the loudest person suggested.

I have watched that meeting play out on 7.6 and on MAS. The platform changed, the meeting did not. What did change is that IBM now publishes measured guidance, in the open, for exactly this problem. The [MAS Performance Wiki](https://ibm-mas.github.io/mas-performance/) is maintained by IBM's Maximo performance team on GitHub, and it carries lab results for Manage, the integration framework, mobile, sizing and diagnosis. The repository's most recent commit when I read it for this post was dated 2 September 2026.

This is Part 6 of the series. Parts 3 and 5 gave you a tuned database and the metrics to see what is happening. This part uses both: it is the Manage layer, from the router down to the cron task.

One scoping note. Everything attributed to IBM below comes from the pages I read directly: the Performance Wiki source files, IBM Docs pages on server bundles, JVM options and pod scaling, an IBM Support abstract, and an IBM Community thread. Where I add my own practitioner view, I say so. Where IBM's pages disagree with each other or look dated, I flag it rather than smoothing it over.

## 🔥 The Performance Stack: Where Slowness Actually Lives

Before any setting, a map. A Manage request crosses every layer in this diagram, and slowness in any one of them looks identical to the user.

        ▼
 ┌──────────────────────────────────────────────┐
 │ OPENSHIFT ROUTER (HAProxy)                   │  balance algorithm, timeouts,
 │                                              │  ingress replicas
 └──────────────────────┬───────────────────────┘
                        ▼

 └──────────────────────┬───────────────────────┘
                        ▼

## 📏 Define "Slow" First: IBM's Two-Second Transaction

You cannot tune against a feeling. The Performance Wiki gives you an actual definition, and it is stricter than the one I had seen quoted in blog posts, including in this series' own index, which called a two-second target a community starting point. Having read the source, that framing needs correcting: the two-second expectation is IBM's, and it is narrow.

**IBM's definition of a transaction.** An out-of-the-box Maximo transaction is expected to complete with a latency of 2 seconds or less, where a transaction is the creation, update or deletion of a single MBO, with no more than one child object and with no attachments or blobs. Latency is the time from when the Maximo server receives the request to when it has sent the response. For UI users it also covers the time from clicking Save to control returning to the user. IBM's examples:

1. Creating one work order, including the generation of its `WORKORDERSTATUS` and `WOANCESTOR` records.
2. Updating one work order, for example moving it from Approved to Closed.
3. Deleting one work order.

**What is excluded.** The wiki lists the cases that fall outside the 2 second characterisation:

| Exclusion | Why it matters in practice |
|---|---|
| Downloading UI resources (js, css, png, jpg) | A slow first page load is a network or caching problem, not a transaction problem |
| Customized applications, and out-of-the-box applications with automation scripts | Your own logic is not covered by IBM's expectation; measure it separately |
| UI transactions with many XHR requests, such as the Start Center (more than 2 per page) | Manage supports HTTP/1.1, so the XHR requests from one page are sequential, not concurrent |
| Customized saved queries | A bad saved query is a database problem you own |
| Bulk load requests | Use MIF or data loading and size it as integration load |
| Report transactions | Reports have their own bundle type for this reason |

The HTTP/1.1 point deserves a second look. IBM's wording is that Maximo currently supports HTTP/1.1, so XHR requests initiated from a single user page are sequential. A Start Center with eight portlets is therefore eight round trips in a row, each paying the full latency to the pod and from the pod to the database. That is why the Start Center is the classic "it's slow when I log in" complaint and why the fix is fewer portlets rather than more CPU.

**How to use the definition.** Take a plain work order save on a clean record and time it. If that is over two seconds, you have a platform problem (database, network, pod). If that is fast and the customized screen is slow, you have an application problem. If both are fast and the Start Center is slow, you have a portlet and query problem. Three different owners, found with one stopwatch.

| Test | Result | Likely layer |
|---|---|---|
| Plain WO save, 1 child record | Over 2 s | Database, network, pod resources |
| Plain WO save | Under 2 s, customized screen slow | Automation scripts, custom Java, custom queries |
| Both fast, login slow | Start Center | Portlets, saved queries, `LAYOUTID` indexes |
| Fast for one user, slow at 10 a.m. | Concurrency | Pod count, heap, connection pool, DB locks |
| Slow only during the night | Batch collisions | Cron and integration load |

## 🧩 Server Bundles: Separate the Workloads

Of everything in this post, the bundle layout has the highest return for the least effort.

### What a bundle is

A Manage server bundle is a deployable set of Manage components running in one or more Liberty pods. IBM's server bundle overview lists six types:

| Bundle type | What it runs | Notes from IBM Docs |
|---|---|---|
| `all` | ui, cron, mea and report components together | If you deploy only one bundle, it must be type `all` |
| `ui` | The user interface, reached through a browser | Can be the default bundle |
| `cron` | Background cron tasks | "A cron bundle cannot serve UI requests" |
| `mea` | Enterprise web services API | Required for user synchronization |
| `report` | Reports | Keeps heavy reports out of the UI JVM |
| `standalonejms` | A JMS server bundle | Configured per IBM's separate JMS guide |

The rules IBM states around them are worth memorising, because breaking them produces a deployment that activates and then misbehaves:

- The **default bundle must be type `all` or `ui`**. Other defaults can deploy without errors but leave the application malfunctioning.
- If the default is a `ui` bundle, you **also need an `mea` bundle** for user synchronization.
- With multiple bundles and no default set, the system randomly picks an `all`-type bundle as the default.
- You can deploy **multiple bundles of the same type** to group workloads with different configurations.
- **All bundles connect to the same database.**
- The default bundle determines the default URL and route to Manage in the workspace.

### Why isolation matters

IBM's statement in the Performance Wiki is direct: it is a best practice to isolate UI, cron, MIF and report workloads on different server bundle types to reduce contention for resources within the same JVM and pod, and to adjust CPU, memory and replica count to match each workload. The server bundle documentation adds the mechanism: each bundle is scaled and managed independently, bundles do not share CPU or memory, and each bundle can carry its own additional server configuration, JVM options and bundle-level properties.

Think about what that means for a working day. A UI JVM wants low latency and a steady heap. A cron JVM runs escalations, PM generation, inventory reorders and integration polling that can allocate a lot of memory in bursts. An MEA JVM is processing messages as fast as the database will let it. A report JVM spikes on memory. In one shared JVM these workloads fight over heap, garbage collection pauses and threads. Isolated, a runaway cron task makes cron slow, and users do not notice.

### The ManageWorkspace configuration

The bundle layout lives in the `ManageWorkspace` custom resource in the Manage namespace. IBM's wiki shows this fragment for adding MEA and cron bundles:

```yaml
apiVersion: apps.mas.ibm.com/v1
kind: ManageWorkspace
...
spec:
  settings:
    deployment:
      serverBundles:
        - bundleType: mea
          isDefault: false
          isMobileTarget: false
          isUserSyncTarget: true
          name: mea
          replica: 1
          routeSubDomain: all
        - bundleType: cron
          isDefault: false
          isMobileTarget: false
          isUserSyncTarget: false
          name: cron
          replica: 1
```

Two fields in that block matter beyond sizing. `isUserSyncTarget: true` on the MEA bundle is how user synchronization finds its target, which ties back to IBM's rule that a `ui` default needs an `mea` bundle. `isMobileTarget` marks the bundle that serves mobile traffic, which I come back to in the mobile section.

Here is the layout I would start a mid-size production estate from. It is **my illustrative layout, not an IBM-published reference architecture**, and the replica counts are placeholders for the sizing method later in this post:

```yaml
spec:
  settings:
    deployment:
      serverBundles:
        - name: ui
          bundleType: ui
          isDefault: true
          isMobileTarget: false
          isUserSyncTarget: false
          replica: 5            # sized from concurrent users, see worked example
        - name: mea
          bundleType: mea
          isDefault: false
          isMobileTarget: false
          isUserSyncTarget: true
          replica: 2            # integration load, scale after a dry run
          routeSubDomain: mea
        - name: cron
          bundleType: cron
          isDefault: false
          isMobileTarget: false
          isUserSyncTarget: false
          replica: 1            # see cron section on running tasks once
        - name: report
          bundleType: report
          isDefault: false
          isMobileTarget: false
          isUserSyncTarget: false
          replica: 1
```

> <aside>
>
> ⚠️ **Verify against your version.** The wiki sample shows `routeSubDomain: all` on the MEA bundle. I show `mea` because a distinct subdomain is how you direct integration traffic at the integration pods; check IBM's server bundle documentation for the behaviour in your Manage version before you apply either.
>
> </aside>

### Which pods can you scale, and how

IBM's "Supported pods for Maximo Manage" page lists what accepts a `replicas` field. All default to 1. For the Manage workspace, the scalable pods include the `monitoragent`, `manage-maxinst`, the server bundle pods (named at activation, for example `mea`), the server bundle monitor agent, and several add-on pods. The page notes that for the `ManageApp` and `ManageWorkspace` deployments **more than one replica is not advised**, which applies to the supporting pods rather than to your server bundles: bundle replicas are how you scale Manage. It also says:

- To spread replicas across zones, use `topologySpreadConstraints` on the server bundle pods.
- Starting in MAS 9.0, `podTemplates` takes precedence over `passThroughDeployment` for server bundle settings such as affinity, node selection and topology spread.
- `build-config` pods accept only `resources` and `nodeSelector`; the Manage operator and truststore manager pods cannot be modified.

That second point is a common trap in upgraded environments: if you set affinity through the older pass-through mechanism on 8.x and the setting seems to be ignored on 9.x, `podTemplates` is what wins.

### Changing the layout safely

A bundle change restarts pods, so treat it as a maintenance activity.

1. Capture the current CR: `oc get manageworkspace -n mas-<instance>-manage -o yaml > manageworkspace-before.yaml`.
2. Apply the new `serverBundles` list in non-production first, and watch the pods come up with `oc get pods -n mas-<instance>-manage -w`.
3. Confirm the default route lands on a `ui` or `all` bundle and that user synchronization still targets the MEA bundle.
4. Log in, save one work order, and run one integration message end to end.
5. Only then schedule the production change, and keep the "before" YAML for rollback.

## 📐 Pod and JVM Sizing: Start From IBM's Numbers, Finish With Yours

### The resource blocks

IBM's wiki shows two resource blocks in the `ManageWorkspace` spec. The first sets the Manage admin pod, the second sets the server bundle pods:

```yaml
spec:
  settings:
    resources:
      manageAdmin:
        limits:
          cpu: '2'
          memory: 4Gi
        requests:
          cpu: '0.2'
          memory: 500Mi
      serverBundles:
        limits:
          cpu: '6'
          memory: 10Gi
        requests:
          cpu: '0.2'
          memory: 1Gi
```

Read the shape of that sample. The **requests** are tiny (0.2 cores, 1Gi) and the **limits** are big (6 cores, 10Gi). That is a deliberately burstable profile: the scheduler places pods thinking they need almost nothing, and the pods are allowed to use a lot. It packs well, and it is exactly how a node ends up under pressure when several pods burst together. I will come back to the overcommit rule below. (The sample as published has indentation that does not parse as written, so check your own CR's structure rather than pasting this block.)

### Users per pod

IBM's sizing guidance, from its benchmark results:

| Guidance | Number | Notes |
|---|---|---|
| General load per UI server bundle pod | **50 to 75 users** | Equivalent to a JVM with 2 cores on Maximo 7.6.x |
| Heavy workloads (complex Work Order, Scheduler) | **30 to 40 users per JVM** | IBM: "guidance rather than strict rules" |
| Network bandwidth | Comparable to Maximo EAM | App server to DB, and client to app server |
| Worker node storage | 300 GB minimum per node | For the MAS app build process |

Bandwidth deserves a footnote. IBM says client traffic may be heavier at first login because of additional user profile data in MAS, but overall bandwidth requirements are comparable to Maximo EAM. In MAS the client talks to the OpenShift ingress rather than to IBM HTTP Server.

### A worked sizing example

This is **my arithmetic on IBM's guidance**, with invented but realistic inputs. Replace every input with your own measurements.

**Inputs:** 1,500 named users, of which about 400 are concurrent at the daily peak. Of those, 340 do general work (work requests, inventory, approvals) and 60 are planners and schedulers working in the Scheduler and complex Work Order screens.

| Step | Calculation | Result |
|---|---|---|
| General UI pods | 340 users ÷ 60 users per pod (middle of 50 to 75) | 5.7, round to **6 pods** |
| Heavy UI pods | 60 users ÷ 35 users per pod (middle of 30 to 40) | 1.7, round to **2 pods** |
| UI total | 6 + 2, plus 1 for N+1 headroom | **9 UI pods** |
| MEA pods | Start at 2, adjust after the integration dry run | **2 pods** |
| Cron pod | One, until you measure a need | **1 pod** |
| Report pod | One | **1 pod** |
| Total server bundle pods | 9 + 2 + 1 + 1 | **13 pods** |

Now the cluster impact, using the wiki's sample limits (6 cores and 10Gi per bundle pod) as an upper bound:

| Resource | Per pod limit | × 13 pods | Compared to requests (0.2 core, 1Gi) |
|---|---|---|---|
| CPU limit | 6 cores | 78 cores | Requests total only 2.6 cores |
| Memory limit | 10Gi | 130Gi | Requests total only 13Gi |

IBM's overcommit rule is that CPU limit and memory limit overcommit should stay **below 300%** of node capacity to prevent node pressure. If the Manage pods are the only workload, 78 cores of limits at 300% means you want at least 26 allocatable cores for them, and 130Gi at 300% means about 43Gi of allocatable memory. Add the database, MongoDB, Core and every other application, and the real arithmetic gets tighter. The IBM sizing page's resource statistics table puts a Manage deployment with one all-in-one bundle at 2.9 cores request, 11.1 cores limit, 4.04 GB memory request and 17 GB limit, and says each **additional Manage pod costs about 1 core request, 6 cores limit, 2 GB request and 10 GB limit**. That last row is the one to multiply by your pod count.

IBM is clear that these statistics are reference values for a standard workload based on an IoT small T-shirt size and a single all-in-one bundle, so use them for scale rather than for commitment.

### Node shape

The wiki's OpenShift page gives node guidance that matters once you have 13 bundle pods to place:

| Recommendation | IBM's reasoning |
|---|---|
| 16 cores and 64 GB for a normal worker node | About 1 core per node is reserved for internal services; 8-core nodes may lack capacity while 32-core nodes lose a lot of capacity in an outage |
| Balanced CPU to memory around 1:4 | Fits typical workload |
| Database nodes with a higher ratio such as 8:1 | Memory-hungry database engines |
| At least 3 worker nodes | High availability with smaller redundant capacity |
| 8 cores and 32 GB for production master nodes | Avoids bottlenecks in internal services |
| 10 GbE for production | Network headroom |
| 300 GB storage per worker node | MAS app build requirements |

The first row interacts with the pod sizing in a way the wiki leaves implicit. A 6-core limit pod fits on a 16-core node, but only two or three of them can burst at once. Spread your UI pods across at least three nodes with `topologySpreadConstraints`, and remember IBM's Mobile page note: the default topology key in the ManageWorkspace CR is `topology.kubernetes.io/zone`, and in a single-zone cluster, if pods are not spreading across worker nodes, consider `topology.kubernetes.io/hostname` instead.

### When to add an instance

IBM answers a question most teams never ask: when do you stop adding pods and add a MAS instance? Its answer is that a new MAS instance is needed when the **database server can no longer be scaled up**. At that point plan a new MAS instance with a new database server and move sites to it. In other words, pods scale out; the database is the ceiling. This is why Part 3 came before this part.

## ☕ The JVM: What Actually Applies to Manage on Liberty

If you came from 7.6 on WebSphere Application Server, your JVM argument list is probably a page long. Most of it does not carry over, and IBM says so plainly: Manage on MAS runs on WebSphere Liberty with OpenJ9 inside OpenShift, and the JVM arguments in the 7.x best practice documents may not be relevant or applicable to 8.x and later. The wiki quotes Liberty Base 21.0.0.5 with OpenJ9 for MAS Manage. That version string looks old next to a 9.2 platform, so I would treat it as the wiki's stated baseline and check the Liberty version your own pods report rather than quote it as current.

### The arguments, and what to do with each

| Argument | IBM's guidance | My take |
|---|---|---|
| `-Xgcpolicy:gencon` | Default policy in OpenJ9; works in 7.x and 8.x | Leave it |
| `-Xmx` or `-XX:MaxRAMPercentage` | With no `-Xmx` and `-XX:+UseContainerSupport`, the JVM uses 75% of container memory as max heap; `-Xmx` overrides `MaxRAMPercentage` | Prefer the percentage, so heap follows the pod limit when you resize |
| `-XX:+UseContainerSupport` | Enables `InitialRAMPercentage` and `MaxRAMPercentage`; `-Xms`/`-Xmx` can override | Keep on |
| `-Xmn` (nursery) | 25 to 33% of total heap recommended | Set only when GC logs show nursery pressure |
| `-Xgcthreads` | Defaults to n-1 where n is the CPU count the node reports; restricting can reduce overhead | Cap it on large nodes with small pod limits |
| `-XcompilationThreads` | Same logic for JIT threads | Cap alongside GC threads |
| `-Xshareclasses` | Shares class data between VMs, faster startup after the cache exists | Leave default |
| `-Xdisableexplicitgc` | Recommended: stops `System.gc()` calls triggering collections | Apply |
| `-Djava.net.preferIPv4Stack=true` | Recommended for performance; cannot be used on IPv6-only hosts | Apply unless IPv6-only |
| `-Xverbosegclog` | Enables verbose GC logging | Enable when diagnosing, with log rotation |
| `-Xcodecache` and `-Xcodecachetotal` | IBM notes a 32 MB maximum for `-Xcodecache` and a 256 MB default for `-Xcodecachetotal` | Leave unless you see code cache warnings |
| `-XX:PermSize` / `-XX:MaxPermSize` | 7.x best practice said 320m | Legacy HotSpot flags; verify they mean anything on OpenJ9 before keeping them |
| `-Xtune:virtualized` | Marked "under review" by IBM | Do not adopt without testing |

On the `PermSize` row: IBM's page repeats the 7.x suggestion and adds that if you see an out-of-memory error for PermSize you could raise it to 512 MB or higher. Permanent generation flags belong to older HotSpot JVMs, so I would not carry that line into a MAS environment without confirming that it has an effect on your JVM. This is my view, not IBM's.

### The 10Gi is not the heap

IBM makes a point worth underlining: the Manage pod memory limit of 10G is not the total heap size. The heap is set by `-Xmx` or `MaxRAMPercentage`, and the 10G also covers memory used by WebSphere for cache and compilation, and by the Maximo MMI container. With the default 75% setting, a 10Gi limit gives a maximum heap of about 7.5Gi, a nursery (at 25 to 33%) of roughly 1.9 to 2.5Gi, and about 2.5Gi left for everything else in the pod. If you set `-Xmx` to 9G in a 10Gi pod you have left the pod about 1Gi for native memory, JIT, thread stacks and the sidecar, and the kernel will kill it with an out-of-memory error that looks like a Java crash but is not.

### Where to set them

IBM Docs describes the UI path for JVM options, and its page does not mention a custom resource:

1. Log in to MAS as a system administrator.
2. Suite administration, then Workspace, then the Manage tile.
3. Actions menu, then **Update configuration**.
4. In the **Server bundles** row, click the Edit icon.
5. Turn **System managed** off.
6. In **Additional properties** for the bundle, click **View**. This only appears when server bundles have been added.
7. Enter your options in **Java virtual machine options**.
8. Save, then **Activate** (new deployment) or **Apply changes** (existing deployment).

IBM's page does not give option syntax, example values, or restart behaviour, so test in non-production and watch the pod roll. Because JVM options are per bundle, you can give the cron bundle a larger nursery and the UI bundle a more conservative setup without compromise, which is another reason to split bundles.

### Threads: leave them alone first

The wiki notes that since Liberty 18.0.0.1 the thread growth algorithm grows capacity more aggressively to react to peak load, and for many environments the autonomic tuning needs no operator tuning. If necessary you can adjust `coreThreads` and `maxThreads`.

An IBM Community thread from April and May 2025 shows how that plays out. An architect from a systems integrator asked whether anyone had tuned the thread parameters for Manage. IBM's performance architect for Maximo replied that a lab test handled more than 2,354 requests per minute (about 40 per second) with no extra `DefaultExecutor` settings, that the default pool size in their environment was around 10 to 11, and that once you account for pod resource requests and limits the default is sufficient for most cases. A Cohesive support lead then suggested the thread pool was unlikely to be the cause and listed what to check instead:

- Slow SQL log entries (`BMXAA6720W`), with the SQL logger set to WARN
- Repeated errors in the logs
- Memory used by each MboSet
- Database connection counts by MboSet

That list is a better first hour of troubleshooting than any thread pool experiment, and I will fold it into the triage section. I would add one caution about the source: that thread is two practitioners and one IBM engineer in a community forum, not an IBM service-level statement.

## 🧪 Cron Tasks: The Quiet Load

Cron tasks are where nights and weekends go to disappear. They are scheduled background jobs that run inside the Manage JVMs, and on MAS they land on whichever bundle is allowed to run them. The sources I read give you the architecture; they do not give a cron tuning guide, so this section mixes IBM's bundle facts with practitioner experience, and I label which is which.

### What IBM tells you

- A `cron` bundle exists to run cron task components, and it cannot serve UI requests.
- An `all` bundle runs cron components too. If your only bundle is `all`, your cron tasks run in the same JVM as your users.
- Each bundle has its own CPU, memory, JVM options and properties, so a cron bundle can be sized for batch work.
- All bundles share the same database, so cron load still lands on your database. Isolating the JVM does not isolate the disk.

### Your own cron inventory

The knowledge base I use for this series lists the kinds of tasks that tend to dominate real estates. These come from the purchasing, work order and integration guides, not from the Performance Wiki:

| Cron task | What it does | Load pattern |
|---|---|---|
| `PMWoGenCronTask` | Generates work orders from preventive maintenance records | Burst at schedule time, scales with PM count |
| `EscalationCronTask` | Drives the escalation engine | Frequent, scales with escalation and record counts |
| `InvoiceMatchCronTask` | Sweeps WAPPR invoices and re-runs matching | Periodic sweep |
| `ConsignmentInvoiceCronTask` | Auto-generates invoices from consignment consumption | Event-driven, periodic |
| `FLATFILECONSUMER` | Processes flat file integration; IBM support recommends it for importing huge flat files through MIF | Burst, IO heavy |
| Custom tasks (for example `SC_GenInvCronTask`) | Customer logic, often legacy from 7.6 | Unknown until measured |

### A cron review you can do this week

1. **List every active cron task instance** with its schedule and run-as user, from the Cron Task Setup application. Export the list.
2. **Find the instances that run more often than their data changes.** An escalation firing every minute against records that change daily is wasted load.
3. **Find the overlaps.** Several heavy tasks scheduled at the same minute (the top of the hour is a classic) hit the database together. Stagger them.
4. **Look for the slow ones.** Review the cron task history for instances whose run times are growing, because growth usually tracks table growth and missing statistics (Part 3).
5. **Retire the zombies.** Every 7.6 estate carries cron tasks nobody can explain. Legacy custom tasks such as reorder generators should be checked after upgrade, as the purchasing guides in my knowledge base recommend, and some can be replaced with automation scripts.
6. **Decide where each task should run.** On a split layout the cron bundle runs them. If you need a heavy task on its own JVM, IBM's rule that you can deploy multiple bundles of the same type is the mechanism: a second `cron` bundle with its own limits.

One more practitioner note, which I have not verified against a current IBM page and you should confirm before relying on it: classic Maximo has a system property, `mxe.crontask.donotrun`, which lists cron task names a given JVM must not run. On a layout where UI and cron are already separate bundles you should not need it, but in an `all`-bundle estate it is the traditional lever to keep a task off the user-facing JVM. Check the property's availability and behaviour in your Manage version first.

### Cron and the database

The Db2 advice from Part 3 matters most here: cron tasks are the workload that suffers when `runstats` has not run, because they scan big tables on a schedule. IBM's wiki recommends increasing the `maxsequence` cache to 50 and running `runstats` or `reorg` periodically, and also that you consider archiving records over one year old. The wiki says Manage does not support MPP or table partitioning in the current version, so archiving is the lever, with Optim named as one tool.

## 🔌 Integration Load: MIF, MEA Pods and the Queue

IBM's performance team ran lab tests for the Maximo Integration Framework on both JMS and Kafka. The conclusions are specific enough to design against, and they overturn a common instinct: you cannot fix a slow integration by adding pods if the database disk is already the limit.

### The headline finding

On both the JMS and Kafka pages, the lab results show a significant correlation between transactions per second and database disk IO utilisation. The IO workload acts as a limit on how many transactions the system can handle. IBM's second observation follows from it: when IO is *not* the limiting factor, increasing the number of MEA pods improves processing performance, and MEA pods are able to scale linearly.

So the first question for a slow integration is not "how many MEA pods" but "what is database disk IO utilisation doing?" If it is saturated, MEA pods will just queue at the database.

### The factors, from IBM's table

IBM's "major performance related factors for MIF" table is worth reading whole. The rows I would act on:

| Component | Setting or factor | IBM's observation and best practice |
|---|---|---|
| JMS and MIF | `maxMessageDepth` | Make it large enough; if it is too small and the queue fills, the process fails and can be hard to recover. Recommend 500,000, the same as SIBus |
| JMS and MIF | `maxEndpoints` | Limit `maxConcurrency` |
| JMS and MIF | MDB (`maxConcurrency`) | Together with batch size, drives speed and MEA pod resource use |
| JMS and MIF | Batch size (`maxBatchSize`) | Together with MDB count, drives speed and MEA pod resource use |
| Maximo | Number of JMS pods | One JMS server works well in the benchmark and does not consume significant resources |
| Maximo | Number of MEA pods | Scales linearly when IO is not limiting |
| Maximo | MEA CPU and memory | Tune MDB and batch size to keep MEA pods in a reasonable range, for example 2 to 3 cores and 4 to 7 GB |
| Maximo | Maximo sequence cache | A reasonable number, for example 20 or 50, reduces database CPU and processing time |
| Maximo | `mxe.int.splitdataonpost` | In some circumstances it showed no positive impact; validate with a dry run in your environment |
| Message | Records per message | Tunable; interacts with batch size |
| Message | Record quality | A large number of internal error messages slows overall processing |
| Misc | Method and speed of posting messages into the queue | Post to the queue as fast as possible; a slow pace lowers the environment's processing capacity |
| Misc | Worker node capacity | May limit MEA pod capacity; consider pod distribution |

### The test method IBM recommends

The wiki's test methodology is a good template for any integration load test:

1. **Monitor first.** Set up monitoring of the essential metrics before the test (Part 5).
2. **Dry run with a single MEA pod** to establish a baseline.
3. **Tune MDB count and batch size** until the MEA pod sits in a sensible range, aiming for about 2 cores and 4 to 7 GB.
4. **Scale MEA pods** to meet the requirement.
5. **Keep watching the database** for the bottleneck that appears next.

### JMS versus Kafka

IBM's two pages differ in one detail that should influence your choice of transport:

| Observation | JMS | Kafka |
|---|---|---|
| Single MEA JVM throughput | Baseline | Same TPS as JMS |
| Multiple processing JVMs | JMS pulls ahead; its workload distribution is more even | Distribution difference grew from 2% to 10% when CRON JVMs and partitions doubled |
| Scaling effect | More MEA pods help when IO allows | Doubling CRON JVMs and topic partitions doubled maximum TPS, but the overall rate then dropped from 72 to 66 TPS in the final phase |
| Cause of the Kafka drop | n/a | Kafka's rule of a maximum of one consumer per partition |
| Message size | n/a | More partitions may help small messages (for example 10 assets per message) more than large ones |
| Recommended topology | One JMS server | One topic with 6 partitions, and multiple topics for parallel processing |

The "72 to 66" figures are IBM's own lab numbers from one test, so do not extrapolate them to your hardware. The lesson is structural: with Kafka, parallelism is capped by partitions, and an uneven spread across consumers can eat the gain from adding workers.

### When the queue is slow for a boring reason

The JMS page contains a diagnosis I have not seen elsewhere and which will save you a long night. JMS commit delays caused by high fsync latency, or by too little IOPS on the message store volume, can be a major cause of poor performance. IBM says the persistent volume used by the JMS pod must support **sub-millisecond average disk write latency**, and gives a way to see it in thread dumps:

- In the cron pods, look for `psdi/iface/jms/JMSClient.commitTx` in thread stacks. That points to a delay in the JMS commit.
- In the JMS pod, look for `LogBuffer.waitForFlush`. That points to a delay flushing the commit to disk.

IBM's flow: the producer thread blocks in `waitToComplete()` while the messaging engine dispatcher thread sits in `rcvXACommit()`, then in `LogBuffer.waitForFlush()`, which waits on a flush helper thread doing `fsync()` on the log file, and only then does the commit acknowledgement go back. If your threads are parked in `waitForFlush`, no number of MEA pods helps. You need faster storage under the JMS pod. IBM provides a Python IOPS-and-latency checker script (linked from the wiki's disk IOPS page) for measuring write latency of the storage from inside a pod that has Python.

### Integration checklist

| Check | Pass condition |
|---|---|
| Queue depth setting | `maxMessageDepth` at least 500,000 (JMS) |
| Queue never starved | Messages waiting while consumers work; an empty queue means the producer is the bottleneck |
| Error rate | Low and watched; review the message reprocessing application for patterns |
| MEA pod size | About 2 to 3 cores and 4 to 7 GB under load |
| Database IO | Not saturated; if it is, stop adding pods |
| JMS storage | Sub-millisecond write latency on the message store volume |
| Worker capacity | Enough nodes for the MEA pods you plan |
| Sequence cache | Raised from default (20 or 50) |

## 🌐 The Router: Balance Algorithm, Timeouts and Ingress

Three router settings cause real, repeatable problems.

### Load balancing algorithm

IBM's Manage page says lab testing showed **roundrobin** gave more stable and better performance than **leastconn**, "which is the default". IBM points to the OpenShift page for how to change it, which says the algorithm is set per route with an annotation:

```bash
oc annotate route <manage-route> -n mas-<instance>-manage \
  haproxy.router.openshift.io/balance=roundrobin --overwrite
```

Here IBM's two pages disagree. The OpenShift page says that from OCP 4.10 there are four algorithms (source, roundrobin, random, leastconn) and the **default is random**; before 4.10 it was leastconn. So on a current cluster the default is not leastconn. The practical reading: set `roundrobin` explicitly on the Manage routes rather than relying on whatever default your OCP version carries, and check the annotation with `oc get route -o yaml`. I list this one in the reviewer notes.

### Ingress capacity

IBM says OpenShift's HAProxy supports up to 20k connections per pod and suggests scaling up the ingress controller for applications with high connection volume, giving this command:

```bash
oc patch -n openshift-ingress-operator ingresscontroller/default \
  --patch '{"spec":{"replicas": 3}}' --type=merge
```

A Manage estate rarely hits 20k connections, but IoT in the same cluster can. Note IBM's warning that OpenShift no longer supports changing ingress deployments through environment variables such as `ROUTER_THREADS` or `ROUTER_DEFAULT_CLIENT_TIMEOUT`, and that edits to the deployment are overwritten while the Ingress Operator is enabled. Use the `IngressController` spec.

### Timeouts for long requests and mobile downloads

The Mobile page tells you that the default server and client timeouts are too low for large downloads, and gives:

```bash
oc -n openshift-ingress-operator patch ingresscontroller/default \
  --type=merge -p '{"spec":{"tuningOptions": {"clientTimeout": "300s"}}}'
oc -n openshift-ingress-operator patch ingresscontroller/default \
  --type=merge -p '{"spec":{"tuningOptions": {"serverTimeout": "300s"}}}'
```

This changes the default ingress controller for every route on the cluster, so decide deliberately.

### The Ping servlet: is it the cluster or the gateway?

When a request times out and you suspect something between the user and the cluster, a gateway or load balancer with a short idle timeout, IBM's diagnosis section has a small servlet for it. You load it as a customization archive through the `ManageWorkspace` CR, which **restarts the server bundles**, then call it:

```bash
curl https://<manage-host>/maximo/ping?timeout=300
```

If a 1 second wait returns `{"thread wait time":"1 seconds","status":"ok"}` but the 300 second one hangs outside the cluster, an external device is cutting the connection. Repeat from the `maxinst` pod against the internal service address with `curl --insecure`; if it works inside, you have found the culprit outside. Because the install restarts bundles, do it in a maintenance window, and note IBM's statement that the servlet is not in the base server bundle code.

## 🔑 The Two-Hour Surprise: LTPA Timeout

A Manage user working actively gets an error asking them to reload after two hours. IBM's wiki explains it: the default two-hour period is when the LTPA token in Manage expires, which redirects the user to the MAS login page.

It is not a performance problem, but it arrives as one: "the system froze, I lost my work." The user was mid-edit on a long work order when the token lapsed.

IBM has a Support article (document 6841623) on increasing the LTPA token timeout in Manage. What I could verify from its public abstract: it modifies `server.xml`, and it applies to MAS 8.10, 8.11 and 9.0 and to Maximo Application Suite as a Service (Manage). The steps themselves sit behind an IBM login, so I am not going to guess at the property names. Read the article, apply it in non-production, and discuss the new value with your security team before production. A longer token means a longer window for a captured session.

## 🗄️ Database Basics You Must Verify From the Manage Side

Part 3 covers Db2 tuning in depth. From the Manage side, IBM's wiki puts three checks in front of any pod tuning, and each is cheap to run.

### Disk

IBM calls disk performance critical to database performance and recommends storage with **throughput above 250 MB/s** and **10 to 100 IOPS per GB** depending on volume size. IBM's `dd` example on a Db2u pod shows 378 MB/s for a 1 GiB write:

```bash
dd if=/dev/zero of=<db2_data_directory>/ddtest bs=128K count=8192
```

> <aside>
>
> ⚠️ **IBM's warning, repeated because it matters:** make sure `ddtest` is appended to the end of the data path, or the `dd` command will wipe the Db2 data directory. Never run it on a path you have not looked at, and never point it at a production data directory without a backup (see Part 4).
>
> </aside>

### Network latency between application and database

IBM: confirm latency is **below 50 ms** with a ping test; for production, **strongly recommend below 10 ms**, with the application and database in the same network segment. In cloud deployments, put the database and OpenShift cluster in the same region and possibly the same availability zone.

Latency multiplies. A Manage save that issues 40 SQL statements on a 12 ms link spends nearly half a second on wire time before the database does anything.

### The DBTest utility

IBM ships a `DBTest` Java utility (Java 11 or higher) that measures database connection time, query execution time and fetch time for every 100 records. IBM's guidance is that with healthy latency and database the expected fetch time is **under 10 milliseconds**. It runs from the `maxinst` pod or a UI pod:

```bash
cd /tmp
curl -L -v -o run-dbtest-in-maxinst-pod.sh \
  https://ibm-mas.github.io/mas-performance/pd/download/DBTest/run-dbtest-in-maxinst-pod.sh
bash run-dbtest-in-maxinst-pod.sh
```

Read the script before you run it, as with anything you download and execute inside a production pod. In query mode (`-q`) it also prints the query result alongside the three timings, which is how you separate "the database is slow" from "the pod is slow" in a single command.

### Containerised Db2 and text search

IBM flags something that explains many list-page complaints: containerized Db2u and Db2 Warehouse deployments **do not support text search**, whereas regular Db2, Oracle and SQL Server do. Searching by Description on a list page is the typical case. IBM's workaround advice is that a non-unique index on `DESCRIPTION` helps when the search is exact (search type EXACT, or the user types `=` before the string) or a prefix (the user types `%` at the end), and that adding other indexed attributes to the query helps too. If your users search descriptions with a leading wildcard, no pod setting will fix it.

### The rest of the Db2 list

IBM's highlights, which Part 3 explains: raise the maxsequence cache to 50; run `runstats` or `reorg` periodically; separate system, user, backup, log and temporary tablespace storage where possible; Manage requires row-organised tables (`db2 update db cfg using DFT_TABLE_ORG ROW`); set `db2_workload=maximo` so `WLM_ADMISSION_CTRL` is `NO`; do not change `DB2_OVERRIDE_NUM_CPUS` or `DB2_OVERRIDE_THREADING_DEGREE`; do not set Db2 instance memory, as the operator calculates it from the container limit; and keep monitor switches off at the database manager level because enabling them for all sessions costs 5 to 10%.

## 🖥️ The Start Center and Other UI Load

The Start Center is the most common source of "slow login" tickets, and it is mostly a configuration problem. IBM's Support article on improving Start Center performance gives specific limits:

| Recommendation | Detail |
|---|---|
| Keep templates lean | Many portlets slow the Start Center; use tabs so each shows only a few |
| Light first tab | Create security groups with tabbed Start Centers and keep the first tab light |
| Result set portlets | No more than 1 to 2 in any template |
| Independent groups | Limit "Independent of Other Groups" per user to two or fewer |
| Query hygiene | Avoid queries that could return hundreds of thousands of records; include `SITEID` for site-level tables such as `WORKORDER`; remove unnecessary `ORDER BY` |
| KPIs | For Live KPIs, consider reading from a table refreshed by a cron task instead of running the query on every open |
| Indexes | Index `LAYOUTID` on all Start Center portlet configuration tables |
| Clean-up | Delete Start Center records for inactive users |
| System property | Set `mxe.db.UseSiteListInQuery` to 1 (IBM says it defaults to 0 in new environments) |

Remember the Performance Wiki's own point: Manage uses HTTP/1.1, so portlet XHR calls from one page are sequential. Eight portlets that each take 400 ms make a 3.2 second page.

### Mobile

For mobile users, IBM's tips are: create a mobile database to support data downloads (online downloads can significantly affect the mobile pods, the database and the network); raise ingress timeouts as above; scale up the `coreapi` pod to improve downloads; consider scaling up mobile pods when a pod's CPU use exceeds 4; make sure database disk throughput is good; and spread pods evenly across nodes. Pair this with the `isMobileTarget` field in the bundle layout so mobile traffic has its own pod set, not the UI bundle's.

## 🩺 Slow System Triage: The Order That Saves Time

This is the sequence I follow. It merges IBM's performance check list, its memory diagnosis steps and the Community thread's advice. The ordering is mine.

### Step 1: Platform health (5 minutes)

IBM's check list, in practical form:

- Any worker node not Ready? Any node with memory, disk or PID pressure?
- Any pod or node with CPU or memory approaching its limit?
- Any pod that has restarted many times recently?
- Any node or pod with high system or IO wait (IBM uses 20% as a warning level)?

```bash
oc get nodes
oc adm top nodes
oc adm top pods -n mas-<instance>-manage
oc get pods -n mas-<instance>-manage --sort-by='.status.containerStatuses[0].restartCount'
```

### Step 2: Is the response time actually high?

Take the 2 second transaction from earlier. Is a plain save over 2 seconds? Are there queries over 2 seconds or with high CPU cost? Check the network for bottlenecks such as the load balancer.

### Step 3: Slow SQL

Turn on Maximo's slow SQL logging and read `BMXAA6720W` entries, as the Community thread suggests. IBM's Support page "System properties to monitor and troubleshoot performance" lists the relevant properties: `mxe.db.LogSQLTimeLimit` (slow SQL threshold), `mxe.db.FetchResultLogLimit`, `MBOCount`, `mxe.db.logSQLPlan` and `mxe.db.sqlTableScanExclude`. Only the abstract is public, so I could not confirm defaults or recommended values; read the full article before changing production values.

### Step 4: Application server or database server?

IBM's decision list:

| If the app server is busy | If the database server is busy |
|---|---|
| Check CPU and memory request and limit values | Check CPU, memory, disk use and limit values |
| Consider more replicas | Check background utilities such as backups |
| | Check database locks |
| | Check for high-cost queries |
| | Check disk performance |

Note "backups" on the right-hand side: a Db2 backup running at 10 a.m. can look exactly like an application slowdown. That is why Part 4 and Part 5 belong together.

### Step 5: JVM diagnostics when pods restart or burn CPU

IBM names the symptoms of memory pressure: pods restarting due to JVM out-of-memory exceptions, and pods with unusually high CPU from excessive garbage collection. IBM's heap dump procedure:

```bash
oc exec -it -n mas-<instance>-manage <pod> -- bash
server dump defaultServer --archive=/tmp/package_file_name.dump.zip --include=heap
exit
oc cp --retries=10 -n mas-<instance>-manage \
  <pod>:/tmp/package_file_name.dump.zip ./package_file_name.dump.zip
```

Extract the zip and open the `.phd` file in Eclipse Memory Analyzer (MAT); IBM says to install the IBM DTFJ plugins first. For non-Liberty JVMs IBM says `jcmd` can produce a heap dump. A heap dump contains live data, including record contents and possibly credentials, so treat the file as sensitive: restrict access and delete it when finished.

For thread-level evidence, the same technique used for JMS (reading thread dumps for `commitTx`) works for any "stuck" symptom.

### Step 6: Use the right tool for the question

IBM's diagnostic utility table, trimmed to what matters for Manage:

| Scope | Tool | Use |
|---|---|---|
| OpenShift and MAS | OpenShift monitoring (Part 5) | Cluster and pod health |
| Db2 | IBM Data Server Manager, `db2top` | Historical and real-time troubleshooting |
| Network and DB | DBTest | Latency and fetch time |
| JVM | IBM Support Assistant, MAT | Heap dumps and GC log analysis |
| Maximo | PerfMon | UI activity tracing, **dev/test with a single user only**; IBM warns it can significantly degrade server performance |
| Browser | HAR viewer | Client-side performance |
| Nodes | `top`, `sar`, `oc debug node/<name>` | Process, resource and node debugging |
| Storage | IBM IOPS-and-latency Python checker (wiki disk IOPS page) | Disk performance checker |

That PerfMon warning is worth stressing. Never switch on the Maximo activity dashboard on a shared production system to see what one slow user is doing.

## 🧰 A Tuning Runbook You Can Defend

| Order | Change | Evidence needed first | How to check it worked | Rollback |
|---:|---|---|---|---|
| 1 | Verify database latency, fetch time and disk | DBTest, ping, `dd` or IOPS script | Fetch under 10 ms, disk above 250 MB/s | n/a (read only) |
| 2 | Set route balance to `roundrobin` | Current route annotation | Even pod load in the metrics | Remove the annotation |
| 3 | Split bundles (ui, mea, cron, report) | Current CR, pod list | UI latency stable during cron windows | Restore the saved CR |
| 4 | Size UI replicas from concurrent users | Peak concurrency, load test | Heap used and CPU per pod below limits | Reduce replicas |
| 5 | Let the container size the heap | GC logs, restart history | No OOM restarts, GC time low | Revert JVM options |
| 6 | Tune cron schedule and overlaps | Cron inventory and history | Shorter, non-overlapping runs | Restore schedules |
| 7 | Tune MIF: MDB, batch, depth, partitions | Dry run with one MEA pod | MEA pod 2 to 3 cores, queue never starved or full | Previous values |
| 8 | Extend LTPA timeout | IBM article 6841623, security sign-off | No two-hour reload complaints | Restore `server.xml` value |

Change one row at a time, and re-measure after each. If two changes land in the same window you will never know which one helped.

## 🛠️ The Seven Commandments of Manage Performance

1. **Thou shalt define slow with a number.** A single-MBO save in under 2 seconds is IBM's yardstick; measure it before you argue.
2. **Thou shalt triage the database first.** Latency, fetch time, disk. Pods cannot outrun a slow disk.
3. **Thou shalt separate the workloads.** UI, cron, MEA and report each get their own bundle and their own limits.
4. **Thou shalt size from guidance and then prove it with a test.** 50 to 75 users per UI pod is a start, not an answer.
5. **Thou shalt let the container size the heap.** And remember the pod limit is not the heap.
6. **Thou shalt stop adding MEA pods when the disk is saturated.** Integration throughput follows database IO.
7. **Thou shalt change one thing at a time and keep the rollback.** Evidence before change, evidence after.
