# Running MAS on OpenShift: The Platform Operations Series Guide

<aside>

🎯 **Who this is for:** Maximo administrators, platform engineers and OpenShift teams who own a running MAS 9 environment (or are about to) and need an operations map: what to patch and when, what to back up, what to watch, and how to keep the whole thing repeatable.

</aside>

**Series:** Series Index - *MAS Platform Operations* | **8 parts** | **Total read time:** ~2.5 hours

---

## 📖 Why This Series Exists

Go-live was the easy part. Three months later the questions change.

> *"Which of these catalogs are we supposed to be on?"*
> *"Why does the release page say Core 9.2.8 and Manage 9.2.4?"*
> *"If the cluster dies tonight, what do we actually get back?"*
> *"Who gets paged when the Manage pods start restarting?"*

In Maximo 7.6 most of those questions had one-word answers: the fix pack, the DBA backup, the WebSphere console. In MAS 9 the answers live in an operator catalog, a Tekton pipeline, a Db2u custom resource and a Prometheus rule, and they are scattered across IBM's release pages, GitHub repositories and a performance wiki. Our [MAS-ADMIN series](/blog/mas-admin-series-index) explains how the administrator's *role* changed. This series is the *runbook* that role needs.

We built it from four kinds of source, and we label which is which:

- **IBM documentation and support pages**, the primary source for versions and dates.
- **IBM's own GitHub repositories** (`ibm-mas/cli`, `ibm-mas/gitops`, `ibm-mas/ansible-devops`) and the CLI documentation site, which is often *ahead* of the product documentation.
- **IBM's MAS Performance wiki**, which holds practitioner-grade tuning guidance.
- **Community reports**, used for colour and always flagged as such.

<aside>

💡 **Key insight:** The unit of change in MAS is the **monthly operator catalog**, and the unit of risk is **version skew** between the pieces that catalog installs. Every part in this series is, one way or another, about controlling those two things.

</aside>

## 🧩 Part-by-Part Guide

### Part 1: The MAS Patch Train Explained

The first thing that confuses new MAS admins is IBM's releases page. It looks like a list of version numbers; it is actually three or four independent release trains. On 20 October the page showed:

| Product | Latest (per IBM page) | Date | Note |
|---|---|---|---|
| MAS Core 9.2 | 9.2.8 (interim) | 7 Oct 2026 | 9.2.4 and 9.2.5 reserved for internal use |
| MAS Core 9.1 / 9.0 | 9.1.27 / 9.0.33 (interim) | 7 Oct 2026 | Same security fix, three branches |
| Manage 9.2 / 9.1 / 9.0 | 9.2.4 / 9.1.25 / 9.0.32 | 29 Sep 2026 | |
| AI Service | 9.2.3 / 9.1.19 | 29 Sep 2026 | |
| Core and Manage 8.x | 8.11.34 / 8.10.37 (Core), 8.7.32 / 8.6.38 (Manage) | 30 Apr 2026 | Maintenance-only |

Part 1 teaches you to read the "reserved" notes, to tell an interim build from a scheduled one, and to use real defect examples (DT501598, where MAXUSER fields are overwritten in a 9.1 to 9.2 upgrade when MASISSUER is NULL; DT500106, where Application Configuration will not open after 9.1.20) to decide whether a given interim build is urgent for you. It also covers the October security fix in Core 9.2.8 for CVE-2026-105052, an unauthenticated path traversal in the login service that IBM's bulletin lists as affecting 8.10, 8.11, 9.0, 9.1 and 9.2.

### Part 2: Db2 12 on OpenShift

For estates using the Db2u operator, the Db2 11 to 12 move is the biggest single platform change in the 9.2 cycle. IBM's `mas update` guide documents the three flags that matter:

```bash
# Db2 11 -> 12 via the MAS CLI (flags per ibm-mas.github.io/cli/guides/update)
docker run -ti --rm -v ~/licenses:/licenses quay.io/ibmmas/cli \
  mas update \
    --catalog v9-261007-amd64 \
    --db2-namespace db2u \
    --db2-v12-upgrade \
    --db2-license-file /licenses/db2-v12-activation.lic
```

The flag `--db2-v12-upgrade` "confirms a major version update for Db2 to version 12", and `--db2-license-file` is required for 11-to-12. The command flow then detects dependencies, shows a summary, runs `pre-update-check`, updates the catalog and finishes with `post-update-verify`. Our 9.2 factbase adds that the upgrade is blocked without the licence file on purpose, since Db2 12 would otherwise fall back to a 30-day trial licence. Part 2 covers the order of operations, the Db2uCluster to Db2uInstance change, the pre-upgrade backup you must take, and how to reference DT502701.

> *"We can just do the Db2 upgrade in the same window as the Manage upgrade."*

You can, if you have a tested rollback. Part 2 helps you decide.

### Part 3: Db2 Tuning for Maximo Manage

A containerised Db2 still needs a DBA's attention. Part 3 works through the database settings that matter for Manage: the `db2_workload=maximo` setting, row-organised versus column-organised tables, sequence caching (`maxsequence`), and the RUNSTATS and REORG routine that keeps statistics current. IBM's MAS Performance wiki links to a "DB2 Performance Diagnosis" section and to DBTest utilities for MAS Manage, which are our starting points. We will flag where a setting comes from the wiki and where it comes from practitioners.

### Part 4: Backup, Restore and Disaster Recovery

This is where the brief for the series and IBM's own documentation need careful reconciling, so here is what IBM's CLI guide actually says.

| Component | In `mas backup`? | Notes (from IBM's CLI backup guide) |
|---|---|---|
| Core configuration and CRs | Always | |
| Operator catalog definitions | Yes | |
| Certificate Manager | Configuration only | Red Hat provider only |
| MongoDB | By default | Community Edition only; external or enterprise not backed up |
| Suite License Service | By default | Can be excluded with `--exclude-sls` |
| Manage app + PV data | Optional | `--backup-manage-app` |
| Facilities app + PV data | Optional | `--backup-facilities-app` |
| Db2 for Manage / Facilities | Optional | Standalone Db2u operator only; **Db2uInstance not supported** |
| Monitor, IoT, Predict and other add-ons | No | |
| Cloud Pak for Data | No | |
| DRO | No | Reinstalled fresh on restore |

The guide also states that restore from the pipeline works only from S3 or Artifactory, that Manage database restore is offline, and that you cannot restore backups taken before CLI v19.0.0 with a later CLI. Because the Db2uInstance limit collides with the Db2 12 move in Part 2, Part 4 spends real time on what to do with Db2 outside the CLI: native Db2 backups, OADP with Velero, and storage-level tools such as Veeam Kasten, where vendor timings are labelled as vendor-reported.

<aside>

⚠️ **Gotcha:** The series brief described CLI backup as "Manage and Facilities only". IBM's page shows it also covers Core, MongoDB CE and SLS. We follow IBM's page, and note the discrepancy in a comment at the bottom of this post.

</aside>

### Part 5: Observability

IBM's Grafana guide for Manage lists the order of work: configure the OpenShift monitoring service, confirm the PodMonitor for the Manage pods (the page notes you no longer have to create PodMonitors by hand, so check what your deployment already provides), verify that data is being collected, install the OpenShift Grafana operator into `openshift-user-workload-monitoring`, and import the Manage dashboard. Part 5 turns that into an alerting design: what to page on (pod restarts, JVM health, database latency), what to chart, how long to keep it, and where Instana fits. We will say plainly where guidance is community-sourced; IBM documents Prometheus and Grafana for Manage, not a MAS-specific Instana recipe.

### Part 6: Manage Performance Tuning

IBM's MAS Performance wiki is organised around MAS best practices (OpenShift, Core, MongoDB, cloud platforms), MAS Manage (overall, Mobile, Integration Framework with JMS and Kafka), sizing guidance, monitoring and performance diagnosis. Part 6 follows that structure and adds what we see in the field: separating UI, MIF and cron bundles, sizing pods and JVMs against measured load, and finding the one cron task or integration queue that is quietly eating the cluster. Community checklists in circulation suggest a two-second target for critical transactions; we treat that as a community starting point, not an IBM service level.

### Part 7: Staying Inside the Support Window

This part is a calendar and a sequence. It covers how the catalog table above maps to OCP, CPD and MongoDB, why an OCP 4.16 cluster is stranded after v9-260827, and the rule from IBM's 9.2 documentation that "IBM App Connect and Cloud Pak for Data do not support odd-numbered Red Hat OpenShift Container Platform versions", so if Maximo Collaborate or Maximo Predict is deployed you must use even-numbered OCP versions. That rule collides with a catalog range of 4.18 to 4.22 more often than you would expect. The CLI also handles dependency alignment during `mas update`: MongoDB and Kafka are aligned to tested versions, and a major MongoDB move requires an explicit flag such as `--mongodb-v8-upgrade` plus a backup.

### Part 8: GitOps, the CLI and ansible-devops

The final part compares three ways to drive MAS and shows how they relate. The CLI wraps Tekton pipelines; ansible-devops is the Ansible collection underneath much of that automation (CLI 23.14.2, for example, bundles ansible-devops 37.21.2); `ibm-mas/gitops` packages MAS for Argo CD. Recent gitops releases show where it is heading: 8.7.0 added MongoDB CE through Argo CD, CPD 5.3.1 Helm installs and private NLB support for AWS PrivateLink, and earlier 8.x releases added RHOAI support and Db2 audit-log upload to S3. ansible-devops 37.21.3 mentions "investigative work" on a Db2 Helm installer, which we treat as a signal to watch, not a feature to plan around.

## 💡 Key Themes Across the Series

1. **Catalog discipline.** You choose a catalog; operators follow. Never mix catalog months across clusters without meaning to.
2. **Version skew is normal, surprise skew is not.** Core, Manage and AI Service version independently. Know your three numbers.
3. **Opt-in upgrades need opt-in evidence.** Db2 12, MongoDB 8 and OCP moves need flags, licences and backups. Capture them in a runbook.
4. **A backup you have not restored is a hope.** Test the restore path and write down what the tooling does not cover.
5. **Measure before you tune.** Dashboards first, settings second.
6. **Automate the boring parts.** Git as the record of intended state beats a wiki page nobody updated.

### The Ten Questions Every MAS Operations Review Should Answer

1. Which catalog is each cluster on, and when was it last updated?
2. What are the Core, Manage and AI Service versions in each environment?
3. Is each OCP version inside the catalog's supported range, and is it even-numbered if Predict or Collaborate is deployed?
4. Is Db2 on 11 or 12, and where is the licence file?
5. When was the last backup restored in a test, not just taken?
6. Which add-ons and databases sit outside the CLI backup scope?
7. Who is paged when a Manage pod restarts three times in an hour?
8. Which cron tasks and integration queues run in the UI bundle?
9. Is desired state in Git, or only in someone's terminal history?
10. What will you do when OCP 4.18 leaves support?
