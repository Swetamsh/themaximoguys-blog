## 🔥 The Blank Screen at 4:45 on a Friday

You published a one-line change to a Technician page. The preview looked fine. On the test phone the work order list is blank, there is no error, and the only message in the chat is *"did you change something?"*

Where do you look first? In the XML? In the controller? In the Manage logs? On the phone? If you answered "all of them, in some order", you have already found the problem. MAF has several places where things can go wrong, each with a different tool, and most debugging time is lost looking in the wrong one.

This part is the map. We cover the **client log switch** (`_graphite_logLevel`), logging from your own code, the **9.2 default log level** attribute, how to go from a DOM element to the line in `app.xml`, the **server side** (Logging application and the `streamLog` method), how to prove what is actually deployed with `build.json`, **device inspection**, and a **triage table** of known defects with their IBM `DT` numbers so you can rule out the platform before you blame your code.

## 🧭 The Four Layers of MAF Debugging

A MAF app is XML and JavaScript that a runtime turns into a React UI, served from a Manage endpoint, optionally downloaded to a device and run offline. Failures can happen at any hop, so we debug in layers.

```
╔════════════════════════════════════════════════════════════════════╗
║  LAYER 4  DEVICE      offline DB, WebView, sync, DEBUG builds      ║
║           chrome://inspect · Help & Support > Log data             ║
╠════════════════════════════════════════════════════════════════════╣
║  LAYER 3  SERVER      OSLC calls, SQL, Manage pod, publish/build   ║
║           Logging app (OSLC, SQL) · streamLog · 9.2 build logs     ║
╠════════════════════════════════════════════════════════════════════╣
║  LAYER 2  YOUR CODE   AppCustomizations.js, controllers            ║
║           app.log.d / e / w / t (TAG, ...)                         ║
╠════════════════════════════════════════════════════════════════════╣
║  LAYER 1  BROWSER     runtime, XML parse, render, datasources      ║
║           ?_graphite_logLevel=trace · DevTools · DOM id -> app.xml ║
╚════════════════════════════════════════════════════════════════════╝
        Start at the layer closest to the symptom. Work outward.
```

| Symptom | First layer | First tool |
|---|---|---|
| Component missing, wrong layout, wrong label | 1 Browser | DOM id search in `app.xml` |
| Button does nothing, hook never runs | 2 Your code | `app.log.d` with a TAG at trace |
| List is empty but no UI error | 3 Server | OSLC and SQL loggers, network tab |
| Works in browser, fails on phone | 4 Device | `chrome://inspect`, in-app debug log |
| Publish succeeded but nobody sees it | Deployment | `build.json`, `MAFAPPDATA` revision |
| Publish or preview hangs | Platform | 9.2 build logs, defect table below |

The last two rows are not layers of the running app; they are about whether the code you think is running is the code that is running. We start there in a later section, because it is the cheapest check and the one most often skipped.

## 🖥️ Layer 1: The Browser Client and `_graphite_logLevel`

Every RBA and the local preview run in a browser, so the browser is your first debugger. The Graphite runtime has its own logger, and IBM's MAF Configuration Practices material documents a URL switch that controls its verbosity (IBM-reported):

```
?_graphite_logLevel=trace|debug|info|warn|error
```

On the local preview from Part 5 that looks like this:

```
http://localhost:3000/?_graphite_logLevel=trace#/createwo
```

Three rules save you pain.

1. **The query parameter goes before the `#`.** Everything after the hash is the in-app route (`#/createwo`). Putting the parameter after it means the router, not the logger, sees it.
2. **It is per page load.** Reload without the parameter and you are back to the default level. Bookmark the debug URL.
3. **It is client-side only.** It changes what the browser console shows. It does not change anything on the server, and it does not change what a published device build logs.

### What each level shows

| Level | Use it for | Noise |
|---|---|---|
| `error` | Failures where an operation cannot continue | Very low |
| `warn` | Recoverable, degraded paths | Low |
| `info` | Lifecycle milestones, one line per event | Medium |
| `debug` | Query parameters, timings, record counts | High |
| `trace` | Loop bodies, event callbacks, every datasource transition | Very high |

IBM's logging guidance puts it bluntly: the **production default is ERROR only**, and a statement must be `error`, `warn` or `info` level to appear in a default support log (IBM-reported). So `trace` is a development tool. Use it while reproducing, then turn it off.

### The first five minutes at `trace`

1. Open the preview URL with `?_graphite_logLevel=trace`.
2. Open DevTools, **Console**, and clear it.
3. Reproduce the problem **once**. Do not click around.
4. Filter the console by the page id or datasource id you suspect.
5. Scroll to the **first** red or amber line. The first error is the cause; everything after it is usually fallout.

Then check the **Network** tab. A failed `oslc` call (a 4xx or 5xx) with an empty list in the UI points you to Layer 3, not Layer 2. Save a HAR file if you are going to open a case.

<aside>

💡 **Key insight:** the console tells you what the *client* believes happened. A datasource that "loaded zero records" may have received zero records or an error it handled quietly. The Network tab and the server logs are what settle it.

</aside>

## ✍️ Layer 2: Logging From Your Own Code

If you customize through `AppCustomizations.js` (Part 3), you also own the log statements. IBM's logging guidance documents the Graphite `log` object with five levels, and the app-level equivalent you use in controllers is `app.log` (the same call shape appears in IBM's practices examples; our Part 3 uses it throughout) (IBM-reported).

| Method | Level | Visible by default? | What to log |
|---|---|---|---|
| `log.e` / `app.log.e` | ERROR | Yes | Failures; pass the error object last |
| `log.w` / `app.log.w` | WARN | Yes | Degraded paths the app recovers from |
| `log.i` | INFO | Yes | Key milestones, one line per event |
| `log.d` / `app.log.d` | DEBUG | No, opt-in | Query parameters, timings, record counts |
| `log.t` / `app.log.t` | TRACE | No, opt-in | Loop bodies, event callbacks |

IBM also documents one-shot variants (`eOnce`, `wOnce`, `iOnce`) that suppress duplicate messages within a session and prefix the TAG with `ONCE-`. They are the right tool for a warning inside a loop that would otherwise print thousands of lines.

### The TAG convention

IBM's rule is to declare `TAG` once as a module-level constant and never inline a string in a log call. Framework code uses `framework + '-' + ClassName`; app code uses `appId + '-' + ClassName`. A good TAG is what lets you filter the console to your own output.

### A worked example

This is an illustrative controller (the structure follows Part 3; the ids are examples, not from a real app). It logs the lifecycle so you can see the order of events at `trace`, and it never uses `console.log`:

```js
const TAG = 'MYTECHMOBILE-AppCustomizations';

class AppCustomizations {
  applicationInitialized(app) {
    this.app = app;
    app.log.i(TAG, 'applicationInitialized');
  }

  pageInitialized(page, app) {
    this.app = app;
    this.page = page;
    app.log.d(TAG, 'pageInitialized', page.name);
  }

  async pageResumed(page, app) {
    app.log.d(TAG, 'pageResumed, loading woDS');
    const t0 = Date.now();
    try {
      const ds = app.findDatasource('woDS');
      await ds.load();
      app.log.d(TAG, 'woDS loaded ' + ds.items.length + ' records in ' + (Date.now() - t0) + ' ms');
    } catch (e) {
      app.log.e(TAG, 'woDS load failed', e);
    }
  }
}

export default AppCustomizations;
```

Notice what a reader of that log can now answer: did the hook run, how many records came back, how long did it take, and what was the error. Compare that with `console.log('here')`.

### Rules of thumb for log messages

| Do | Don't |
|---|---|
| Start with a verb, include the key identifier, add timing where relevant | Log "here" or "done" |
| Pass the error object as the last argument | Concatenate `e.message` and lose the stack |
| Use `log.d` / `log.t` for chatty output | Use `console.log` (IBM's guidance says not to) |
| Log login type, token-refresh outcome, load start and finish | Log raw credentials, tokens, cookie values or personal data |
| Keep INFO to one line per milestone | Call `JSON.stringify` on large objects at INFO or above |

The last row of that table is a security rule as much as a style rule. A trace log that includes a bearer token and gets pasted into a support case is a credential leak.

## 🎚️ The MAS 9.2 `default-log-level` Attribute

MAS 9.2 (GA 25 June 2026) added an attribute on the root element of the app:

```xml
<maximo-application id="mytechmobile" default-log-level="debug" ... >
```

Our research base records this from the MAS 9.2 what's-new material as `default-log-level` on `<maximo-application>`, used to set a default log level for the **preview** (IBM-reported). That is all we can responsibly say. The IBM Docs page that defines the accepted values and the exact scope returned HTTP 403 to our tooling, and our general web searches found no independent write-up. So we do **not** state the value list, whether it applies to published builds, or whether the `_graphite_logLevel` URL parameter overrides it.

Here is how we would use it, with those unknowns respected:

| Question | Our guidance |
|---|---|
| Can I set it during development? | Yes, as a convenience for preview, and verify the effect in your own environment |
| Does the URL parameter still work? | Assume yes and test: load the preview with the parameter and with the attribute removed |
| Should it go to production? | No. IBM's guidance is ERROR-only by default; remove it in the reviewed commit before you publish |
| Where do I check the real behaviour? | The 9.2 Application Configuration help and your own test |

Put one line in your pull request checklist: *"no `default-log-level` below `error` in the published `app.xml`."* It is cheap and it prevents a very quiet class of incident.

## 🔎 From DOM to XML: Finding the Element That Is Wrong

You see a wrong label or a missing field in the browser. Which line of `app.xml` produced it? IBM's **Debugging UI** page in the MAF Configuration Practices site gives a five-step workflow (IBM-reported):

1. Launch the Role-Based Application you want to debug (IBM's example is TECHMOBILE).
2. Open an existing record that exercises the feature, such as a work order that has an asset.
3. Right-click the element and choose **Inspect**. Hover over the HTML to highlight the matching part of the UI.
4. Record the `id` attribute of the element that wraps what you care about. IBM's example value is `yzqaa`.
5. In the configuration tool, open the app, click in the code editor, press Ctrl+F or Command+F, paste the id, and "the code editor should automatically jump to that element with the correct id."

The page describes the mapping key as the DOM `id` and does not go further into how the runtime derives the value, so we do not either. The practical meaning is this: **component ids in `app.xml` are the contract between the XML, the DOM and your delta file.**

### The same trick in your local workspace

With MAF Local Configuration (Part 5) the XML is on disk, so use your editor's project-wide search instead of the browser tool:

```bash
# Illustrative: find a component id across the workspace XML
grep -rn 'id="assetdesc"' src/ --include=*.xml
```

### What the lookup can and cannot tell you

| You learn | You do not learn |
|---|---|
| Which component produced the element | Whether the data inside it was right |
| Which XML file owns it (main file or an included file) | Whether a controller changed it at runtime |
| That an id you expected is missing (not rendered) | Why a `visible` or `enabled` expression evaluated false |

For that last row, go back to Layer 2: log the expression's inputs at `debug`.

<aside>

💡 **Key insight:** if you rename a component id to "tidy up", you break the DOM-to-XML map, any controller that finds the component by id, and the delta that tracks your change. Part 2's rule stands: **keep IBM component ids unchanged**, and choose your own ids for new components deliberately.

</aside>

## 🛰️ Layer 3: The Server Side

When the UI is empty and the client log says "loaded 0 records", ask whether the server ever answered.

### The Logging application: OSLC and SQL

IBM Support's mobile troubleshooting guidance is consistent (IBM-reported): open the **Logging** application, search for the **OSLC** and **SQL** loggers, set them to **INFO**, reproduce the error, and collect `SystemOut` and `SystemErr` with matching timestamps. In MAS Manage, use the same loggers but collect the logs from the **Manage pod**. If INFO is not enough, support may ask for **DEBUG**, which IBM warns "can impact the server performance". Start at INFO and change it back afterwards.

```bash
# Illustrative: tail a Manage pod's log while you reproduce (names are examples)
oc get pods -n mas-<instance>-manage | grep -i maxinst
oc logs -f -n mas-<instance>-manage <manage-pod-name> | grep -i -E "oslc|MAFAPPDATA|graphite"
```

Which pod and which workload names apply depends on how Manage is deployed (server bundles such as UI, MIF or cron), so check yours before you copy the command.

### The `streamLog` endpoint

Our research base lists a server log stream method on the Logging service (IBM-reported, via the MAF Configuration Practices site):

```
/maximo/oslc/service/logging?action=wsmethod:streamLog
```

It exists so you can watch the server log from a browser or a REST client without shell access to the pod. Be careful with what you claim about it: we did not re-verify its parameters, authentication or output format this run, and the IBM Docs page was unreachable. Treat it as follows.

| Question | Guidance |
|---|---|
| Does the path exist? | IBM-reported in our research base; confirm on your version with a safe `GET` as an authorised user |
| Does it need the Logging application's loggers set first? | Almost certainly it only streams what the configured loggers write; set OSLC and SQL to INFO first |
| Who may call it? | Treat it as an administrative endpoint; use the same API key or SSO rules as the rest of `/maximo/oslc` |
| Is it production-safe? | A streaming log can contain business data. Use it in non-production, or under change control |

If your platform team cannot give you pod access, `streamLog` is the question to ask them about. If it is not available on your version, the downloadable logs in 9.2 (next section) cover the build and publish side.

### Publish, preview and build logs in 9.2

MAS 9.2 added real-time progress for preview, publish and save-and-preview jobs, a queue for them, and **downloadable preview, publish and build logs** in Application Configuration (IBM-reported, from the 9.2 what's-new material in our research base). The failure toast also links the build log. An IBM Ideas request raised before 9.2 complained that teams depended on an SRE opening a case to see the `graphite-configuration` pod logs when a build failed, which is exactly the gap these downloads close.

| When this happens | Download this |
|---|---|
| Preview never finishes | The preview log |
| Publish ends in an error toast | The build log from the toast, then the publish log |
| The app builds but misbehaves | Not a build log problem; go to Layers 1 and 2 |
| You are opening an IBM case | All three, plus `app.delta.xml` |

## ✅ Is the Code You Are Debugging the Code That Is Running?

Before you touch code, prove what is deployed. Our research base records a practitioner technique for reading the version of a deployed app (practitioner-reported):

```
https://<host>/maximo/oslc/graphite/techmobile/build.json
```

`build.json` holds the build version. Each publish also creates a new revision row in `MAFAPPDATA`, with a `VERSION` taken from `build.json`, a `REVISION` that increments, a `STATUS` of ACTIVE or DISABLE, and `DEPLOYBY` and `DEPLOYDATETIME` columns (Part 4 and the DOC17 storage notes). Together they answer "what is live, who published it and when".

```sql
-- Illustrative read-only query against the Manage database
SELECT appid, version, revision, status, deployby, deploydatetime, ismobile
FROM   mafappdata
WHERE  appid = 'MYTECHMOBILE'
ORDER  BY revision DESC;
```

### The "published but not showing" checklist

| Check | Why |
|---|---|
| `build.json` version equals what you published | Confirms the browser is served your build |
| Latest `MAFAPPDATA` row is ACTIVE and has the revision you recorded | Confirms the publish landed |
| `ISMOBILE` is on for the app | A duplicated app's "Mobile?" flag is off by default, so devices will not receive it |
| Hard-reload the browser (clear cache) | The RBA can hold a stale bundle |
| Device has synced or re-logged-in | A device only learns about a new version through its own flow (we could not confirm the exact trigger; see Part 7) |

If the browser RBA does not reflect a publish, two practitioner and IBM-support remedies are recorded in our research base. A practitioner thread says to delete the `maf` directory under the path set by `mxe.int.globaldir` so the app is re-extracted, and IBM technote ibm16988871 says to delete the app's `build/src` folder (their example is `TECHMOBILE/build/src`) to force a rebuild. Both are blunt instruments; use them in non-production first and with the platform team in the room.

## 📱 Layer 4: The Device

A browser preview is not the offline app. The device has a local database, a WebView, its own sync and its own log. That is why "works in preview, blank on phone" is such a common call. Part 7 explains the offline data model; here is how to see what the phone sees.

### Step 1: the in-app debug log

IBM Support's mobile guidance (IBM-reported): in the app, go to **Help and Support**, then **Log data**, and mark **Enable debug logging**. Reproduce the problem, then use **Share logs** to save or email them. This is the first thing IBM Support will ask for, and it needs no tooling. IBM's guidance also says the server logs are not required as first-set evidence when the problem is purely in a mobile feature such as the camera or an unresponsive button, though support may ask later.

### Step 2: remote DevTools with `chrome://inspect`

For a debuggable Android build, enable developer options and USB debugging on the phone, connect it, and on your workstation open:

```
chrome://inspect/#devices
```

You can then inspect the app's WebView, with the Console, Network and Application (storage) panels. IBM Community threads on debugging the mobile app describe this approach, and one 2020 thread (on the older Anywhere product) reports that the Play Store build was not debuggable, so the answer was to build a debuggable APK. Do not assume a store build will appear in the inspect list.

| Problem | Likely cause | What to try |
|---|---|---|
| Device not listed | USB debugging off, no authorisation prompt accepted | Re-plug, accept the key on the phone |
| App listed but no WebView | Release build is not debuggable | Use a debug build; ask IBM or your mobile team |
| Console is empty | Log level is default | Enable in-app debug logging first |
| Cannot reach a local server from the phone | Port not reachable | Use port forwarding in the inspect window (see below) |

### Step 3 (Gen 1 only): preview on device with the Docker image

If you are still on MAS 8.x or 9.0 with the Docker `maf-tools` image, IBM's *Preview on device in Configuration app* blog (30 November 2022) describes the device-side workflow (IBM-reported):

1. The preview feature works **only in DEBUG builds** of the Android app, which the article says you obtain through an IBM contact.
2. Enable remote debugging on the device.
3. Start the container with the environment variable `GRAPHITE_PREVIEW=1`; preview is off by default.
4. Make sure the device can reach the Configuration application (test it in the device browser).
5. In Chrome DevTools connected to the device, run in the Console: `preview.preview(<preview server URL>, <app id>, {live:true})`, where the preview server uses port 3006 and the app id is the `id` attribute of the `application` element in `app.xml`.
6. Edit and **Save**. The device prompts you to reload.

The article lists limits: live mode polls for changes, `preview.reset()` stops the running tasks, repeated reloads can cause out-of-memory crashes (the suggested fix is to update Android System WebView), and the feature is "not supported through regular support channels" and provided as-is.

A January 2025 IBM Community thread from a developer running the 8.9 image under WSL on Windows shows what goes wrong in practice: `Failed to connect to localhost/127.0.0.1:3006`, a mixed-up 3001 versus 3006 port, and port forwarding in the inspect window as a workaround. The thread had no accepted answer when we read it. The lesson: **ports 3001 (configuration app) and 3006 (preview server) are different services**, and Docker under WSL needs the ports reachable from the phone, not just from the host.

For Gen 2 and Gen 3 (Application Configuration and Local Configuration), the device-preview path is different and not documented in the sources we have; a Local Configuration preview runs on `localhost:3000` in a browser (Part 5). Our research base does not record a supported "live device preview" for Gen 3, so we do not claim one.

## 🚦 Reading the Failure: The Triage Table

When you do not know where to start, start here.

| Observation | Most likely layer | Next action |
|---|---|---|
| Console shows a red error as the first line | 1 or 2 | Read it, find the TAG or component id, fix |
| Console is clean, UI is wrong | 1 | Inspect element, map id to `app.xml`, check expressions |
| Console shows "0 records", Network shows 200 and an empty body | 3 | Check security, saved query, object structure |
| Network shows 401 or 403 | 3 | Security groups, API key, session |
| Network shows 413 | Platform | See `DT449679` / `DT450721` below |
| Works on the preview, not on a published RBA | Deployment | `build.json`, revision, cache |
| Works in RBA, not on the phone | 4 | In-app debug log, `chrome://inspect`, offline data |
| Publish stuck on "running" | Platform | Check for an invalid `app.xml` (`DT503372`), get the build log |
| Preview shows `ModuleNotFoundError` after a save | Platform | `DT458704` (Docker 9.0.16-9.0.19) |

### Five tests that remove most guesses

1. **Does it fail with your customization removed?** Comment out your `AppCustomizations.js` registration and retry. If the base app also fails, it is the platform or the data, not your code.
2. **Does it fail for another user?** Security groups and site access change what datasources return.
3. **Does it fail in a second browser profile?** Cache and extensions cause "ghost" bugs.
4. **Does it fail on the local preview and on the published app?** Only-preview or only-published narrows the layer.
5. **Does it fail on the device with a fresh sync?** A stale offline database looks like a code bug.

### How to use the table honestly

- A `DT` number is a **lead, not a diagnosis**. Match the symptom, your exact MAS version and the fix version before you conclude anything.
- **`DT450848` has an unresolved fix version.** IBM gave both 9.1.7 and 9.1.8. If you are on one of those, test rather than assume.
- **`DT424062` has a status discrepancy.** Our base lists it as a known issue in 9.2.0, while our Part 3 research found a 9.2.0 readme entry reading as fixed. Check your own build.
- The 500 KB zip cap and the stale-image problem are **practitioner reports**, not IBM statements. Treat the workarounds as field experience.
- `DT503372` is the one to remember for Local Configuration users too: **validate your XML before you publish**. A malformed `app.xml` that saves silently and then hangs the publish is a misleading symptom, because the log will look like an infrastructure problem.

<aside>

💡 **Key insight:** the publish-to-test loop in 9.1 was the core pain that produced most of these entries, and it is what Local Configuration targets (Part 4). Fewer publishes means fewer chances to hit the platform's rough edges. Debug locally, publish rarely.

## 🧰 Field Pitfalls That Look Like Bugs

These are practitioner-reported and worth a mention because each one costs a day.

| Pitfall | What you see | Fix or check |
|---|---|---|
| WSL Docker cannot reach `localhost:3006` | Device or host connection refused | Make ports reachable from the device; port forwarding in `chrome://inspect` |
| Content Security Policy blocks external tiles | On 9.1.4, preview could not load OpenStreetMap tiles | Test maps on a deployed build; do not trust preview for third-party content |
| Component ids changed | Controller cannot find a component; delta shows odd changes | Restore original ids |
| Attribute names not lowercase | Silent misbehaviour | Keep attribute names lowercase (Part 2) |
| Publishing while the preview server is starting | Hung or odd publish | Wait for the preview to be ready (IBM guidance for Local Configuration) |
| Object structure duplicated | Offline data merges wrongly | Mobile merges object structures with the same root object; do not duplicate (Part 7) |
| Testing only in a browser | Passes preview, fails offline | Always smoke-test on a device for mobile apps |

## 🤖 Debugging With an AI Assistant (Carefully)

If you use IBM Bob or another assistant with MAF Local Configuration (Part 5; Part 9 covers the MCP side), debugging is a good job to give it, with guardrails. Our MAS-BOB series covers the tool itself; see [Bob Meets Maximo](/blog/mas-bob-04-bob-and-maximo).

| Good use | Guardrail |
|---|---|
| "Add `app.log.d` statements with a TAG to every hook in this controller" | Review that no secret or personal data is logged |
| "Explain this console trace" | Paste only sanitised logs |
| "Find the component with this DOM id in the workspace" | Fine, it is a read-only search |
| "Fix the bug" | Require a diff; keep changes to `app.xml` and `AppCustomizations.js`; never let it rewrite IBM component ids or edit out-of-the-box JS files |

Our research base records that the Graphite MCP server in Local Configuration has an open report of editing out-of-the-box JS files, which IBM's own support policy forbids. Keep file protection on and read every diff.

## 📜 The Commandments of Debugging MAF

1. **Locate the layer before you touch anything.** Browser, code, server or device.
2. **Prove what is deployed.** `build.json` and the `MAFAPPDATA` revision first.
3. **Put the log parameter before the hash.** `?_graphite_logLevel=trace#/page`.
4. **Read the first error, not the last.** The rest is fallout.
5. **Log through `app.log` with a TAG.** Never `console.log`, never a secret.
6. **Keep component ids.** They are the contract between DOM, XML and delta.
7. **Turn verbose logging off before you publish.** ERROR is the production default.
8. **Check the defect table before you rewrite code.** A `DT` number can save a day.
9. **Test on a device.** Browser preview is not the offline app.
10. **Attach `app.delta.xml` to every case.** It is the first thing support needs.
