# Maximo Application Framework Development: The Complete Series Guide

<aside>

🎯 **Who this is for:** Maximo developers and configurators who have been handed a Maximo Mobile or Role-Based Application change request and discovered there is no Application Designer to open; mobile leads who need to know why a change worked in the browser preview and failed on the device; MAS platform admins who own the OpenShift pod, the persistent volume and the security groups behind Application Configuration; and architects deciding how much custom MAF work is safe to carry through the next upgrade.

</aside>

**Series:** Series Index - *Maximo Application Framework Development* | **9 parts** | **Total read time:** ~2.5 hours

---

## 📖 Why This Series Exists

You know how to customize classic Maximo. You open Application Designer, drag a field onto `presentation.xml`, add an automation script, run a quick Database Configuration, and ship it. Then someone asks for a change to the Technician mobile app, or the new work order Role-Based Application, and none of that applies.

> *"Where's Application Designer for the mobile app?"*
> *"There isn't one. It's XML, JavaScript and a React build."*

That exchange is where most Maximo developers meet MAF. The **Maximo Application Framework** is the framework IBM uses for every modern, non-classic Maximo UI: the Maximo Mobile apps (Technician `TECHMOBILE`, Inspections `INSPECTION`, Service Request `SRMOBILE`, Inventory `IRMOBILE`/`ICMOBILE`) and the browser Role-Based Applications that replaced Work Centers. Health and Monitor ship MAF apps too. Internally IBM calls the framework **Graphite**, so if you have seen `/graphite/configtool/packages`, `graphite-tools.js` or `?_graphite_logLevel=trace`, you have already seen MAF under its other name.

Until now the content gap on MAF has been real. Our own MAS-MANAGE Part 2 and MAS-BOB Part 4 *mention* MAF, but they do not teach it. IBM's component reference, in turn, lives inside the product, under the Developer Documentation entry of the Application Configuration help menu, and is not published online. That is a recurring complaint among practitioners: the remaining difficulties are not configuration problems, they are framework questions with no public answer.

Two things changed in 2026 that make this the right moment for a developer-grade series:

1. **IBM brought MAF development back to the desktop.** In May 2026 IBM began shipping an early-access VS Code and IBM Bob extension, **MAF Local Configuration** (formerly "Local Dev Mode"). After two years of publishing-to-test inside a browser editor, you can once again edit in your own IDE, keep the source in Git, run a local preview server and review a diff.
2. **MAS 9.2 reshaped the surface.** The "Role Based Applications" menu was removed, mobile apps are now labelled "(Mobile)", `chat-log` is deprecated, and Application Configuration got a faster preview, a publish queue and downloadable build logs.

<aside>

💡 **Key insight:** The organizing idea of this series is a single sentence: **MAF work is ordinary front-end engineering with three Maximo-specific constraints - two supported customization seams, no Migration Manager, and an offline device you cannot test in a browser.** Every part either teaches you to work inside those constraints or shows you the tooling that makes them manageable.

</aside>

## 🧱 MAF in One Page

Before the part-by-part guide, here is the whole framework on one page. Everything below is expanded in the parts that follow.

| Dimension | Fact | Where it is covered |
|---|---|---|
| Internal name | Graphite (`/graphite/...` paths, `graphite-tools.js`) | Part 1 |
| Authoring model | Declarative XML compiled to React; minimal JavaScript | Parts 1-2 |
| Data access | `maximo-datasource` over OSLC object structures, e.g. `MXAPIWODETAIL` | Part 2 |
| Storage | `MAFAPPDATA` table, zip BLOB, one revision per insert | Parts 1, 8 |
| Supported customization | `app.xml` and `AppCustomizations.js` (plus CSS from 9.0) | Parts 2-3 |
| Configuration support floor | 8.10 and later | Part 4 |
| Environment promotion | Not via Migration Manager | Part 8 |
| Mobile runtime | Store app is a shell that downloads Graphite apps from the server | Parts 1, 7 |

*Source for the table: IBM documentation and IBM support pages (IBM-reported); see References.*

And here is how an app travels from source to screen:

```
┌────────────────────────────────────────────────────────────────────┐
│                      THE MAF APP LIFECYCLE                         │
│                                                                    │
│  app.xml ──┐                                                       │
│  *.xml     ├──► build ──► zip ──► MAFAPPDATA (new ACTIVE revision) │
│  AppCustomizations.js ─┘                         │                 │
│                                                  ├──► RBA in browser│
│                                                  └──► Mobile shell  │
│                                                       (downloads)  │
│                                                                    │
│  Authoring tool = Docker maf-tools │ Application Configuration │   │
│                   Local Configuration (VS Code / Bob)              │
└────────────────────────────────────────────────────────────────────┘
```

The point of the diagram is that **the authoring tool changes but the artifact does not**. Whichever generation of tooling you use, the output is a zip stored as a new revision in `MAFAPPDATA`. That is why the three generations can coexist in one shop, and why a team can adopt the new one without abandoning the others.

## 🛠️ Three Generations of Tooling

Most of the pain and most of the opportunity in MAF development sits in the tooling, so the series gives it two dedicated parts (4 and 5). The summary table is below; the evidence behind each row is in Part 4.

| Generation | MAS versions | Where it runs | Edit and preview loop |
|---|---|---|---|
| **1. `maf-tools` Docker image** | 8.4 - 9.0 | Developer desktop, a privileged container pulled from `cp.icr.io` with an entitlement key | Browser UI on :3001, local React preview on :3006, publish to Manage |
| **2. Application Configuration** | 9.1+ | OpenShift pod (`graphite-configuration`) with a persistent volume; users in the `MAFCONFIGADMIN` group | In-suite browser editor; early 9.1 preview was reported broken, so teams "published to test" |
| **3. MAF Local Configuration** | 9.1.21+ and 9.2.1+ | Your editor (VS Code or IBM Bob) with Node.js 20+ and Yarn | `yarn start` preview on `localhost:3000` against live Manage, local diff and delta, Git, publish |

*Sources: IBM documentation, IBM support pages and the ibm-mas/maf-local-dev-mode site (IBM-reported); practitioner reports for field behavior.*

The narrative in one paragraph: IBM moved MAF configuration off developers' laptops and into the suite in 9.1. That removed the Docker friction (privileged containers, 8 GB of RAM minimum, a separate image for every patch), but it replaced it with a browser-only editor, a preview that timed out on some 9.1 builds, upload size caps, and images that went stale after patches. Practitioners reported publishing to a server just to see whether a change worked. The Local Configuration extension is IBM's answer to that loop.

<aside>

⚠️ **Read this before you plan around Local Configuration.** The extension is **early access**, IBM describes it as **not for production use**, it is **IBM proprietary software** usable only with a valid MAS license, and the project site offers it **AS IS**. At the time of writing the latest release is **v0.0.1-beta.6 (2026-09-22)**, it is distributed through GitHub Releases rather than the Marketplace, and it **cannot create or clone applications** - you still need Application Configuration for that. Everything this series says about it is tagged accordingly, and Part 5 lists the open GitHub issues (notably the Windows build failure caused by the offline npm mirror). Nothing here should be read as a support commitment from IBM or from us.

</aside>

## 🧩 Part-by-Part Guide

### Part 1: What Is the Maximo Application Framework?

**Read Part 1 - [What Is MAF?](/blog/mas-maf-dev-01-what-is-maf)** · 16 minutes

The foundation: one framework, two delivery surfaces (offline-capable Maximo Mobile and online Role-Based Applications), and the architecture IBM describes as XML transformed into ReactJS applications and stored as zip files in a BLOB column of `MAFAPPDATA`.

**You learn:** why "MAF = Graphite" is a safe mental model; the application inventory (which apps are MAF and which are still classic Application Designer screens, including the list of back-office apps that are not moving); what MAF replaced (Maximo Anywhere, Work Centers) and why neither migrates; and how to confirm the app IDs on your own system with `GET /graphite/configtool/packages` or `SELECT APPID FROM MAFAPPDATA`.

### Part 2: Anatomy of app.xml

**Read Part 2 - [Anatomy of app.xml](/blog/mas-maf-dev-02-app-xml-anatomy)** · 18 minutes

The file you will edit most. A downloaded app is a project with `src/app.xml`, included XML files, `AppCustomizations.js`, `i18n/labels.json` and, from 8.11, an auto-generated `app.delta.xml`.

**You learn:** the skeleton (`maximo-application`, `pages`, `states`, `dialogs`); the three datasource types (`maximo-datasource`, `json-datasource`, `custom-datasource`) and the properties that matter (`saved-query`, `where`, `page-size`, `pre-load`, `offline-immediate-download`); why `id` values must never be edited, attribute names must be lowercase and declaration order matters; and how to read a schema against an object structure such as `MXAPIWODETAIL`. A short taste of what the part works through:

```xml
<maximo-datasource id="woListDS" object-structure="MXAPIWODETAIL" saved-query="ASSIGNEDWORK">
  <schema>
    <attribute name="wonum" searchable="true" id="attr_001"/>
    <attribute name="description" searchable="true" id="attr_002"/>
  </schema>
</maximo-datasource>
```

### Part 3: Controllers and AppCustomizations.js

**Read Part 3 - [Controllers and AppCustomizations.js](/blog/mas-maf-dev-03-controllers-appcustomizations)** · 18 minutes

The only supported place for custom JavaScript, and the reason your customizations can survive a fix pack. IBM's own wording is that `AppCustomizations.js` "persists through upgrades".

**You learn:** the lifecycle hooks (`applicationInitialized`, `pageInitialized`, `pageResumed`, `onBeforeLoadData`, `onAfterSaveData` and friends) and the order they fire; event bubbling from component to datasource to page to application controllers; the support tiers (app.xml supported, AppCustomizations.js supported, separate controller classes "limited support", edited OOTB controllers unsupported); how to wrap an existing controller method safely; and community recipes for setting a field from a button, restricting work order statuses and building a hierarchical classification lookup.

### Part 4: From Docker to Desktop

**Read Part 4 - [Three Generations of MAF Tooling](/blog/mas-maf-dev-04-tooling-generations)** · 17 minutes

The tooling history with the receipts: commands, versions, defects and the practitioner quotes that explain why IBM kept changing the model.

**You learn:** the `docker run` pattern and entitlement-key login for `maf-tools`; how Application Configuration is enabled (persistent volume, access mode, `MAFCONFIGADMIN`); the 9.2 improvements IBM reports (zip upload auto-creating deltas, a FIFO queue for preview and publish, downloadable logs, a claimed 50-80% faster preview build); the known-defect table; and a decision guide for which generation to use for which job. Note that several 9.1 and 9.2 claims in this part rest on IBM Documentation pages, which we re-checked where IBM's content API allowed, and flag where we could not.

### Part 5: Hands-On with MAF Local Configuration

**Read Part 5 - [Local Configuration in VS Code and IBM Bob](/blog/mas-maf-dev-05-local-configuration-handson)** · 20 minutes

The longest part and the one most readers will bookmark. A step-by-step workflow on the early-access extension, from install to publish, including the things that are not in IBM's quick-start.

**You learn:** prerequisites (VS Code 1.74+ or IBM Bob, Node.js 20+, and Yarn, which the build and preview tasks shell out to); the install script and why regulated shops should download and verify the VSIX instead of piping a script into bash; the three authentication methods (OIDC with a PKCE client, username and password, API key) and the rule that API keys work against the Manage URL while OIDC uses the MAS Home URL; why registering the OIDC client needs cluster-level secrets once and should be a platform-team task; the offline npm mirror that makes or breaks `yarn build`; the preview server on `localhost:3000`; the publish pipeline; and the open issues. Where IBM's site and the extension's code disagree (for example the offline-cache location), the part says so instead of picking a winner.

### Part 6: Debugging MAF Apps

**Read Part 6 - [Debugging MAF Apps](/blog/mas-maf-dev-06-debugging)** · 16 minutes

A practical debugging toolbox, because MAF failures rarely announce themselves. An invalid `app.xml` can save with no error and then hang the publish.

**You learn:** the `?_graphite_logLevel=trace|debug|info|warn|error` URL parameter; tagged logging with `this.app.log.d(TAG, ...)`; the server-side `streamLog` endpoint; mapping a DOM id in the browser inspector back to a component id in `app.xml`; checking what is really deployed through `/maximo/oslc/graphite/<app>/build.json`; mobile device inspection with `chrome://inspect`; what to do when a publish does not show up in the RBA; and the defect table by reference number.

### Part 7: Offline by Design

**Read Part 7 - [Offline by Design](/blog/mas-maf-dev-07-offline-data)** · 17 minutes

The part that explains why "it worked in the browser" is not a test result for a mobile app.

**You learn:** the preloaded reference database and how datasources opt in; the mobile master schema, which Maximo merges by object rather than by datasource id (which is why duplicating object structures causes trouble); `offline-immediate-download`, `download-page-size` and `mobile-qbe-filter`; cross-app data sharing introduced in 9.2.0; how errored transactions surface; and a device test checklist. Open questions in IBM's material, such as conflict-resolution rules and how a device detects a new app version, are marked as unverified rather than guessed.

### Part 8: Ship It

**Read Part 8 - [Promoting and Upgrading MAF Apps](/blog/mas-maf-dev-08-promotion-upgrades)** · 19 minutes

The admin-tier part, and the one that saves the most pain. IBM states that Migration Manager cannot move a Maximo Mobile or Role-Based (Graphite) application from one environment to another, so you need a deliberate strategy.

**You learn:** the `MAFAPPDATA` columns and revision behavior; why there is no IBM-documented revert and what the unofficial SQL approach risks; the promotion options compared (republish a Git workspace per environment, manual copy, REST upload, CI/CD); the delta model for upgrades (`diff` to create a delta against the original, `apply` to bring it forward) and the 9.2 behavior of generating deltas for all XML files; the security grants (`MAFCONFIGADMIN`, `OSLCMAFAPPDATA`); and a Git-driven release flow.

### Part 9: AI-Assisted MAF

**Read Part 9 - [AI-Assisted MAF](/blog/mas-maf-dev-09-ai-assisted-maf)** · 16 minutes

The extension bundles a Graphite MCP server and a "MAF Config" mode for IBM Bob. This part evaluates both honestly, including the open issues where the MCP server edited out-of-the-box JavaScript files, which IBM's own support policy forbids.

**You learn:** what the bundled `@maximo/graphite-mcp-server` and the MAF Config mode's skill catalog do; the review guardrails for AI-authored MAF changes (restrict edits to `app.xml` and `AppCustomizations.js`, never let an agent rewrite component ids, require a Git pull request that includes `app.delta.xml`, publish only from a reviewed commit, test offline behavior on a device); and where agent-neutral MCP assets such as Max_mcp and Max_Interfaces complement it on the data and API side. Whether IBM's MCP server works from non-Bob agents is unverified, and the part says so.

## 💡 Key Themes Across the Series

**Two supported seams, and everything else is on you.** App XML and `AppCustomizations.js` are what IBM supports and what survives upgrades. Every part repeats the same discipline: stay in those two files, keep IBM's component ids untouched, and treat edits to out-of-the-box controllers as a decision to merge by hand at every release.

**Duplicate or modify in place - decide once.** If you configure the default app, an upgrade archives it and the new version becomes active; if you configure a duplicate (say `TECHMOBILE` to `MYTECHMOBILE`), IBM does not touch it, but it falls behind and you bring your configuration forward with deltas. Parts 4 and 8 give the trade-off, and Part 5 notes that the local tool cannot clone, so the duplicate is made in Application Configuration first.

**The browser is not the device.** A localhost preview does not exercise the offline path. Parts 6 and 7 build a device-testing habit because datasource, lookup-data and `mobile-qbe-filter` changes behave differently once data is on a handset.

**Source control is the missing safety net.** Because there is no Migration Manager and no IBM-documented revert, Git plus a publish pipeline is the only reliable history. Local Configuration is the first IBM tool that makes that natural, which is why it gets two parts.

**Vendor claims are labelled.** Performance figures, support statements and roadmap items come from IBM's own documentation and site and are tagged IBM-reported; they are not independently audited. Items that rest on a single weak source (the live-reload mechanism, whether a three-way merge UI exists, whether the Graphite MCP server works outside Bob, conflict-resolution rules) are carried as open questions, not facts.
