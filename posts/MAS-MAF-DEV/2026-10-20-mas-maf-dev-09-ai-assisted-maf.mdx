# AI-Assisted MAF: Bob's MAF Config Mode, the Graphite MCP Server and Guardrails

<aside>

Parts 3, 5 and 8 of this series are the background.

</aside>

## 🔥 The Agent That Edited the Wrong File

It is the second week of July 2026. A MAF developer opens the brand-new Local Configuration extension in IBM Bob, types one sentence ("add a COLOR field to the Create Service Request page") and watches the assistant go to work. A few seconds later the editor shows a warning. The assistant has changed a JavaScript file that belongs to IBM.

Not a custom file. Not `AppCustomizations.js`. An out-of-the-box controller.

The developer files a GitHub issue the same evening. The maintainer's reply is refreshingly candid: right now there are no guardrails in place at all, and the next job is the part that adds modes and rules.

> *"It worked. It also did the one thing IBM's support policy says never to do."*

That is the whole story of AI-assisted MAF development in one incident. The agent was fast, plausible and wrong in a way that does not show up until your next upgrade, when the delta model has nothing to merge against. Everything IBM added afterwards (a dedicated Bob mode, a skill catalog, file protection, an MCP server that looks things up instead of guessing) is an attempt to keep the speed and remove the plausible-and-wrong.

This final part of the series walks through what IBM actually shipped, what we found when we opened the package up, what went wrong early, and the guardrails we would require before anyone merges an AI-authored MAF change. It also shows the agent-neutral version of the same idea, because the pattern is bigger than one editor.

IBM's project site says it is offered "AS IS, WITH NO WARRANTY OF ANY KIND" and positions it as an enhancement to the supported MAF configuration tool; it is not a production-supported product, and its AI features are the newest and least settled part of it. We did not test that.

## 🧭 What IBM Ships: Three Pieces and a Command

The AI features of the Local Configuration extension are not one thing. There are three components and one command that installs them.

| Piece | What it is | Where it appears | First shipped | Source |
|---|---|---|---|---|
| **Graphite MCP server** | `@maximo/graphite-mcp-server` v1.3.0, bundled in the extension; answers questions about the Graphite component registry and Manage object structures | `external-tools/graphite-mcp-server/` in the package; launched over stdio | beta.1, 2026-07-15 | from the package, release notes |
| **Auth-bridge wrapper** | `graphite-mcp-server-wrapper.cjs`; reads a credentials file, sets the `GRAPHITE_PROXY_*` environment, spawns the server with `--stdio` | `external-tools/` | beta.1 | from the package |
| **MAF Config Bob mode** | A Bob custom mode (slug `maf-config`, display name "MAF Config") with five rule files | `external-tools/bob/modes/maf-config/` | beta.2, 2026-07-28 | release notes, from the package |
| **Skill catalog** | Markdown skills derived from IBM's Configuration Practices docs, loaded by the mode with `use_skill` | `external-tools/bob/skills/` | beta.1/beta.2 | from the package |
| **Command** | **Configure Bob Features (Graphite MCP)**, command id `maximoDevTools.configureBobFeatures` | VS Code / Bob command palette | beta.1 | release notes, from the package |

The practical way to think about it: the MCP server answers "what exists?", the skills answer "how does IBM say to do this?", the mode enforces "look it up, then write it, and never touch IBM's files", and the command copies all of it into your workspace in one step.

<aside>

💡 **Key insight:** Nothing here makes the model smarter about MAF. It narrows the model's room to improvise. The value is a retrieval and process layer wrapped around a general-purpose assistant, and that is exactly how you should evaluate it: by what it stops the assistant from guessing, not by how clever the output looks.

</aside>

The three pieces matter in a particular order. The Bob mode instructs the assistant to use the MCP tools, and the MCP server needs credentials, which only the command supplies. Skip the command and you have a mode with nothing to call. Run the command against a production-connected session and you have just handed an assistant a live token. We will come back to that, because it is the single most important operational fact in this post.

## ⚙️ Configure Bob Features: What the Command Actually Does

IBM's release note for beta.1 says the command "automates Graphite MCP server setup for the IBM Bob AI assistant", writing a wrapper file and registering the server in `~/.bob/config.json`. That is what our research base recorded. When we read the beta.6 package, the command's code described something a little different and more specific, so here is the beta.6 behavior (from the package) as a numbered sequence.

1. **It needs an active MAS session.** It reads the session from the extension's connection manager, so you must already be signed in (Part 5), and it determines the auth method: password, OIDC or API key.
2. **It builds the Manage URL.** It takes the instance URL from the extension's secret store and strips any trailing `/maximo`, because the MCP server adds that itself.
3. **It creates a `.bob/` directory in your workspace** if it does not exist.
4. **It writes `.bob/graphite-mcp.json`.** The file holds the URL, the auth method, the credential (the session's access token, a base64 password string, or an API key) and an `allowSelfSignedCerts` flag.
5. **It patches the project `.bob/mcp.json`**, adding or updating a `graphite-mcp` entry that runs `node` against the bundled wrapper, with one environment variable, `GRAPHITE_MCP_CREDENTIALS_FILE`, pointing at the file from step 4.
6. **It copies the MAF Config mode and the skills** into the workspace, with the skills landing in `.bob/skills/`.
7. **It keeps the file fresh.** An OIDC token expires, so the extension listens for session changes and rewrites the token in `.bob/graphite-mcp.json` when the active OIDC session refreshes. API-key and password credentials are not refreshed.

The MCP entry the command writes looks like this (paths shortened; this is the shape from the code, so check the file the command produces on your machine):

```json
{
  "mcpServers": {
    "graphite-mcp": {
      "command": "node",
      "args": ["<extension>/external-tools/graphite-mcp-server-wrapper.cjs"],
      "env": {
        "GRAPHITE_MCP_CREDENTIALS_FILE": "<workspace>/.bob/graphite-mcp.json"
      },
      "disabledTools": [],
      "disabled": false,
      "timeout": 300000,
      "alwaysAllow": [
        "graphite-list-components",
        "graphite-show-multiple-component-properties",
        "graphite-show-component-properties",
        "graphite-show-component-samples",
        "graphite-get-json-schema-for-object-structure",
        "graphite-find-maximo-object-structure"
      ]
    }
  }
}
```

And the credentials file it refers to, per the schema documented at the top of the wrapper:

```json
{
  "url": "https://<your-manage-host>",
  "authMethod": "oidc",
  "credential": "<access token, base64 maxauth, or API key>",
  "allowSelfSignedCerts": false
}
```

Two details deserve a pause.

**First, the credentials are a plaintext file inside the workspace.** In the code we read, the command writes the file with a plain write call. We found no step that adds `.bob/graphite-mcp.json` to `.gitignore`. That is a normal pattern for a developer tool, and it is also exactly how tokens end up in repositories. Put `.bob/graphite-mcp.json` in your `.gitignore` before you run the command, and remember that the repository's pre-commit secret scan is a backstop, not a plan. (This is derived from reading beta.6 code; confirm on your own build.)

**Second, `alwaysAllow` is pre-filled for six tools.** Bob's own MCP documentation says an `alwaysAllow` entry means Bob does not ask before calling that tool, provided auto-approval for MCP servers is switched on in Bob's settings; otherwise Bob proposes each tool use and waits. The six tools on the list are lookups against the framework's component registry and Manage's object-structure schema. One server tool is deliberately not on the list, `graphite-fetch-data-from-manage`, so a call to read live data should still prompt you. That is the right default. Keep it.

<aside>

💡 **Key insight:** The risky part of an MCP setup is never the tool list. It is the credential behind it. A server that can only read component docs is harmless; the same server holding a token for a production Manage is an agent with your identity. Point it at development, with a scoped login, every time.

</aside>

## 🔧 The Graphite MCP Server: Eleven Tools, Two Jobs

Reading the bundled server's registered tool names (from the package) gives eleven tools. They split cleanly into two jobs.

| Tool | Job | On the auto-approve list? | What it answers |
|---|---|---|---|
| `graphite-list-components` | Component registry | Yes | Does this component exist, and in which category? |
| `graphite-show-component-properties` | Component registry | Yes | Which properties does it take, which are required, what types? |
| `graphite-show-multiple-component-properties` | Component registry | Yes | The same, for several components in one call |
| `graphite-show-component-samples` | Component registry | Yes | Real usage examples from the framework source |
| `graphite-get-component-enum-values` | Component registry | No | Valid values for an enumerated property (icons, colors, statuses) |
| `graphite-search-icons` | Component registry | No | Find an icon name |
| `graphite-search-colors` | Component registry | No | Find a color token |
| `graphite-find-maximo-object-structure` | Manage metadata | Yes | Which object structure holds "work order labor"? |
| `graphite-get-json-schema-for-object-structure` | Manage metadata | Yes | Field names and types for a structure, in brief or standard mode |
| `graphite-fetch-data-from-manage` | Manage data | No | Run a read against live Manage |
| `graphite-mcp` (guide/overview resources) | Documentation | n/a | Controller and overview guides bundled with the server |

The two jobs map neatly onto the two ways an assistant goes wrong on MAF.

**Job 1: component and property hallucination.** The Graphite component reference is not public (a research gap we listed back in Part 2), so a general-purpose model has only training data, which may be stale or invented. If it writes `<maximo-datasource>` with an attribute that does not exist, the app either ignores it or fails at build time, and the error is not always friendly. The component tools replace memory with a lookup against the framework version your environment actually uses.

**Job 2: object-structure and field hallucination.** A datasource needs a real object structure name and real field names in its `select` and `where`. Guess `WORKORDERLABOR` instead of the structure the app should use, or `COLOUR` instead of `COLOR`, and you get empty lists or a READ-not-allowed error, which Part 8's security checklist covers. The two Manage metadata tools let the assistant find the structure and read its schema before it writes a line.

The MAF Config mode's rule file for these tools spells the discipline out. It tells Bob to call the lookups before generating XML or JavaScript that depends on them, not after drafting. It forbids inventing component names, property names, object structure names and field names. And it says not to ask the user for something a tool can answer, such as "what fields does your object structure have?" (from the package).

### A worked sequence

Take a request every MAF developer has met: add a lookup on a new attribute to a create page. A well-behaved run, following the mode's rules, goes like this.

| Step | What Bob does | Tool or skill used |
|---|---|---|
| 1 | Classifies the request: XML only, or does it need JavaScript? | Mode triage |
| 2 | Finds the object structure for the new data | `graphite-find-maximo-object-structure` |
| 3 | Reads the field list and types, brief mode first | `graphite-get-json-schema-for-object-structure` |
| 4 | Confirms the lookup and datasource components and their properties | `graphite-list-components`, `graphite-show-component-properties` |
| 5 | Loads the matching skill (for example a simple lookup practice) | `use_skill` |
| 6 | Writes the change in `AppCustomizations.xml` or `AppCustomizations.js` only | Mode safe-edit rules |
| 7 | Tells you to preview and device-test it | Mode workflow |

It is the maintainers' own issue #8 that shows where this chain breaks. A developer asked Bob to add an attribute with its domain values as a lookup. The server could not find the domain because it was not using the right object structure, and the developer had to feed the domain values to Bob by hand. The maintainer's note was that the server would need support for a get-list style call, and that he was not sure there was a generic domains API in the OSLC REST set. A commenter answered: **MXAPIDOMAIN** is the generic domain API. The issue is open, labeled enhancement and future. Until it lands, domain-driven lookups are a place where you supply the values and the agent supplies the XML.

## 🎛️ The MAF Config Mode: Process as a Guardrail

A Bob **custom mode** is a named bundle of role definition and rules that changes how the assistant works. The MAF Config mode (slug `maf-config`, shown as "🔧 MAF Config") arrived in beta.2 on 2026-07-28. Reading its files in the beta.6 package shows five rule documents and a role definition.

| File | What it governs |
|---|---|
| `maf-config.yaml` | The role definition: a MAF configuration specialist fluent in AppCustomizations.xml overrides, the global controller lifecycle, class extension, datasource configuration and the Graphite component model, with "safe edit guidance" as a stated competence |
| `1_workflow.xml` | The seven-step triage flow and a classification gate that separates XML-only changes from ones that need JavaScript |
| `2_configuration_practices.xml` | The three ways to customize and which are acceptable; the safe-edit rules |
| `3_decision_logic.xml` | A table of ambiguous phrases ("add validation", "filter data") with the one clarifying question to ask before routing |
| `4_troubleshooting.xml` | Routes error symptoms to `issues-*` skills instead of improvised fixes |
| `5_graphite_mcp_tools.xml` | When and how to call each MCP tool, and the sequencing rule: tools before code |

The workflow file's opening line is the philosophy: Bob "never writes configuration code from general knowledge" and always loads the appropriate skill first (from the package).

### The three-approach rule

This is the part that answers the incident from the start of the post. The practices file lists the three ways to customize a MAF app and tells Bob to enforce them in every response.

| Approach | Upgrade-safe? | IBM support | What the mode tells Bob |
|---|---|---|---|
| `AppCustomizations.js` | Yes, the file persists through upgrades | Full | Default for simple to moderate changes |
| Class extension (subclass an OOB controller in a new file) | Yes, the new file persists | Limited | For complex logic or guaranteed method order |
| Direct edit of an OOB controller | No, overwritten on upgrade | None, voids support | Never; redirect immediately and explain the risk |

This matches the support tiers in Part 3 and the id-and-delta warnings in Part 8. The mode's safe-edit rules add three refinements that are worth quoting in spirit: all custom JavaScript goes in `AppCustomizations.js` or a new extended-controller file the developer creates; **Bob cannot determine programmatically whether a given JavaScript file is out-of-the-box or custom-authored**, so it must state the guidance and must not silently edit JavaScript files that might be OOB without confirming with you; and new `.js` files created by the developer are safe for Bob to create and edit (from the package).

Read that second rule twice. It is IBM's own mode admitting the limit. The assistant has no reliable test for "is this file IBM's?", so it falls back on asking you. That is an honest design, and it also tells you precisely what your own guardrail has to do: provide the check the model cannot, with file protection and review.

### What a mode cannot do

A mode is an instruction, not an enforcement mechanism. It sits in the model's context. A long session, a user who says "just edit it", a skill that conflicts with a rule, or a plain model slip can all route around it. The maintainer's July comment that rules were "coming" was about this exact layer, and the mode is a strong improvement over nothing, but it is advisory. The enforcement layers are elsewhere: the extension's file protection, Bob's approval gates, and your Git review. We cover those in the guardrails section.

## 📚 The Skill Catalog: IBM's Playbook in Bob's Hands

The skills README in the package says "45 Bob agent skills for IBM Graphite/MAF configuration practices", and the mode README repeats "45-skill catalog". When we counted the folders in beta.6, the directory had **45 entries, of which one is `README.md`**, leaving **44 skills**. We use 44 plus a README, flag the difference in the review notes, and do not make anything of it. A count mismatch in an early-access doc is normal.

| Prefix | Count | What it holds | Examples (from the package) |
|---|---:|---|---|
| `simple-*` | 14 | Single-change recipes | `simple-add-tooltips`, `simple-marking-required-fields`, `simple-making-fields-read-only`, `simple-add-dashboard-tile` |
| `advanced-*` | 20 | Multi-step recipes with logic | `advanced-dynamic-mobile-filter`, `advanced-cross-app-datasource-sharing`, `advanced-restrict-complete-status`, `advanced-enable-wo-classification` |
| `concept-*` | 4 | Background the others lean on | `concept-mobile-master-schema`, `concept-preloaded-database`, `concept-dialog-component-guide` |
| `guide-*` | 2 | Component guides | `guide-datasources`, `guide-page-component` |
| `issues-*` | 3 | Diagnostic procedures | `issues-read-action-not-allowed`, `issues-debug-ui`, `issues-faq` |
| `graphite-configuration-advisor` | 1 | A top-level advisor | The entry point for open-ended questions |

These mirror IBM's public **Configuration Practices** site (14 simple and 20 advanced practices, basic concepts, troubleshooting and a FAQ, per the site's own contents page). If you have used that site, you already know the content; the skills turn it into material the assistant can load on demand instead of paraphrasing from memory. In practice, it gives Bob IBM's own MAF playbook.

Three of those skills line up with earlier parts of this series, which is the best test of whether the catalog is worth trusting:

- `advanced-dynamic-mobile-filter` is the `mobile-qbe-filter` pattern from Part 7. An assistant that loads it instead of improvising will write the filter in the place and form that actually works offline.
- `issues-read-action-not-allowed` is the security failure from Part 8: a user group missing READ on an object structure used by a new datasource.
- `issues-debug-ui` is the DOM-to-XML id mapping from Part 6.

Where the catalog stops is as informative as where it starts. There is nothing for promotion, delta files or release flow; those are process, and Part 8 plus your pipeline own them. There is nothing for Java-side extensions either, which is why the server-side counterpart lives in the [MAS-JAVA-EXTENSIONS](/blog/mas-java-extensions-series-index) series.

The extension's GitHub tracker is, at the time of writing, the only independent signal about how this works in the field. Three of the early issues concern the AI features. Our earlier research notes listed all three as open. We re-read them on 2026-10-20 through the GitHub API, and two have since closed, so here is the corrected picture.

| Issue | Title | Opened | State on 2026-10-20 | What the thread shows |
|---|---|---|---|---|
| #6 | MCP automatically updates OOTB JS files instead of custom one | 2026-07-15 | **Closed as completed**, 2026-07-16 | The reporter said the MCP never chose to create a new JS file, so it always triggered the protected-file warning. Maintainer: part 2 of the MCP server is the modes and rules, "right now there are no guardrails in place at all", implementing modes is the next priority |
| #7 | MCP Server seems to use a lot of token | 2026-07-15 | **Closed as completed**, 2026-07-16 | One prompt on a fresh task, with only the embedded MCP server and the Graphite mode, used one Bob coin. Maintainer: the server is optimized to be token efficient, but the spend is down to how Bob performs the task; simple JavaScript work typically costs 1 to 10 coins |
| #8 | Ability for MCP Server to discover domains | 2026-07-16 | **Open**, labels `enhancement` and `future` | The server cannot find the domain behind an attribute; MXAPIDOMAIN suggested as the generic domain API |

Be careful what you conclude from "closed as completed". The maintainer's comment on #6 admitted a gap and promised modes and rules. ## 🛡️ Guardrails for AI-Authored MAF Changes

Here is the set we would require. It starts from the five guardrails in our research base and adds two for the agent itself. Each guardrail has a reason that traces back to something earlier in this series.

| # | Guardrail | Why | Enforced by |
|---|---|---|---|
| 1 | **Keep changes in `app.xml`, `AppCustomizations.js` and developer-created files only** | OOB files are overwritten on upgrade and void IBM support (Part 3) | Mode rules (advisory) plus file protection plus PR review |
| 2 | **Leave file protection on** (`maximoDevTools.fileProtection.enabled` and `.showWarnings`, both default true) | It warns when you modify core files that are not upgradeable, using a manifest-checksum guard (Part 5) | The extension (the only machine check in the chain) |
| 3 | **Never let an agent rewrite component ids** | The delta model addresses controls by id; change one and the delta loses its anchor (Part 8) | PR review of the XML diff; a reviewer rule |
| 4 | **Require a Git pull request that includes the generated `app.delta.xml`** | The delta shows your changes relative to IBM's original, which is the cleanest view of what the agent really did | Branch protection |
| 5 | **Publish only from a reviewed commit, by a human with the release identity** | A publish creates a new ACTIVE MAFAPPDATA revision and there is no official revert (Part 8) | Credentials: agents never hold the production identity |
| 6 | **Test offline behavior on a device** | The browser preview never exercises the offline path (Part 7); no agent can see a device | A human with a phone |
| 7 | **Give the agent the least-privilege, development-only identity, and keep its credentials out of Git** | `.bob/graphite-mcp.json` is plaintext; a token there is a login | `.gitignore`, a scoped Maximo user, secret scanning |

### Turning the list into a pull request template

A checklist reviewers actually use is shorter than a policy. This is the one we would paste into the repository's PR template for a MAF app:

```markdown
## MAF change review
- [ ] Files changed are only: app.xml, AppCustomizations.js, new custom files
- [ ] No edits to files flagged by file protection (screenshot or note if a warning appeared)
- [ ] No component `id` values changed in default apps
- [ ] `app.delta.xml` regenerated and included
- [ ] New datasources use object structures that exist in TEST and PROD
- [ ] Security groups have READ on every new object structure
- [ ] Offline path tested on a device (device, OS, result)
- [ ] AI assistance used? Which tool/mode/skill: ______
- [ ] Release owner (human) will publish from this commit
```

The last-but-one line is the cheap one that teams skip and regret. Recording which tool, mode and skill produced a change makes a later bad pattern traceable to its cause, which is the AI-era version of writing the ticket number in the commit message.

### Reviewing an agent's diff

An AI-authored MAF diff has a few characteristic faults. These are the ones we would look for first, each tied to a check the reader can do in a couple of minutes.

| Symptom in the diff | What probably happened | Check |
|---|---|---|
| A changed `.js` file that is not `AppCustomizations.js` and not new | The assistant edited an OOB controller | Compare against IBM's original in `ibm-config`; revert |
| A component id differs from the base app.xml | The assistant "tidied" or regenerated a control | Revert; a delta anchored to the old id will fail |
| A property you cannot find in any component sample | A hallucinated attribute; the lookup was skipped | Run `graphite-show-component-properties` or read the component reference in-product |
| A `select` or `where` naming a field the object structure does not have | The schema lookup was skipped | Run the schema tool in brief mode; compare |
| A datasource on a structure that exists only in DEV | A structure created for the test and not promoted | Metadata lane first (Part 8) |
| A very large diff for a small request | The assistant regenerated a whole file | Ask for the minimal change; reject wholesale rewrites |
| Comments or attribute order churn across the file | Not necessarily the agent; the 9.1 migration drops comments and attribute order | Normalize in review (Part 8, IBM Ideas MASMOBILE-I-804) |

## 🧪 A Pilot You Can Run This Month

Do not start with a production app. Start with a one-week pilot on a development environment and a copy of one real app, and measure what you would measure for any tool.

| Day | Activity | Output |
|---|---|---|
| 1 | Install the extension (Part 5), sign in to a **development** environment with a scoped identity, add `.bob/graphite-mcp.json` to `.gitignore`, then run Configure Bob Features | A working MCP entry and a `.bob/` directory you have read line by line |
| 2 | Try five simple tasks from the `simple-*` skills (tooltip, required field, read-only field, tile, default query) with MAF Config mode | Time, Bobcoins used, diff size and defects per task |
| 3 | Try three `advanced-*` tasks (a dynamic mobile filter, a cross-app datasource, a status restriction) | The same four measures |
| 4 | Break it on purpose: ask for a change that tempts an OOB edit ("change the behavior of the work order list controller") | Did the mode refuse or ask? Did file protection fire? |
| 5 | Run the PR checklist over everything produced; device-test the offline-relevant ones | A defect log and a go/no-go for continuing |

The fourth day is the one that tells you the most. You are not testing whether the assistant is capable. You are testing whether your guardrails hold when somebody asks it to do the wrong thing, because someone will.

### What to expect, honestly

Nothing here is published as a benchmark for MAF work, and IBM's Bob-for-Maximo efficiency claims elsewhere come with no stated method, as the MAS-BOB series notes. Our expectation, which is an opinion and not a measurement, is that the lookup-driven tasks (component properties, object-structure fields, standard practices) are where an assistant earns its keep, and the judgment-driven tasks (what should this app do, how will it behave offline, is this the right clone-or-extend decision) are where it does not. A community evaluation of Bob on Maximo tasks by Yann Bordelanne, summarized in the MAS-BOB series, reached a similar conclusion: output quality depends heavily on the quality of the context you provide, and human validation stays in the loop.

## 🔀 The Agent-Neutral Angle

Everything above is wired to Bob because IBM ships the wiring for Bob. The underlying ideas are not Bob-specific, and you should not let a tool choice lock the practice in.

### What would transfer, and what we do not know

The Graphite MCP server is a standard stdio MCP server. The wrapper reads a credentials file, sets `GRAPHITE_PROXY_*` environment variables and spawns the bundled server with `--stdio`, passing the standard streams straight through (from the package). On paper, any MCP-capable client (Claude, Copilot, Cursor) that can launch a `node` command with an environment variable could launch the same wrapper.

We have **not tested that**. IBM documents and supports only the Bob path, and the claim that other agents can use the server remains unverified in our research base (DOC17 gap 12). There is also a licensing point: the extension is IBM proprietary software usable with a valid MAS license, so read the terms before copying bundled files out of it. What you can safely take from the extension is the **pattern**:

| Ingredient | Bob path | Agent-neutral equivalent |
|---|---|---|
| IBM's practices as loadable knowledge | MAF Config skills in `.bob/skills/` | The public Configuration Practices site, converted into your agent's skill, rules or `AGENTS.md` mechanism |
| Process discipline | A custom mode with five rule files | Repository rules: "triage, look up, then write; never edit OOB files" |
| Component and schema lookups | Graphite MCP server | A Maximo-side API for schemas and data, plus the in-product developer documentation |
| Permission gates | Bob approval gates, `alwaysAllow` | Your agent's approval and permission model |
| Review | PR with `app.delta.xml` | The same PR, with the same template |

### Where TMG's tools fit

TheMaximoGuys maintains two assets that sit on the Maximo data and API side of this picture. Neither replaces IBM's Graphite tools, which cover the component registry and the app-building side that only IBM can see.

| Asset | What it is | License | Role in an AI-assisted MAF workflow |
|---|---|---|---|
| **Max_Interfaces** | An API library for Maximo: 2,439+ endpoints across 14 modules, OSLC and NextGen REST, Postman v2.1 and OpenAPI 3.0 collections | **MIT, open source** | Give any agent real endpoint and field names, including `MXAPIDOMAIN`, so it does not guess an object structure or a domain API (the gap in issue #8) |
| **Max_mcp** | A Maximo MCP server: 175 tools across 20 modules (including Domains, Query, Security Groups, Autoscripts and Developer Tools), TypeScript with Zod validation, rate limiting, caching, retries, multi-environment and Docker; npm package `@themaximoguys/maximo-mcp` v2.0.0 | **Proprietary, not open source**; available through npm and GitHub | An agent-neutral MCP server for reading and, with scoped keys, changing Maximo data through the API layer, across Maximo versions |

A short, careful way to say how they combine: the Graphite server tells an assistant what a MAF page can contain, Max_Interfaces and Max_mcp tell it what the Maximo behind the page contains, and the Git review decides whether the result ships. Neither TMG tool edits a MAF app or understands app.xml, and we do not claim they do.

The MAS 9.2 native Maximo MCP server is the other option on the Maximo side. As the MAS-BOB series covers, it requires MAS 9.2, runs as an `instance-mcp` deployment, and generates tools from Manage; Max_mcp works against earlier versions as well and is something you operate yourself. They complement each other, and in either case the credential and its security group decide what the agent can do, not the tool list. For the connection pattern (a dedicated read-only key first, a scoped write key per use case, never the database), see [MAS-BOB Part 4: Bob and Maximo](/blog/mas-bob-04-bob-and-maximo).

<aside>

💡 **Key insight:** Treat the AI layer as three separable decisions: what knowledge the agent loads (IBM's practices), what live facts it can query (components, schemas, data), and what it may change (a branch, never a publish). You can swap the tool in each slot without changing the guardrails around it.

</aside>

## 🧰 Troubleshooting the AI Setup

| Symptom | Likely cause | First check |
|---|---|---|
| Bob shows "Request timed out" when the MCP server starts | The wrapper exited before the protocol handshake, for example a missing credentials variable | Run Configure Bob Features again; confirm `.bob/graphite-mcp.json` exists and `GRAPHITE_MCP_CREDENTIALS_FILE` is set. The wrapper sends a JSON-RPC error message on a fatal start-up fault so the client can show a real message |
| MCP tools return authorization errors after a few hours | The OIDC access token expired | The extension rewrites the token on session refresh; sign in again, or re-run the command. API-key and password credentials do not refresh |
| Tools return 404 or wrong-host errors | URL mismatch: OIDC uses the MAS Home URL, an API key needs the Manage URL | Issue #5 and Part 5; the command strips `/maximo` itself |
| The assistant invents component names | The mode is not active, the MCP server is disabled, or the model skipped the lookup | Confirm MAF Config is the selected mode, the server shows as enabled, and the tool list is populated |
| The assistant cannot find the domain behind a field | Known gap, issue #8 | Supply the domain values, or fetch them through MXAPIDOMAIN with a scoped read key |
| A change touches an `.js` file that is not yours | The assistant edited an OOB controller | File protection warning; revert and re-prompt with "AppCustomizations.js only" |
| Token or Bobcoin spend is high | MCP calls and skill loads add to every task | Start with a measured pilot; ask for smaller diffs; load one skill, not several |
| Self-signed certificate errors on a dev environment | `allowSelfSignedCerts` is false in the credentials file | Fix the certificate chain where you can; setting it true is a dev-only shortcut |
| Windows build fails with `@maximo/maxdev-cli` not found | The offline mirror is missing | Part 5 offline mirror section; issue #16, open |

## 📜 The Commandments of AI-Assisted MAF

1. **Thou shalt look it up, not guess it.** Components, properties, object structures and fields all have tools.
2. **Thou shalt not let an agent edit an out-of-the-box file.** Not once, not "just to test".
3. **Thou shalt keep file protection on.** It is the only machine check in the chain.
4. **Thou shalt not let an agent rewrite a component id.**
5. **Thou shalt keep `.bob/graphite-mcp.json` out of Git.** A token in a file is a login in a repository.
6. **Thou shalt connect agents to development, with the least privilege that works.**
7. **Thou shalt review the XML diff and the `app.delta.xml`**, not the assistant's summary of them.
8. **Thou shalt let only a human publish.**
9. **Thou shalt device-test what no agent can see.**
10. **Thou shalt remember that Local Configuration is early-access, AS IS and proprietary,** and keep Application Configuration warm as the supported fallback.
