<aside>

</aside>

## 🔥 The Day You Stop Publishing to Test

You changed one attribute on a Technician page. To see it, you pressed Publish in the browser editor, waited, opened a test device, and discovered you misspelled a datasource id. Now there is a new revision in `MAFAPPDATA` with your typo in it, and you are explaining to a supervisor why the test phone showed a blank screen.

That loop is the problem Part 4 described. This part is the fix, and it is a hands-on one: we install IBM's **MAF Local Configuration** extension, connect it to MAS, pull an app to disk, commit it to Git, preview it on `localhost:3000`, and publish it back. We also spend real time on the three things that will bite you: the **API-key URL mismatch**, the **offline mirror**, and the **fact that this tool is not finished**.

<aside>

⚠️ **Status, stated once and meant.** MAF Local Configuration is offered by IBM **AS IS**, with no warranty, as **IBM proprietary software** that is **not yet on the VS Code Marketplace**. IBM's earlier README wording, as recorded in our research base, calls it an **early access preview, not for production use**. On 19 October 2026 we re-fetched the public landing, install, features and manual pages and the repository page; they show the AS IS disclaimer but **do not repeat the early-access sentence**, and the repository page lists the license only as "IBM". We cannot tell whether IBM softened or relocated the wording, so we keep the hedge: it is a `v0.0.1-beta.6` tool, and everything below is **IBM-reported** unless we say we read it from the released package or from a practitioner source. It also **cannot create or clone applications**.

</aside>

By the end you will be able to:

1. Install the extension in VS Code or IBM Bob, and decide when **not** to use IBM's one-line installer.
2. Choose the right URL for OIDC versus API-key sign-in, and explain why OIDC setup is a platform-team job.
3. Diagnose the offline-mirror failure that stops `yarn build`.
4. Run the preview server, edit, and publish a new revision, knowing what the pipeline does.
5. Set up a Git-based workflow with review, and know the issues that are still open.

A note on sourcing, as in earlier parts. **IBM-reported** means IBM's public site, repository, release notes or issue tracker. **Package-reported** means we read it from the compiled released VSIX (`package.json` and code) during earlier research, not from prose documentation. **Practitioner** means a partner or community source. Items marked **UNVERIFIED** are in our research base as single or weak sources; we do not state them as fact.

## 🧰 Prerequisites and Install

### What you need before you start

| Requirement | Detail | Source |
|---|---|---|
| Editor | IBM Bob IDE, or VS Code 1.74.0+; the `bobide` or `code` command on PATH | IBM-reported |
| Node.js | 20.0.0 or later; used by the preview server and dev tools | IBM-reported |
| Yarn | Not in IBM's public list, but build, preview and publish shell out to `yarn` | Package-reported |
| Git | Any recent version; "optional, but recommended" | IBM-reported |
| Network | Internet for installation and for MAS authentication; GitHub reachable for the installer | IBM-reported |
| MAS | A valid license and an environment at 9.1.21+ or 9.2.1+ | IBM-reported |
| Operating system | No official support matrix; installer is bash; Windows needed fixes (#11 closed, #16 open) | IBM issue tracker |
| Platform | Application Configuration enabled, `MAFCONFIGADMIN` membership, a duplicated app | Cached IBM docs; see limits below |

Check your toolchain in one go:

```bash
node --version        # expect v20.x or later
yarn --version        # any current Yarn
git --version
code --version        # or: bobide --version
```

If Node is too old, IBM's install page suggests `nvm install 20 && nvm use 20` or installing from nodejs.org. If `code` is not found, run "Shell Command: Install 'code' command in PATH" from the Command Palette and restart your terminal (IBM-reported troubleshooting).

### Install option 1: the one-liner

IBM's documented install forms are:

```bash
# IBM Bob IDE
curl -fsSL https://ibm-mas.github.io/maf-local-dev-mode/scripts/install.sh | bash -s bob

# VS Code
curl -fsSL https://ibm-mas.github.io/maf-local-dev-mode/scripts/install.sh | bash -s vscode

# Interactive: prompts for an editor if several are found
curl -fsSL https://ibm-mas.github.io/maf-local-dev-mode/scripts/install.sh | bash
```

Per IBM, the script checks prerequisites, downloads the latest `.vsix` from GitHub Releases, installs and configures the extension, and prints next steps. In earlier research we read the script's logic: it queries the GitHub `releases/latest` API, takes the first `.vsix`, runs `<cli> --install-extension <vsix> --force`, and tells you that local Manage needs no extra setup while remote MAS needs the OIDC setup inside the plugin.

<aside>

💡 **Key insight:** `curl ... | bash` runs whatever that URL returns at the moment you run it. For a personal sandbox that is a judgement call. For a regulated shop it is a supply-chain risk, and security teams are right to refuse it.

</aside>

### Install option 2: the auditable way

IBM documents the manual path on its install and manual pages, and it is the one we recommend in a controlled environment:

```bash
# 1. Download the script and read it first
curl -fsSL https://ibm-mas.github.io/maf-local-dev-mode/scripts/install.sh -o install.sh
less install.sh
chmod +x install.sh && ./install.sh vscode

# 2. Or skip the script entirely: download the .vsix from GitHub Releases,
#    record its SHA-256 in your change ticket, then install it
sha256sum maximo-developer-configuration-tools-0.0.1-beta.6.vsix
code --install-extension maximo-developer-configuration-tools-0.0.1-beta.6.vsix
# Bob:
bobide --install-extension maximo-developer-configuration-tools-0.0.1-beta.6.vsix
```

The GitHub Releases page is `https://github.com/ibm-mas/maf-local-dev-mode/releases`. The Marketplace listing is described as "Coming Soon", so you will not find the extension by searching the Marketplace today. In the UI, use Extensions, then the "..." menu, then "Install from VSIX...".

If the extension does not appear after install, IBM's guidance is to **fully quit and restart** the editor (reloading the window is not enough), confirm it is enabled, and check the Output panel. IBM also says not to use `sudo` for the install and to check write access to `~/.vscode/extensions/`.

## 🔐 Signing In: OIDC, API Key, and the URL Trap

The extension supports three sign-in methods: OAuth 2.0 / OIDC, username and password, and API key (IBM-reported). Sessions appear in the editor's Accounts menu because the extension registers an authentication provider (package-reported). You can keep several sessions and switch between environments, and connections can be exported and imported (package-reported).

### Which URL goes with which method

This is open repository issue **#5**, "Different URL expected based on the authentication method" (opened 2026-07-15, still open on 19 October 2026). A maintainer's answer recorded in our research is blunt: use the **MAS Home URL** with OIDC; for an **API key you HAVE to use the Manage URL**.

| Method | URL to enter | Typical failure if wrong |
|---|---|---|
| OIDC / OAuth 2.0 | MAS Home URL, for example `https://home.<instance>.<domain>` | Redirect loop or "unable to register" if you use the Manage host |
| API key | **Manage** home URL, for example `https://<instance>.manage.<domain>` | 302 redirects or 401s if you use the MAS Home host |
| Username / password | Manage URL (local or classic Manage) | Authentication failure; common on non-OIDC dev boxes |

The hostnames above are illustrative patterns; confirm yours from the MAS admin dashboard.

A related fix: before beta.4, API-key sessions hit 302 redirect errors, and the release notes say the call path moved from `/oslc/` to `/api/`. If your API-key connection still fails, check your version before debugging anything else.

### Why OIDC is a platform task

For OIDC the extension registers a **public PKCE client** named `configtoolpkce` ("Maximo Configuration Tool") with the MAS OIDC server, then obtains tokens by authorization code and refreshes them automatically (package-reported). Registration needs the **MAS OAuth admin credentials**. The in-extension help points to the OpenShift secret `<instance>-credentials-oauth-admin` in the `mas-<instance>-core` namespace, and otherwise says to ask your cluster administrator to register the OIDC configuration from the plugin.

```bash
# Platform admin only. Illustrative: read the OAuth admin secret for the registration step.
# Instance name is a placeholder; do NOT hand these values to individual developers.
oc get secret <instance>-credentials-oauth-admin -n mas-<instance>-core \
  -o jsonpath='{.data.oauth-admin-username}' | base64 -d; echo
```

**Governance takeaway.** Registering the client needs cluster-admin-level secrets once. Make it a ticket to the platform team, record that it was done, and give developers a connection that works. Do not circulate the admin secret.

### The API-key alternative

On a development environment you may prefer API keys, which skip the client registration. In Gen 1 the key came from a single call, `POST /oslc/apitoken/create` with `{"expiration":-1}` (IBM-reported, Part 4), and a non-expiring key deserves the caution it implies. For this extension, give the key a short life, scope its user's security groups to what the work needs, and store it in your OS credential store, not in a repo. The extension stores credentials securely (IBM features page), but your `.env` file is your responsibility.

Whichever method you use, the signed-in user's groups need authorization on the **OSLCMAFAPPDATA** object structure, and on any object structure your datasources use (IBM-reported, Part 4).

### Self-signed certificates

Dev environments often use self-signed certificates. The extension allows this per connection (`allowSelfSignedCerts`, package-reported), and IBM's features page describes "configurable security settings". Use it for a lab, not for a shared environment with a proper CA.

## 📥 Download the App and Make Git Your Safety Net

Prerequisite: the app you want to change has already been **duplicated** in Application Configuration, for example `TECHMOBILE` to `MYTECHMOBILE`. The extension cannot create or clone applications. IBM's own limitation text says to use the MAF tool to clone for now.

1. Open the **Maximo Configuration Tools** view in the activity bar. You get a **Connections** view and an **Applications** view (package-reported).
2. Add a connection (name, URL, auth method), then sign in. In the Command Palette the equivalent is **Maximo Dev Tools: Sign In to MAS**.
3. In Applications, search for your app. The panel lists packages from five categories: `manage`, `core`, `addons`, `assist` and `monitor` (package-reported).
4. Download it.

A practitioner who tested the Technician app (MRM-EAM, 14 October 2026) describes the download as extracting the application, installing helper files, syncing offline development packages, and preparing dependencies and the build. After it finishes, the actions Open, Build, Publish, Duplicate, Migrate and Preview become available. Under the hood, the download calls `GET /graphite/configtool/packages/{app}/binary` and unpacks `app-source.zip` into the workspace (package-reported). The beta.6 setting `maximoDevTools.download.keepZip` controls whether the zip is retained.

### The one step that earns the tool its keep

```bash
cd <workspace>/MYTECHMOBILE
git init
cat > .gitignore <<'EOF'
node_modules/
build/
.env
*.log
EOF
git add -A
git commit -m "baseline: pristine download of MYTECHMOBILE from DEV rev <n>"
```

Do this **before** you touch a file, and note the `MAFAPPDATA` revision in the message. Now every XML and JS change is a diff, every review is a pull request, and the baseline is your rollback point. Neither Gen 1 nor Gen 2 gave you that cleanly.

Two cautions on the `.gitignore`. First, whether `build/` should be ignored depends on your promotion model; we ignore it because the pipeline rebuilds it, but check what your workspace contains before you copy that line. Second, do not commit `offline-mirror/` blindly: it is large, and it is served by MAS, so it can be regenerated. Decide with your team whether to keep it out of the repository (we do).

| What to commit | What to keep out |
|---|---|
| `src/app.xml`, included XML, `AppCustomizations.js`, `i18n/labels.json`, `app.delta.xml` | `node_modules/`, `.env`, logs |
| A baseline tag (`baseline-<rev>`) | The offline mirror (regenerable) |
| Any custom CSS (9.0+) | Credentials or API keys, ever |

The repository's own pre-commit secret scan, if you use TheMaximoGuys conventions, will block commits containing API keys. Use the same habit in your app repo.

## 🪞 The Offline Mirror: Your First Gotcha

Here is the failure, from open issue **#16** (filed 2026-10-04, still open on 19 October 2026): on Windows 11 against MAS 9.1.22, building the **ASSETMOBILE** app in VS Code fails with:

```
error An unexpected error occurred: "https://registry.yarnpkg.com/@maximo%2fmaxdev-cli: Not found".
```

### Why it happens

IBM's build packages, including `@maximo/maxdev-cli`, are **not published on the public npm registry**. A normal `yarn install` therefore has nowhere to fetch them. The extension compensates with an **offline mirror**. In the released package we read a `tools/configure.cjs` that builds an `offline-mirror/` directory in the workspace, holding npm tarballs **served by MAS**, plus `vendors/` and a `libraries.json` (package-reported). Yarn is then pointed at that local mirror. If the mirror is missing, incomplete or stale, yarn falls back to the public registry and you get the error above. A commenter on the issue said the fix is the offline mirror and that this "should [be] more clearly documented", which is a fair summary of where the docs stand.

### A documentation conflict we are not going to smooth over

DOC17's open gap #2 asked where the cache lives. We re-checked on 19 October 2026:

| Source | What it says | Status |
|---|---|---|
| IBM features page (re-fetched) | "Offline Cache Support" caches application metadata, object structures and configuration data; location `~/.maximo-dev-tools/cache/`; says nothing about a mirror | IBM-reported |
| Released package code | Builds `offline-mirror/` inside the workspace, with tarballs, `vendors/` and `libraries.json` | Package-reported |
| MRM-EAM walkthrough (practitioner) | Download "syncs offline development packages" and prepares dependencies | Practitioner |
| Release notes beta.3 and beta.6 | Health Check does "offline mirror checks"; beta.6 adds an "Offline Mirror Docs" button | IBM-reported |

**Our reading, flagged as inference:** these are probably two different things sharing a word. The home-folder cache looks like a *metadata cache* for working disconnected, and the workspace `offline-mirror/` is an *npm package mirror* for building. IBM's own release notes treat the mirror as a first-class concept with its own health checks, so the mirror exists and matters. We have **not** verified which directory is authoritative for any given operation, so do not write either path into a runbook as fact. Use the Health Check output to tell you what the tool is checking on your machine.

### A troubleshooting sequence that works in practice

1. Confirm you are on the latest release (beta.6 or newer) and that the Node version is 20+.
2. Open the **Health Check** panel (Command: **Maximo Dev Tools: Run Health Check**). It checks the environment, the connection, the required Graphite version and the mirror (IBM release notes for beta.3 and later).
3. Run **Maximo Dev Tools: Refresh Offline Cache**.
4. Click **Offline Mirror Docs** in Health Check if the checks fail (beta.6).
5. Look in the workspace for the mirror and confirm it is not empty:
   ```bash
   ls -la offline-mirror | head
   test -f libraries.json && echo "libraries.json present" || echo "libraries.json missing"
   ```
6. Re-run `yarn build --no-upgrade` from the workspace. The preview flow can offer this itself before it starts the server.
7. If it still fails, delete `node_modules/` only (not the mirror) and retry. If the mirror itself is missing, re-download the app.
8. Use **Get Support** in Health Check, which pre-fills a GitHub issue, and attach your OS, editor and extension versions, as IBM's own troubleshooting asks.

Check also that your corporate proxy allows the MAS host: the mirror is served by MAS, so a proxy that allows the public npm registry but blocks your MAS API host breaks the very thing the mirror needs. On Windows, issue #11 (closed) found that downloads failed without `unzip` and that a `&&` in a post-download command is unsupported in some PowerShell versions. beta.5 switched to portable commands but IBM says it is untested on Windows, so a WSL or Linux or macOS workstation is the lower-risk choice for a pilot.

<aside>

💡 **Key insight:** If `yarn build` says "Not found" for a `@maximo/` package, you do not have an npm problem. You have a mirror problem. Stop retrying `yarn install`.

</aside>

## 👀 Preview on localhost:3000

### Starting the server

Run **Maximo Dev Tools: Start Preview Server with MAS Session** from the Command Palette. It may first offer `yarn build --no-upgrade`. IBM's site describes the result as a local development server "with an authenticated MAS session and live reload, without deploying", and says the app is expected to start at `http://localhost:3000`. Only one preview server is intended to run at a time (package-reported).

In earlier research we read the mechanism: the extension runs `yarn start` as a VS Code task and injects environment variables that tell the local Graphite server how to proxy data to live Manage (package-reported):

| Variable | Purpose |
|---|---|
| `GRAPHITE_PROXY_MANAGE_URL` | Manage URL (with `/maximo`) the dev server proxies to |
| `GRAPHITE_PROXY_SECURE` | Whether to use TLS to the target |
| `GRAPHITE_PROXY_MANAGE_XACCESSTOKEN` and `GRAPHITE_PROXY_MAS_EMULATION=true` | OIDC sessions |
| `GRAPHITE_PROXY_MANAGE_MAXAUTH` | Username and password sessions |
| `GRAPHITE_PROXY_MANAGE_APIKEY` | API-key sessions |

If you ever run the proxy by hand, for example from a terminal in a CI job, the bundled MCP documentation describes a `.env` with these variables, and warns that after editing it you "MUST run `yarn clean && yarn build`" before `yarn start`. A sketch, with every value a placeholder:

```bash
# .env (never commit). API-key flavour; the Manage URL is the one that works for keys.
GRAPHITE_PROXY_MANAGE_URL=https://<instance>.manage.<domain>/maximo
GRAPHITE_PROXY_SECURE=true
GRAPHITE_PROXY_MANAGE_APIKEY=<your-key>

yarn clean && yarn build && yarn start   # then open http://localhost:3000
```

Treat that as package-reported behaviour, not a supported interface; the extension manages it for you.

### Live reload and what it means

IBM's features page says changes to XML configuration files "are reflected in your browser without manual refresh". The mechanism most likely comes from the Graphite dev server's own file watcher (UNVERIFIED mechanism), so treat reload as a convenience, not a guarantee: if you see stale output after changing a datasource or JS file, restart the server. A note from earlier releases is relevant here: beta.3 fixed "publish hanging on file watchers", so file-watcher behaviour has been a source of bugs.

### What the preview proves, and what it does not

| Proves | Does not prove |
|---|---|
| XML renders, bindings resolve, controllers run | Offline behaviour: transaction queue, preloaded database, sync |
| Datasources return live data through the proxy | `mobile-qbe-filter` and lookup-data behaviour on a disconnected device |
| `AppCustomizations.js` hooks fire (watch the console) | Device-only APIs and signature options, which are evaluated only when connected |
| Layout in a desktop browser | Layout on a phone or tablet screen |

Part 7 covers the offline model in detail. For now, remember: **the preview is a browser against live data.** Any change that touches datasources, lookup data or `mobile-qbe-filter` needs a device test after publish.

### Debugging in the preview

Append `?_graphite_logLevel=trace` to the preview URL, for example `http://localhost:3000/?_graphite_logLevel=trace#/createwo`, and use `app.log.d(TAG, ...)` in your controller. The `default-log-level` attribute on `<maximo-application>` (9.2) sets a default for preview. Part 6 is a full debugging guide.

## ✏️ The Edit Loop: A Worked Example

Using the example from Part 4, we hide the Complete button when no failure report exists. App id, page and datasource names are illustrative. Confirm yours in your own `app.xml`.

```xml
<!-- src/app.xml: disable the button using page state set by a controller -->
<button id="btn_complete" label="Complete"
        disabled="{!page.state.hasFailureReport}"
        on-click="completeWorkOrder"/>
```

```js
// src/AppCustomizations.js: set the state when the page is shown
class AppCustomizations {
  pageResumed(page) {
    if (page.name !== 'workOrderDetail') { return; }
    const ds = page.findDatasource('woDetailDS');
    const wo = ds && ds.item;
    page.state.hasFailureReport = !!(wo && wo.failurereport && wo.failurereport.length);
    page.app.log.d('TMG', 'hasFailureReport=' + page.state.hasFailureReport);
  }
}
export default AppCustomizations;
```

The loop, step by step:

1. Edit the XML and JS in the editor. Keep component `id` values unchanged and attribute names lowercase (Part 2).
2. Save. The preview reloads. Open DevTools with the log level set to `trace`.
3. If you hit a file-protection warning, read it. The next section explains why.
4. Review `git diff`. Both your changes and the `app.delta.xml` that the pipeline produces are reviewable text.
5. Commit with a message that says *what* and *why*.

```bash
git diff --stat
git add src/app.xml src/AppCustomizations.js
git commit -m "TECH-142: disable Complete until failure report present (pageResumed + app.xml)"
```

### File protection: the tier-4 guard

Part 3 explained that editing out-of-the-box controllers is unsupported and has to be merged by hand at every release. The extension adds a software guard: it **warns when you modify core application files that are not upgradeable** (IBM features page). It is implemented as a manifest-checksum check (package-reported, and beta.3 notes call it "leaner"). Settings and commands:

| Item | Value | Source |
|---|---|---|
| Setting | `maximoDevTools.fileProtection.enabled` (default true) | Package-reported |
| Setting | `maximoDevTools.fileProtection.showWarnings` (default true) | Package-reported |
| Command | Maximo Dev Tools: Check If Current File Is Protected | Package-reported |
| Command | Maximo Dev Tools: View IBM Package Manifest | Package-reported |

If the guard fires, move the logic into `AppCustomizations.js`. Do not turn it off to get past it.

## 🚀 Publishing: What Actually Happens

### The pipeline

From the released package, the publish sequence is (package-reported):

1. `yarn clean`
2. `yarn build`
3. `yarn build:production`
4. Generate diffs (deltas) for modified XML
5. Read the version and description from `app.xml`
6. `maxdev-cli package-app -a <app> -v <ver>`
7. `POST /graphite/configtool/packages/{appId}/binary?workspaceId=...&appid=...&appDesc=...&version=...&isMobile=...` with the zip and an `x-access-token` header

The result is a **new ACTIVE revision in `MAFAPPDATA`**, the same outcome as a publish from Application Configuration, UpdateDB or `maxdev-cli upload-app`. Since alpha.8 the extension also checks core-file hashes before publish.

| Pipeline stage | If it fails | Where to look |
|---|---|---|
| clean and build | Mirror problem; Node version | Health Check, terminal output |
| production build | Invalid XML, duplicate ids, JS syntax | Task output; fix and rebuild |
| deltas | Unexpected diff on core files | File-protection warnings; `git status` |
| package-app | Missing `maxdev-cli` | Mirror |
| upload | 401/403/413, TLS, wrong URL type | Error documentation service (beta.6) |

beta.6 added an **error documentation and remediation service** that classifies API, HTTP and network errors and surfaces notifications with links to documentation. That helps with the upload stage in particular.

### History of publish bugs

The repository shows that publish has been the least stable stage: issues **#9** ("Publish button does not work") and **#10** ("Publish button get stuck in Running mode" on a WOSUMMARY build) were both closed in late July and early August 2026, and beta.3 fixed "publish hanging on file watchers". Both are closed, but they are a reminder to publish only when the preview is not mid-start, which IBM's own workflow guidance also warns about.

### A publish checklist

| Before you publish | Why |
|---|---|
| Commit and tag the workspace | The Git commit is your record of what shipped |
| Note the current `MAFAPPDATA` revision | You need it to explain a rollback |
| Check the target connection name | One connection per environment, so DEV is never confused with PROD |
| Confirm Mobile? flag intent | A duplicate's "Mobile?" flag is off by default (cached IBM docs) |
| Assign security groups on first publish | Duplicates need them (cached IBM docs) |
| Confirm no preview server is starting | Avoid publishing mid-start (IBM guidance) |

After publishing, verify from the database. A read-only query like this one (column list from DOC17 and not re-verified on a live schema) shows which revision is serving devices:

```sql
SELECT APPID, VERSION, REVISION, STATUS, DEPLOYBY, DEPLOYDATETIME, ISMOBILE
FROM   MAFAPPDATA
WHERE  APPID IN ('MYTECHMOBILE')
ORDER  BY REVISION DESC;
```

Never update that table by hand. IBM does not document a revert action, and a partner SQL method is unofficial (Part 4). With this extension the practical revert is `git revert` and a republish.

### Promotion

IBM's technote ibm17045770 (June 2026, content login-gated; cited from our research base) says Migration Manager cannot migrate Maximo Mobile or Role-Based (Graphite) apps between environments. The workable pattern is to **republish the same reviewed workspace to each environment's connection**, one connection per environment, driven from Git. Duplicated apps must be duplicated in both environments first. Record the revision published to TEST and PROD next to the Git tag.

## 🔁 Git-Based Workflow and Team Hygiene

| Practice | How |
|---|---|
| One repo per app, or per series of apps | Keep `MYTECHMOBILE` separate from `MYINSPECTION` |
| Baseline tag per IBM revision | `git tag baseline-r<rev>` after downloading |
| Branch per change | `feature/TECH-142-failure-report-gate` |
| Review the delta | Include `app.delta.xml` in pull requests; it is what survives upgrades |
| Protected `main` | Publish only from `main`, only after review |
| Release notes | Put the `MAFAPPDATA` revision in each tag message |
| Upgrade branch | Run **Check for Configuration Migration**, commit the result separately from feature work |

IBM's guidance when you contact support is to attach `app.delta.xml`. A repository that tracks it makes that trivial.

### A review checklist for MAF pull requests

1. No component `id` changed (diff the XML for `id=` edits).
2. Attribute names are lowercase where they bind to server JSON.
3. No edits to IBM controller files; custom logic lives in `AppCustomizations.js`.
4. Any new object structure is granted in the target environment's security groups.
5. Object structures are not duplicated, because mobile merges by root object (Part 10 of DOC17; Part 7 of this series).
6. A device test is recorded for any datasource, lookup or QBE change.

## 📜 The Commandments of Local MAF Development

1. **Clone first, in the suite.** The extension cannot create or clone apps.
2. **Commit the pristine download before you edit.** Your baseline is your safety net.
3. **Match the URL to the sign-in.** OIDC with the MAS Home URL; API key with the Manage URL.
4. **When `yarn` says "Not found" for `@maximo/`, fix the mirror.**
5. **Only edit what IBM supports:** `app.xml` and `AppCustomizations.js`.
6. **A browser preview is not a device.** Test offline-sensitive changes on hardware.
7. **Publish from a reviewed commit, record the revision, and keep `git revert` as your rollback.**
8. **Pin the extension version and read the release notes.** It is a beta, offered AS IS.
