# Anatomy of app.xml: Pages, States, Datasources and Schemas

<aside>

🎯 **Who this is for:** Maximo developers and configurators who have opened a MAF app for the first time and are staring at a few thousand lines of XML; mobile leads who must review someone else's app.xml change; architects who need to know what is safe to touch and what will break at the next upgrade.

</aside>

**Series:** MAS MAF-DEV | **Part 2 of 9** | Previous: [Part 1 - What Is MAF?](/blog/mas-maf-dev-01-what-is-maf) | Next: Part 3 - Controllers and AppCustomizations.js

---

## 🔥 The File You Will Edit Most

In Part 1 we established that a Maximo Mobile app or Role-Based Application is declarative XML that IBM says is transformed into a ReactJS application and stored as a zip revision in `MAFAPPDATA`. This part opens the hood on that XML.

If you came from classic Maximo, the closest mental model is `presentation.xml`, but the resemblance is shallow. A classic presentation file describes tabs, sections and controls bound to MBO attributes, and the server renders it. A MAF `app.xml` describes **pages with routes**, **client-side state**, **datasources that fetch through OSLC**, and **UI components**, and a build step compiles all of it. It is closer to a front-end project than to Application Designer output.

By the end of this post you should be able to:

1. Name every file in a downloaded MAF workspace and say which ones you may edit.
2. Read an `app.xml` skeleton top to bottom: properties, menu, datasources, pages, states, components, dialogs, messages.
3. Choose between the three datasource types and write a schema that matches an object structure.
4. Use bindings, state, routing and signature-option gating correctly.
5. Apply the three rules that cause most MAF upgrade pain: never change ids, keep names lowercase, declare in order.
6. Recognise the places where IBM's own documentation disagrees with itself, so you stop trusting the wrong sample.

A word on sourcing. We tag vendor claims **IBM-reported**: they come from IBM Documentation, IBM support pages, IBM PDFs, or IBM-authored sites such as the *MAF Configuration Practices* guide, and we have not independently audited them. IBM does not publish a public, attribute-by-attribute component reference for MAF; the full property tables sit in the in-product Developer Documentation inside Application Configuration. So this post teaches structure and rules that IBM's public material supports, and tells you where to go in the product for the exhaustive tables.

<aside>

⚠️ **Tooling status, stated once.** Everything here applies to any of the three tooling generations (Docker `maf-tools`, in-suite Application Configuration, Local Configuration) because the file format and the resulting `MAFAPPDATA` revision are the same. But the newest tool, **MAF Local Configuration**, is an **early-access preview**, offered **AS IS**, **IBM proprietary software** that requires a valid MAS license, and IBM describes it as not for production use. It cannot create or clone applications. Treat it as a developer convenience on non-production environments.

</aside>

## 📂 The Workspace: What You Actually Download

When you download an app with any of the three tools, you get a project folder. IBM-reported layout, using the Technician app as the example:

```
TECHMOBILE/
  src/
    app.xml                 <- the main application XML
    wo-card-group.xml       <- included XML (pulled in with <include src="...">)
    AppCustomizations.js    <- the supported JavaScript customization point
    i18n/labels.json        <- default (English) labels
    app.delta.xml           <- auto-generated delta of your XML changes (8.11+)
  build/ ...                <- build output (build/app is what gets packaged)
  ibm-config/  (8.11)  or  TECHMOBILE_backup/  (8.10 and below)
                            <- IBM's unmodified originals
```

| Path | Edit it? | Why it matters |
|---|---|---|
| `src/app.xml` | Yes, this is the supported XML seam | The tree this entire post is about |
| `src/*.xml` (included files) | Yes | Large apps are split with `<include src="./wo-card-group.xml" id="jwq72"/>`; the include itself carries an id |
| `src/AppCustomizations.js` | Yes | The upgrade-safe app-wide controller, covered in Part 3 |
| `src/i18n/labels.json` | Yes | Default English labels; other languages are separate files |
| `src/app.delta.xml` | No, it is generated | Your changes expressed as add/remove/modify/move operations against component ids |
| `ibm-config/` or `*_backup/` | No | The pristine original IBM uses as the baseline for deltas |
| `build/` | No | Output only; regenerated on every preview or publish |

Two practical consequences follow. First, **commit `src/` and ignore `build/`** if you keep the workspace in Git (Part 5 shows the full workflow). Second, the original-versus-configured pair is what makes upgrades tractable. The delta is computed by comparing what IBM shipped with what you changed, which is exactly why the id rule in a later section is non-negotiable.

To confirm the app IDs available on your own system before you download anything, use the same two checks from Part 1:

```sql
SELECT APPID, VERSION, REVISION, STATUS, ISMOBILE, DEPLOYBY, DEPLOYDATETIME
FROM MAFAPPDATA
ORDER BY APPID, REVISION DESC;
```

or `GET /graphite/configtool/packages`. IBM's FAQ on the practices site publishes a similar `MAFAPPDATA` query and adds that the revision number doubles as an indicator that an installed app carries configuration.

## 🧱 The app.xml Skeleton

Here is the skeleton, reconstructed from IBM's 8.4 customization PDF section titled "Anatomy of an application XML file" and the examples on the Configuration Practices site. Attribute values are illustrative:

```xml
<maximo-application id="techmobile" title="Technician" version="9.2.x">
  <properties> ... </properties>
  <menu> ... </menu>                         <!-- left-side navigation -->
  <maximo-datasource id="..."/>              <!-- app-global datasources -->
  <pages>
    <page id="workOrderDetail" path="workorders/:wonum"
          controller="WorkOrderDetailController">
      <states>
        <state name="isLoading" value="false" type="boolean" id="state_001"/>
      </states>
      <maximo-datasource id="woDetailDS" object-structure="MXAPIWODETAIL"> ... </maximo-datasource>
      <header-template> ... </header-template>
      <stacked-panel> ... </stacked-panel>
      <dialogs> ... </dialogs>
    </page>
  </pages>
  <messages> ... </messages>
</maximo-application>
```

Read it like a table of contents:

| Element | Role | Notes |
|---|---|---|
| `maximo-application` | Root | Carries the app id, title, version. From 9.2, IBM added a `default-log-level` attribute here (IBM-reported, cached 9.2 what's-new; we could not re-verify it live) |
| `properties` | App-level properties | Feature switches and defaults |
| `menu` | Navigation | The left-side menu entries |
| top-level `maximo-datasource` | App-global data | Visible to every page; good for reference data used everywhere |
| `pages` / `page` | Routable screens | Each page has an `id`, usually a `path`, optionally a `controller` |
| `states` / `state` | Reactive values | Page-scoped here; app-scoped state also exists |
| page-level `maximo-datasource` | Data owned by one page | Created and released with that page |
| layout and display components | The UI | `header-template`, `stacked-panel`, `box`, `border-layout`, `table`, `field` and so on |
| `dialogs` | Modals and lookups | `dialog`, `lookup`, `sliding-drawer` live here |
| `messages` | Localizable message definitions | Referenced from code and bindings |

IBM's practices site describes the page as the unit of structure: a page has a unique route within the application, owns states, datasources, a controller and dialogs, and is the place where lifecycle hooks (`pageInitialized`, `pageResumed`, `pagePaused`) fire. We treat lifecycle in Part 3; here we stay on the XML.

### Includes: keeping a 20,000-line file reviewable

Large apps are split with the include element:

```xml
<include src="./wo-card-group.xml" id="jwq72"/>
```

Two details matter. The include has its **own id**, which falls under the same never-change rule. And from 9.2, IBM states that delta files are generated at publish for **all** XML files, not only `app.xml`, so an included file's changes are tracked too (IBM-reported). When you add your own include for a new section, give it a descriptive id; when you touch an IBM include, leave the id alone.

## 🗺️ Pages and Routes

A page is declared with an `id` and, for navigable pages, a `path`:

```xml
<page id="workOrderDetail" path="workorders/:wonum">
```

IBM's practices site states that the path defines the route and that dynamic segments such as `:wonum` are read at runtime from `page.params`. That is how a list page hands a record to a detail page without global state: the list navigates to `workorders/1234`, the detail page's controller reads `page.params.wonum`, and a datasource on the detail page uses it to load the right record.

**Controllers** attach in one of two ways on the same page:

```xml
<page id="workOrderDetail" controller="WorkOrderDetailController">

<page id="workOrderDetail">
  <controller src="WorkOrderDetailController.js"/>
  <controller src="ValidationController.js"/>
</page>
```

The attribute form takes a single controller; the child-element form attaches several. When several controllers define the same method, Part 3 explains why you must not assume an order.

**Navigation order** matters when you reason about where to load data. IBM states that moving between pages runs `pagePaused` on the old page, then `pageInitialized` on the new page (first visit only), then `pageResumed`, and then datasource dynamic properties are processed. Two lifecycle details from the same page are worth carrying forward now: `pageInitialized` fires once, before render, so do not load datasources there; `pageResumed` fires on every activation but before datasources load, so do not assume data is present.

## 🔁 States and Bindings

### Declaring state

State is reactive: change a value and every binding that reads it updates. There are two scopes:

| Scope | Declared | Read in XML | Read in controllers |
|---|---|---|---|
| Page state | Inside a page's `<states>` | `{page.state.selectedTab}` | `this.page.state.selectedTab` |
| Application state | Application level | `{app.state.networkConnected}` | `this.app.state.networkConnected` |

IBM's examples show built-in app state such as `app.state.networkConnected` and `app.state.screen.size`, which is how an app switches layout for a phone versus a tablet or hides a button when offline.

**Here is the first IBM inconsistency to know about.** IBM-authored material declares states in two different shapes:

```xml
<!-- shape A (8.4-era material and several examples) -->
<state name="isLoading" value="false" type="boolean" id="state_001"/>

<!-- shape B (current Configuration Practices page) -->
<state id="selectedTab" value="details"/>
```

We found no IBM statement that reconciles them. Our rule: **copy the form already present in the app.xml you downloaded from your own environment**, since that is the form your MAS version's build accepts. Do not paste shape A or B from a blog, including this one, into an app that uses the other.

### Bindings are JavaScript expressions

Curly braces evaluate expressions against datasources, state and the reserved name `item`:

```xml
<button id="btn_complete" label="Complete"
        hidden="{item.status === 'COMP'}"
        disabled="{!page.state.isValid}"/>
<field label="Work order" value="{item.wonum}"/>
<text value="{woDetailDS.item.description}"/>
```

IBM's practices page lists three binding forms: datasource bindings, state bindings and conditional bindings. Input components use two-way binding, so a user edit writes back to the bound item. `item` is the reserved name for the current record of the datasource in scope; `dsname.item.field` reaches a specific datasource when several are in scope.

A binding is an expression, not a statement. That is powerful and slightly dangerous: a typo evaluates to `undefined` and the field silently renders empty. Part 6 of this series (debugging) covers the console and `?_graphite_logLevel=` for exactly this class of problem.

## 🗄️ Datasources: The Part That Decides Whether Your App Works

Datasources are where MAF meets Maximo. IBM's *Data Sources Guide* documents three types:

| Type | IBM description | Typical use | Schema |
|---|---|---|---|
| `maximo-datasource` | "Connects directly to Maximo OSLC APIs for server-side data" | Any Maximo record through an object structure | Required |
| `json-datasource` | "Client-side, in-memory data source for non-Maximo data" | Static options, computed lists, data from a JS loader | Optional |
| `custom-datasource` | "Fully custom data adapter for specialized requirements" (IBM adds that it is "rarely needed") | Exotic adapters | Depends |

```xml
<json-datasource id="itemsDS" src="loader.js" pre-load="true"/>

<maximo-datasource id="workOrderDS" object-structure="MXAPIWODETAIL"
                   where="status='WAPPR'" order-by="wonum desc">
  <schema> ... </schema>
</maximo-datasource>
```

### Properties you will actually use

IBM's practices pages show no formal property reference, so the list below is the union of properties that appear in IBM's own examples. Treat it as "known to exist", not "exhaustive":

| Property | Applies to | What it does |
|---|---|---|
| `id` | all | Referenced by bindings, controllers, `findDatasource()` |
| `object-structure` | maximo | The OSLC object structure, for example `MXAPIWODETAIL` |
| `saved-query` | maximo | A Maximo saved query, for example `ASSIGNEDWORK`, `PMWOLIST` |
| `where` | maximo | Server-side filter, appended to the saved query; supports keywords such as `SYSDAY` |
| `order-by` | maximo | Sort, for example `wonum desc` |
| `page-size`, `download-page-size` | maximo | Fetch sizes for online and offline download |
| `pre-load` | json, maximo | Load at startup rather than on demand |
| `can-load` | all | Expression that gates loading, for example `{app.state.userAuthenticated}` |
| `depends-on` | all | Controls load order between datasources |
| `selection-mode` | maximo | Single or multiple selection in lists and lookups |
| `lookup-data` | maximo | Marks data used by lookups |
| `controller` | all | A controller bound to this datasource |
| `relationship`, `notify-when-parent-loads` | child datasources | Child records tied to a parent |
| `include-counts` | maximo | Request record counts |
| `offline-immediate-download` | maximo | Download immediately for offline use |
| `mobile-qbe-filter` | maximo | Client-side filter on already-downloaded data (device only) |
| `src` | json | The loader file |

### Where versus mobile-qbe-filter: the offline trap

This distinction causes more "works in the browser, wrong on the phone" defects than anything else in MAF datasources, so we spell it out.

| | `where` | `mobile-qbe-filter` |
|---|---|---|
| Evaluated | Server-side, against all Maximo data | Client-side, against the local downloaded database |
| Server keywords (`SYSDAY`, `&PERSONID&`) | Supported | Not resolvable offline; use concrete values, often from app state |
| Nested properties | Per OSLC rules | Top-level properties only; use an alias for nested values |
| Case | Per Maximo | Case-sensitive |

IBM's practices page puts it plainly: mobile QBE filters "only work on data already downloaded to the device" and "filter the local database, not the server." Its offline-safe pattern builds the filter from state instead of a keyword:

```xml
<!-- fails offline: SYSDAY cannot be resolved against the local database -->
mobile-qbe-filter="{{'schedstart': '<=SYSDAY'}}"

<!-- offline-safe: concrete value from app state -->
mobile-qbe-filter="{{'schedstart': '<='+app.state.currentDate}}"
```

The practitioner write-up from BPD Zenith reaches the same conclusion from the field: a datasource `where` is only applied when the app runs as a Role-Based Application, not on a device, so a filter you need offline belongs in `mobile-qbe-filter`. And a community thread comparing the mobile web app with the native app on the same object structure `where` clause reported different row counts for the same reason; an IBM Champion's suggested fix was adding `mobile-qbe-filter`.

A datasource can carry both attributes. IBM's PM-work-order example uses a server `where` for the date window and a `mobile-qbe-filter` for status, together with `offline-immediate-download`:

```xml
<maximo-datasource-override id="pmduewolistDS"
    saved-query="PMWOLIST"
    where="schedfinish>=&quot;&amp;SYSDAY&amp;&quot; and schedfinish<=&quot;&amp;SYSDAY&amp;+7D&quot;"
    mobile-qbe-filter="{{'status_maxvalue': '!=COMP,CAN,CLOSE,WAPPR'}}"
    offline-immediate-download="true"/>
```

(Reproduced from IBM's "Change or replace apps' saved queries" example, reformatted onto several lines; the original is a single self-closing element.)

### Saved query, where clause, or both

IBM's guidance on that same page is worth quoting in spirit. Changing the Query Definition of a saved query in Maximo changes the data for every application and client API that uses it; IBM's own warning is that it "will change the work type data that is made available to the Technician application." The `where` attribute **appends** to the saved query, so extending is safer than editing:

| Approach | Blast radius | Republish needed | Use when |
|---|---|---|---|
| Edit the saved query in Maximo | Every consumer of the query | No | The new filter is correct for every app |
| `saved-query` plus app-level `where` | This app only | Yes | The restriction is specific to your app |
| New saved query, referenced by `saved-query` | Only apps that reference it | Yes | Several of your own apps share the filter |
| `mobile-qbe-filter` only | This app, device only | Yes | Narrowing downloaded data on the device |

A community discussion from the Maximo Mobile 8.7 days adds the administrator's perspective: saved queries let you adjust filtering in Maximo without touching the app, while an inline `where` is the fallback when no saved query fits. We agree, with one amendment from the table: when the query is shared with a classic UI or an integration, make the change in the app, not in the query.

### maximo-datasource-override

`maximo-datasource-override` lets you reuse or extend an existing datasource, for example to swap its saved query as above. The rule from IBM-authored material: **never override `object-structure`.** If you need a different object structure, declare a new datasource.

### Do not duplicate object structures

Mobile merges data from object structures that share a root object. IBM's *Mobile Master Schema* page is explicit that the merge is "object-based, not datasource-id-based": `MXAPIWODETAIL` resolves to `WORKORDER`, entries resolving to the same object are combined, and their `select` lists are unioned. Only **active** mobile apps contribute. The IBM FAQ says plainly that duplicating object structures is discouraged: reuse the same object structure across apps and apply logic in the app to show only what is needed.

The performance corollary matters on a device. Each field you add to a schema widens the shared select, which means bigger payloads, more offline storage and more metadata to process. IBM's advice for administrators is to trim unused `select` fields, remove unused datasources, cut unnecessary child relationships, and deactivate mobile apps nobody uses.

## 📐 Schemas: Telling the Datasource What to Fetch

A `maximo-datasource` needs a `<schema>` listing the attributes to fetch from the object structure. A small, real-shaped example:

```xml
<maximo-datasource id="woListDS" object-structure="MXAPIWODETAIL" saved-query="ASSIGNEDWORK">
  <schema>
    <attribute name="wonum" searchable="true" id="attr_001"/>
    <attribute name="description" searchable="true" id="attr_002"/>
    <attribute name="status" id="attr_003"/>
    <attribute name="asset.description--assetdesc" searchable="true" id="attr_004"/>
  </schema>
</maximo-datasource>
```

Attribute properties documented across IBM's sources:

| Property | Meaning |
|---|---|
| `name` | The object attribute, relationship path, or alias |
| `type` | For example `STRING`, `INTEGER`, `DECIMAL`; IBM's practices examples show `<attribute name="price" type="DECIMAL"/>` |
| `required` | Marks the field required (the practices site has a dedicated example for marking fields required) |
| `searchable` | Include in search |
| `default-value` | Initial value for new records |
| `unique-id` | Marks the unique identifier |
| `sort` | Controls availability in the sort list (see IBM FAQ below) |
| `id` | Component id; IBM's practices page describes it for attributes as a required unique identifier |

### Aliases and relationship attributes

Practitioner techniques documented by Maycon Belfort on MoreMaximo (April 2025) are consistent with IBM's FAQ examples:

- **`name--alias`** fetches a related or nested field under a flat alias. IBM's own FAQ example is `location.description--locationdesc`, and it is the standard answer to "nested properties do not work in the mobile QBE filter".
- **`rel.x{a,b}`** pulls an attribute set from a relationship.
- Overriding the `MOBILEDOMAIN` query in place can be better than creating a new saved query.

The IBM FAQ also notes how to make a schema attribute available in the sort list: set its `sort` property to `true`, or remove the property, per the FAQ's wording and its example `<attribute name="location.description--locationdesc" searchable="true" id="d_m_3"/>`. We have not independently tested which of the two phrasings is canonical on each MAS version; verify in your preview.

### The schema is the contract with the device

On a device, the schema does double duty. Each app's datasource schemas are inputs that Maximo merges into the **mobile master schema** used for offline download; IBM says the app's own `mobileDisconnectedSchema.json` is one of the inputs to that merged result. If an attribute is missing from the schema, it is not downloaded, and a binding to it renders empty. That is the second most common "works online, blank offline" cause after the `where` trap above.

### A worked example: add a field end to end

Requirement: show the asset description on the work order list card.

1. In the list datasource schema, add the alias attribute (so the device downloads it):

```xml
<attribute name="asset.description--assetdesc" searchable="true" id="attr_asset_desc"/>
```

2. In the card component, bind the alias:

```xml
<text value="{item.assetdesc}" id="txt_asset_desc"/>
```

3. Preview, then publish, then **test on a device** (Part 6 explains why browser preview is not enough). The alias is lowercase by design; see the next section.

Notice what we did not do: no new object structure, no new saved query, and the new ids are descriptive because they are ours.

## 🚨 Three Rules That Bite

These are the rules our research base repeats from IBM-reported material because breaking them is how teams lose a day, or a release.

### Rule 1: Never change an existing `id`

Component ids are generated by the build and are what delta files use to identify your changes. In IBM's delta format a change is an operation against an id:

```xml
<updatescript version="">
  <app apptype="maf" id="TECHMOBILE">
    <add before="xd5k8" container="w224k" control="attribute">
      <set property="id" value="jvggb"/><set property="name" value="risk"/>
    </add>
  </app>
</updatescript>
```

(Illustrative: the `risk` attribute and ids are an invented example in the shape IBM's 8.11 delta documentation uses, not an IBM sample.)

The `before` and `container` values are component ids. Rename an id in `app.xml` and the next `apply` cannot locate the component. IBM's apply output logs ADD, REMOVE, MODIFY and MOVE lines and warnings such as `Cannot MOVE control ... NOT_FOUND_ERR`, which usually means the target component was deprecated or its id changed; you then re-implement the change on the replacement. XML comments are not preserved by the apply step, so do not rely on comments to document intent.

IBM's FAQ for post-upgrade troubleshooting gives the practical check: verify that ID references still exist, especially states and datasources declared in XML, then review `app.delta.xml`, then retest `AppCustomizations.js`.

One apparent tension, reconciled: IBM's practices guidance says to use descriptive ids for elements. That applies to ids **you** create (`pmduewolistDS`, `btn_complete`). The prohibition applies to ids **IBM's build generated** (`xd5k8`, `jwq72`). Our convention is to prefix every id we add with a short team tag so a reviewer can tell ours from IBM's in a diff.

### Rule 2: Attribute names are lowercase

Maximo returns JSON keys in lowercase, so bindings and schema names must match: `item.somename`, never `item.someName`. This rule is carried in our research from IBM's 8.4 customization material; IBM's current *Data Sources Guide* does not restate it, though every example on it uses lowercase. That is a good reminder that rules live in different documents: treat the older PDF as still binding. The symptom of a violation is silent: the field renders empty, no error is raised.

### Rule 3: Declaration order matters

Declare datasources **before** the lookups and components that use them. IBM-reported (from the Configuration Practices overview material) and consistent with the `depends-on` property, which exists specifically to control load order between datasources:

```xml
<json-datasource id="departments" src="departments.js" pre-load="true"/>
<json-datasource id="employees" depends-on="departments" src="employees.js"/>
```

On a related note, IBM's *Data Sources Guide* recommends `smart-input` for editable forms because it infers the input type from the schema, and advises against creating controllers unless you need custom logic. Fewer controllers means less to merge on upgrade.

## 🔐 Gating Components: Security and License in XML

### Signature options

You can gate a component on a Maximo signature option:

```xml
<button id="btn_read_only_action" label="Review" sigoption="workview.read"/>
```

and, in code, `app.checkSigOption('<os>.WO_DELETEERROR_TRX')`. IBM-reported caveat that catches teams: **signature options are valid only in connected mode.** An offline device cannot evaluate them against the server, so do not rely on `sigoption` as the only guard for an action that must be restricted offline.

### License gating

`license="tpaebase"` on a component restricts it to a licensed product. IBM-reported; we have seen it in examples, not in a reference table.

### Data security still lives in Maximo

XML gating hides UI; it does not secure data. If a user lacks READ on the object structure behind a datasource, the app fails with an error of the form "The action READ is not allowed on object ...". IBM's *Common Issues* page gives the fix: find the failing call in the browser Network tab, open **Security Groups**, select the user's group, go to the **Object Structures** tab, grant READ to the structure named in the response, then have the user sign out and in. Our rule: **every new object structure you add to a datasource gets a security review the same day**, because the app compiles and previews fine for an administrator and fails for the first real user.

## 🧪 Sharing Data Across Apps (9.2)

One datasource feature deserves a mention because it changes how you think about duplication. IBM's practices site documents cross-app datasource sharing, introduced in **MAS 9.2.0**: a consumer app's `maximo-datasource` declares where to borrow downloaded data from:

```xml
<maximo-datasource id="inspectionAssetDS" object-structure="MXAPIASSET" offline-enabled="true">
  <mobile-shared-data-from app-id="techmobile" datasource-id="assetDS"/>
</maximo-datasource>
```

Several `mobile-shared-data-from` elements form a fallback chain, checked in order. IBM lists caveats worth a design review:

| Caveat | Consequence |
|---|---|
| Consumer schema must be a subset of the source schema | Missing attributes come back null with no error and empty UI fields |
| Same `object-structure` on both sides | A mismatch is an error |
| No circular links | "Recursive linking detected" |
| `offline-enabled` required | Omitting it is a listed mistake |
| Automatic fallback if the source app is missing | The consumer downloads its own data, silently, so the fallback can go unnoticed |

It is a good fit when two of your cloned apps would otherwise download the same asset set twice. It is a poor fit when you cannot control the source app's schema, because the source can change under you on an upgrade.

## 🧭 Reading Someone Else's app.xml: A Review Checklist

Use this when reviewing a change request or an inherited customization:

| Question | Where to look | Red flag |
|---|---|---|
| Which ids changed? | `git diff` on `src/`, then compare to `app.delta.xml` | An id on a line IBM generated |
| Are new ids descriptive and tagged? | Added elements | Generic `id="1"` or random strings |
| Is every new datasource declared before use? | Document order | A lookup above its datasource |
| Does each `maximo-datasource` have a schema? | `<schema>` child | Binding to fields not in the schema |
| Are all schema names lowercase? | Attributes | `someName` |
| Where vs mobile-qbe-filter | Datasource attributes | A `SYSDAY` in `mobile-qbe-filter` |
| New object structure? | `object-structure=` | No matching security group grant |
| Duplicated structure? | Compare with existing | A clone of `MXAPIWODETAIL` |
| Deprecated components? | Component names | `container`, `page-header`, `chat-log` |
| Sigoption on an offline-critical action? | `sigoption=` | Used as the only guard |
| Declared state shape consistent? | `<state` | Mixed name/id forms |

## 🛠️ Troubleshooting Table

| Symptom | Likely cause | First check |
|---|---|---|
| Field renders blank, no error | Uppercase or wrong attribute name, or missing from schema | Lowercase name; schema entry |
| Works in browser, wrong rows on device | `where` applied online only, or `mobile-qbe-filter` absent | Add `mobile-qbe-filter` with state-based value |
| "Action READ is not allowed on object ..." | No object structure authorization | Security Groups, Object Structures tab |
| Publish hangs after save | Invalid app.xml saved silently (IBM-tracked DT503372) | Validate XML; check the build log |
| Lookup shows no data | Datasource declared after the lookup | Move the datasource earlier or use `depends-on` |
| Delta apply warns `NOT_FOUND_ERR` | Edited id, or deprecated target | Restore the id; re-implement on the replacement |
| Preview works, device does not update | `ISMOBILE` off for a duplicated app | `SELECT APPID, ISMOBILE FROM MAFAPPDATA` |

The DT503372 and ISMOBILE items come from IBM-reported defect and storage notes in our research base; the duplicate app's "Mobile?" flag defaults to off, per IBM.

## ✅ Key Takeaways

- A downloaded MAF app is a small project; edit `app.xml`, included XML, `AppCustomizations.js` and labels, and leave `app.delta.xml`, the IBM originals and `build/` alone.
- `app.xml` is a tree of pages, states, datasources, components and dialogs; pages are routes with their own state and data.
- Three datasource types exist; `maximo-datasource` requires a schema of the attributes to fetch.
- `where` is server-side and `mobile-qbe-filter` is device-side; offline filters need concrete values.
- Never edit generated ids, keep names lowercase, declare datasources first, and do not duplicate object structures.
- IBM's documentation contradicts itself on state declaration and on deprecated components in examples; copy from your own downloaded app.
