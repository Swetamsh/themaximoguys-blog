# Every Maximo Mobile and Role-Based App in MAS 9.2: The Complete Catalog

> 🎯 **Who this is for:** Maximo administrators, solution architects and mobility leads who keep getting asked "is there a mobile app for that?" and want one trustworthy table to answer it. If you are a MAF developer, this is the inventory that sits in front of the [MAS-MAF-DEV series](/blog/mas-maf-dev-00-series-index).

*Part 1 of 3 in the MAS Mobile series. This is a three-part mini-series with no separate index post; the parts link to each other at the bottom.*

## 🔥 The Question Nobody Can Answer from One Page

"Does Maximo have a mobile app for approvals?" "Is there an inventory counting app?" "Which of these can I build on in Application Configuration, and which are still Application Designer?" Every one of those is a five-minute question that takes an hour, because the answer is scattered across product pages, what's-new pages for three releases, security-group tables and community threads.

We went looking for the single authoritative list. It does not exist. What exists is:

- IBM's statement that Application Configuration "supports IBM Maximo Mobile, IBM Maximo Health, and IBM Maximo Manage," and that you can "also configure non-mobile, role-based applications."
- A what's-new page per release that names apps when they arrive (Material Request in 9.2, Timesheets in 9.2, Incident Reporter in 9.1) but never gives their IDs.
- Documentation examples that use app IDs in passing (`TECHMOBILE` in the upgrade and workspace instructions, `ITMOBILE` in the OSLCMAFAPPDATA security table).
- Community logs and threads that reveal the rest by accident.

This post stitches those into one catalog, and it does something most catalogs skip: **every row carries a confidence label**. A table you cannot trust is worse than no table, so where we could not confirm an ID, we say "ID unknown" instead of guessing one that looks plausible.

<aside>

💡 **Key insight:** In MAS, "the mobile app" is two things. One is a **native shell** you install from a store. The other is a set of **server-published apps** the shell downloads. Almost every question in this post comes down to which of the two you are asking about.

</aside>

## 🧱 First Principles: Shell, Graphite Apps and MAFAPPDATA

Before the catalog, the three terms that every row depends on.

**The shell.** IBM's architecture page describes the Maximo Mobile App as the shell "across various environments (iOS, Android, and Windows)," and says it "does not carry any functionality beyond downloading and executing functional modules." You install it from the Apple App Store or Google Play once Manage is deployed and activated. It owns the things only native code can do: the offline database, the transaction queue, camera and barcode access, push notifications, biometrics and (new in 9.2) Bluetooth Low Energy connectivity.

**Graphite apps.** The functional modules are built with the Maximo Application Framework. MAF is Graphite internally, and you will see that name in dev tool paths, REST paths (`/graphite/configtool/packages`) and IBM guide titles. For blog purposes, **MAF equals Graphite**. Developers describe apps as declarative XML (`app.xml` plus included files) with a little JavaScript, and a build step turns them into React applications.

**MAFAPPDATA.** The built apps are stored "as zip files in the MAFAPPDATA database table, within a BLOB column." The shell "downloads these Graphite Applications when users first connect to the Maximo server" and "updates the files into the shell whenever a new version of the Graphite Application is available." IBM also notes that "not all Graphite Applications are available to every user," because delivery follows authorisation.

> ⚠️ **Not a PWA.** We keep seeing Maximo Mobile described as a progressive web app. It is not. It is a native store application that runs server-published web-technology modules inside its own container. The distinction matters for your MDM policy (you deploy a store app), for offline behaviour (native database, not browser storage) and for patching (shell updates go through the store; app updates go through a MAFAPPDATA publish).

| Layer | What it is | Where it lives | How it updates |
|---|---|---|---|
| Shell | Native iOS, Android and Windows app | App Store, Google Play, enterprise distribution | Store release or MDM push |
| Graphite app | MAF app compiled to React | `MAFAPPDATA` BLOB on the Manage server | New ACTIVE revision published, shell pulls it |
| Browser RBA | The same MAF code served online | Manage / MAS web UI | New revision, next page load |
| Classic app | Application Designer `presentation.xml` screens | Manage database (`MAXPRESENTATION`) | Application Designer or migration packages |

## 🗂️ The Delivery Key: Hybrid, Browser, Mobile

Every row in the catalog gets one of three delivery labels.

- **Hybrid:** an offline-capable Maximo Mobile app and an online browser role-based app (RBA) built from the same code.
- **Browser:** a role-based application only, opened in the web UI.
- **Mobile:** device only. It exists inside the shell and has no browser twin.

And one confidence label.

- **verified:** named in IBM documentation or an IBM what's-new page, or appears in an IBM-authored artefact such as a security table or workspace example.
- **likely:** consistent evidence from practitioner sources or a code inspection, but not stated by IBM.
- **[UNVERIFIED]:** reported or inferred; do not build a design on it without checking your own system.

Two more conventions. "Since" is the earliest version we could tie to the app; a tilde means the version is probable rather than documented. And every app listed here can be configured in Application Configuration, and for most you can duplicate it before changing it (`TECHMOBILE` to `MYTECHMOBILE`). MVI Mobile is the one exception, covered after the table.

### The one app that is explicitly not MAF

**Maximo Visual Inspection Mobile (MVI Mobile)** is a native iOS and iPadOS application. It is not built on MAF, is not published through MAFAPPDATA, and cannot be duplicated and configured in Application Configuration. It shows up in this conversation because the Inspections app can call MVI models: in 9.1 you can configure inspection questions to "automatically analyze images using MVI models" by selecting *Always perform MVI analysis* and specifying the model. That is MAF calling out to MVI, not MVI being a MAF app.

## 🚫 IDs That Look Like Apps but Are Not

This is where catalogs built from log files go wrong. Several strings circulate in forums and spreadsheets that are not applications at all.

| String | What it actually is | Where you see it |
|---|---|---|
| `IROPENPOMOBILE` | A **saved query** used by IRMOBILE to show purchase orders available to receive | Saved Query lists, receiving screens |
| `IROPENSHIPMOBILE` | A **saved query** used by IRMOBILE for shipments available to receive | Same |
| `ISMOBILE` | A **MAFAPPDATA column**, not an app | Database schema listings |
| `CXITMOBILE` | A customer's **duplicate of ITMOBILE**, seen in a community log; not an IBM app | Community error logs |
| `TPAEMOBILE` | **Not found** in any source we searched | Occasional forum mention |
| Calibration, Linear, Spatial maps, ACM asset swap | **Capabilities inside** TECHMOBILE and ASSETMOBILE, not separate apps | What's-new pages, which headline them like apps |

The calibration and linear point trips up scoping. A customer reads "Calibration for Maximo Mobile" in a what's-new page and asks for the Calibration app. There is none. The behaviour appears inside the Technician app when the work type's WORKTYPE synonym domain maximum value is `CAL`, or when a datasheet is attached. IBM's 9.2 page spells out exactly when the calibration icon appears, and it is a data condition, not a separate install.

The same logic applies to **Quick Reporting** (emergency work order creation, 9.0) and **Maximo Spatial** tools (Layers, Identify, Query, Results, Sketch, Edit, Show Related). They are features that surface inside other apps, which is why scoping a rollout by "app" without reading the release notes will over- or under-count.

## 🏛️ What Is Still Classic Application Designer

The flip side of the catalog matters just as much, because the question you will actually get is "can we make *this* mobile?" and for a large part of Maximo the honest answer today is "not as a supported MAF app."

| Area | Classic apps (Application Designer UI) |
|---|---|
| Purchasing (no procurement RBA found, no roadmap item found) | PR, PO, RFQ, Invoices, classic Receiving, Companies, Contracts |
| Inventory masters | Item Master, Inventory, Storerooms, Inventory Usage, Count Books |
| Planning | Job Plans, PMs, Routes, Safety / LOTO |
| Core records | Work Order Tracking, Assets, Locations, Meters, Failure Codes, Classifications |
| Platform | Application Designer, Database Configuration, Workflow Designer, Escalations, Automation Scripts, Cron Tasks, integration apps, Security Groups (Manage) |
| Service management | Service Desk, Desktop Requisitions |
| Industry solutions | Aviation, Nuclear, Transportation, Utilities, Civil. The only industry MAF apps we found are the HSE and Oil & Gas Incident Reporter and Permit to Work |
| Scheduler boards | Graphical Scheduling Gantt boards |

Two clarifications keep this table from being misread.

**Some of these have a MAF "front" for field tasks.** Work Order Tracking is classic, but technicians execute work orders in TECHMOBILE. Locations is classic, but there is a Locations app on MAF from 9.2. Inventory masters are classic, but counts, receipts and issues have MAF apps. The classic app stays the system of record for configuration; the MAF app is the persona-focused front.

**Two worlds, two configuration tools.** IBM is explicit that "any configuration changes made to applications based on the previous Maximo Asset Management framework cannot be migrated to Maximo Application Framework applications." Application Designer edits `presentation.xml`; Application Configuration edits `app.xml`. They do not share artefacts. If your 7.6 estate has heavily customised Work Centers, those customisations are not carried into the RBAs, and the same is true of Maximo Anywhere configuration moving to Maximo Mobile.

| Old | Replaced by | Migration note |
|---|---|---|
| Maximo Anywhere (Worklight / MobileFirst plus Dojo) | Maximo Mobile on MAF | No migration path; re-implement the configuration |
| Work Centers (deprecated 8.9, removed in 9.x) | Role-based apps on MAF | Customisations do not carry over |
| Inspection Forms Work Center | Inspection Forms RBA (Manage 9.0) | Rebuilt on MAF with the same functionality, per IBM |
| MMI Work Center | Manage Monitoring Information (`MMIUI`) | Rebuilt on MAF |

### Direction of travel

- IBM has said that "Maximo WorkCenters are now fully deprecated."
- In 9.2 the "Role Based Applications" submenu was removed and mobile apps are now labelled "(Mobile)."
- IBM slide decks mention cross-MAS dashboards, expanded mobile assignments and auditing (mobile assignments and auditing arrived in 9.1) and industry-solution mobility. Those decks are not commitments.

Our rule of thumb, which has survived every release since 8.9: **MAF owns field execution, approvals, inventory floor work and admin consoles. Classic still owns back-office transactions and configuration.** If you are planning around a gap, plan around the classic UI being there for the foreseeable future.

## 🔬 How to Confirm the List on Your Own System

Everything above is a snapshot of what we could assemble from documents. Your system is the source of truth. There are three ways to read it, from lowest to highest effort.

### 1. Query MAFAPPDATA

MAFAPPDATA holds one row per published revision of each app, so a plain select returns duplicates. Group it.

```sql
-- Which MAF apps exist on this Manage database, and how many revisions each has?
SELECT appid,
       COUNT(*)            AS revisions,
       MAX(version)        AS latest_version
FROM   mafappdata
GROUP  BY appid
ORDER  BY appid;
```

If you have a column that flags the active revision, filter on it. We have seen `ISMOBILE` described as a MAFAPPDATA column, which is why it shows up in schema dumps and is sometimes mistaken for an app.

### 2. Call the configtool packages endpoint

This is the same backend that Application Configuration uses. The category parameter takes the five package categories IBM's tooling supports.

```bash
# From a session with a valid token or API key on the API host
curl -s -H "x-access-token: $TOKEN" \
  "https://api.${MAS_DOMAIN}/graphite/configtool/packages?workspaceId=${WORKSPACE}&appIds=manage,core,addons,assist,monitor"
```

The five categories are `manage`, `core`, `addons`, `assist` and `monitor`. That is also how you check the category-level rows in the browser table, for example whether any `monitor` or `assist` packages are published for your workspace.

### 3. Open Application Configuration

Users in the `MAFCONFIGADMIN` security group (or an alternative group, if configured) see *Application Administrator, Application configuration*. The list there is filtered by what you are authorised for. IBM says "a user can configure only the applications they are authorized to access," so a missing app may be a permissions artefact rather than an absence.

| Method | Needs | Shows | Best for |
|---|---|---|---|
| SQL on MAFAPPDATA | DB read access | Every published app and revision | Complete inventory, revision counts |
| `/graphite/configtool/packages` | Token or API key, `OSLCMAFAPPDATA` access | Packages by category | Scripting, comparing environments |
| Application Configuration | `MAFCONFIGADMIN` membership | Apps you can configure | Day-to-day admins |

### Troubleshooting the inventory

| Symptom | Likely cause | What to check |
|---|---|---|
| App from this post missing in your list | Version predates the app (e.g. Material Request needs 9.2), or add-on not installed | `SELECT` the Manage version; compare against the "Since" column |
| App in the list but users cannot see it | Authorisation: apps are delivered per user | Security group access and signature options for that app |
| `TECHMOBILE` not found in MAXMENU | MAF apps are not `MODULEAPP` entries | Query MAXMENU by `KEYVALUE`, not `MODULEAPP` |
| Two similar IDs (`ITMOBILE`, `CXITMOBILE`) | Someone duplicated the app | Treat the non-IBM one as customer-owned |
| 403 from the packages endpoint | Missing `OSLCMAFAPPDATA` or `WPEDITSETTING` authorisation | Set to "Use Object Structure for Authorization Name" and grant |

> ⚠️ **Security reminder.** Reading MAFAPPDATA through the object structure requires `OSLCMAFAPPDATA` READ at minimum. Your security template for `ITMOBILE` and its siblings shows the app ID alongside `OSLCMAFAPPDATA`. Grant the least privilege that works and keep write access to your config admin group only.

## 🧭 Using the Catalog: Four Practical Scenarios

**Scenario 1: "Our requesters want a mobile service request form."** `SRMOBILE` exists, is Hybrid and needs no AppPoints. In 9.2 the `SELFSERVICE` security group gained new permissions for service request mobile users. Check the security group before you assume users will see the new options.

**Scenario 2: "Can storeroom staff count stock on a phone?"** Yes: `ICMOBILE` handles count books and ad hoc counts, offline. Reconciliation is the exception. It stays browser only, so build the reconcile step into the supervisor's desktop checklist.

**Scenario 3: "We want a mobile PO approval."** The honest answer is that we found no procurement role-based app and no roadmap item. Purchasing is classic. The nearest MAF approval is `SUPMOBILE` for work orders and, since 9.0, material requisition approval. If PO approval on a phone is a hard requirement, scope it as a custom MAF app or a workflow-notification approach and say so in the project plan.

**Scenario 4: "We duplicated TECHMOBILE years ago. What happens now?"** Your `MYTECHMOBILE` copy keeps working, but you do not automatically inherit IBM's new features such as 9.2 crew work orders. Compare the copy against the current original and plan a delta migration. The MAF-DEV series covers promotion and upgrades in detail.

## ✅ The Commandments of the App Catalog

1. **Ask the system first.** `MAFAPPDATA` beats any blog post, including this one.
2. **Never invent an ID.** If you cannot find it, write "ID unknown."
3. **Separate apps from capabilities.** Calibration, linear and spatial live inside other apps.
4. **Separate apps from saved queries.** `IROPENPOMOBILE` is not an application.
5. **Remember the shell.** Native shell, server-published apps, never a PWA.
6. **Plan for classic.** Purchasing, masters and planning remain Application Designer.
7. **Duplicate before you customise.** `TECHMOBILE` to `MYTECHMOBILE`.
8. **Never edit generated ids.** Delta files depend on them.
9. **Treat roadmap slides as slides.** Only release notes are commitments.
10. **Re-verify every release.** 9.2 added three apps in one drop.
