# MAS Security Operations: Identity, Access and Patching (Series Guide)

> 🎯 **Who this is for:** MAS administrators, platform engineers and security leads who own the answer to "who can get into our Maximo, what can they do once inside, and how fast can we close a hole?" If you also own the identity provider or the OpenShift cluster, this series is written for you too.

## 🔥 The Week the Login Page Became the Attack Surface

You've spent years hardening Maximo the way the old world taught you: put the application server behind a reverse proxy, lock the database, keep the admin console off the internet. Then MAS arrived, and the front door moved. Authentication is no longer a servlet filter inside your app server. It is a separate component in the suite, a login service that every user and every integration passes through before any application sees them.

On 3 October 2026, IBM published a bulletin for exactly that component. **CVE-2026-105052** is a path traversal in the MAS login service. IBM rates it CVSS 3.1 base score 7.5, vector `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`. Read that vector slowly: network, low complexity, **no privileges, no user interaction**. A remote attacker sends a crafted URL with `/../` sequences and reads files they should never see. IBM lists MAS 8.10, 8.11, 9.0, 9.1 and 9.2 as affected.

Two days later, on 5 October, IBM published a second bulletin for **Maximo AI Service 9.1.0 and 9.2.0**, headlined by **CVE-2026-90920**, a code-injection flaw (CWE-94) with an IBM-assigned CVSS of **9.8**.

What happened to your patching process in those two weeks? If the honest answer is "we found out from a vendor email, and we weren't sure which of our environments were affected," this series is for you.

> 💡 **Key insight:** MAS security is four layers that fail independently. You can have a flawless SAML setup and still be exposed through an unpatched login service. You can patch within 48 hours and still have 40 orphaned accounts that SCIM never deprovisioned. Treat each layer as its own program with its own owner and its own evidence.

This is Part 0, the map. Parts 1 to 6 are the territory. Everything below is labeled by how we verified it, because the rule for this series is the same as our lifecycle series: **do not state a date, version or score as fact until you have seen it on IBM's own page.**

## 🔐 Layer 1: Authentication — What MAS Actually Supports

IBM's authentication documentation describes local (MongoDB-held) accounts, LDAP and SAML as the established options, and from MAS 8.11 several can run at once so users have more than one way to log in. One identity provider can be set as the default; if SAML is configured but is not the default, it appears on the login page as an alternative. **Seamless login** is a separate setting: enable it and the login page is skipped entirely, with users redirected straight to the default IdP.

Where it gets more interesting is multiple identity providers of the *same* type, which matters for mergers, contractor populations and multi-tenant arrangements.

| Capability | Introduced | How you configure it | Source |
|---|---|---|---|
| Local + LDAP + SAML side by side | 8.11 | Suite administration | IBM Docs, authentication |
| Multiple SAML or LDAP IdPs | 9.0 | Admin API / CLI only | IBM Docs, multiple IdPs |
| Multiple OIDC IdPs | 9.1 | Admin API / CLI | IBM Docs, multiple IdPs |
| Multiple IdPs in the UI | 9.2 | Suite administration UI | IBM Docs; MAS 9.2 factbase |
| SAML initiated logout | 9.0 | SP settings plus matching IdP single logout | IBM Docs |
| Electronic signature validated against LDAP | 9.2 | Manage / suite settings | MAS 9.2 factbase |

The API route stays relevant after 9.2 because IBM positions it for automation, scripting and bulk configuration. It needs an API key with system administrator permission, which should make you think about where that key lives (Part 3).

### MFA lives in the IdP

The question we get most is "how do we turn on MFA in MAS?" The answer from IBM Developer's article on single sign-on and MFA for MAS is that you don't, not in MAS. The article describes three stages: establish SAML trust (MAS generates service-provider metadata, the IdP administrator registers it and returns IdP metadata, MAS uploads it), enroll users in the IdP with the right MFA policy, and enroll users in MAS with the issuer set to SAML. At login, MAS starts the SAML flow for users whose authentication type is SAML, and the IdP decides whether an extra factor is needed based on session state and policy.

That design is a strength if you have a good IdP and a gap if you don't. A community question from January 2025 asks how to apply MFA to external contractors on MAS 9 *without* an IdP; in the results we reviewed there is no confirmed answer, and we did not find an IBM page that says otherwise. We are also unable to confirm, from IBM's own pages, the claim sometimes repeated in partner circles that external OIDC providers cannot satisfy certain Manage-side flows. We list both as **open** and test them in Part 1.

> 💡 **Key insight:** "Does MAS support MFA?" is the wrong question. "Does every path into MAS go through something that enforces MFA?" is the right one. A single enabled local account is a path.

## 👥 Layer 2: Lifecycle — SCIM and LDAP Decide Who Still Exists

Authentication tells you who is at the door. Lifecycle decides who is on the guest list. MAS gives you two mechanisms: LDAP synchronisation and, since 9.0, SCIM 2.0 provisioning driven by your identity provider.

### SCIM 2.0 in five steps

IBM documents the setup as follows:

1. Create an API key in Suite administration with user-management access, setting the token expiry.
2. Exchange it for a JWT by calling `GET /v1/authenticate` with the key ID as the username and the token as the password (HTTP Basic).
3. Create a MAS SCIM profile that defines the configuration applied to synchronised users and groups.
4. In the IdP, create an application, enable SCIM 2.0 provisioning, set the base URL to `https://api.{mas-instance-id}.{domain}/scim/v2/{profileId}`, and supply the JWT as the header credential.
5. Assign users and groups to the application to start syncing.

```bash
# Step 2: exchange the API key for a JWT (placeholders only; never paste real keys into tickets)
curl -s -u "${MAS_API_KEY_ID}:${MAS_API_KEY_TOKEN}" \
  -H "mas-jwt-expiry-duration: P90D" \
  "https://api.${MAS_INSTANCE_ID}.${MAS_DOMAIN}/v1/authenticate"
```

That `mas-jwt-expiry-duration` header is where most SCIM deployments quietly go wrong. The default expiry is short, which means the IdP's provisioning connection breaks on a schedule nobody wrote down. IBM's documentation allows ISO 8601 durations such as `P90D`, and in MAS 9.2, 9.1.7 and 9.0.18 and later, much longer values (for example `P100Y`) or `NEVER`. Longer is more convenient and more dangerous: a non-expiring token with user-admin rights is a permanent credential for creating accounts. Part 2 shows how to pick an expiry, rotate it, and alarm on its age.

### The Entra ID footnote

IBM publishes a support article on Microsoft Entra SCIM problems with MAS. The symptoms it lists: users not properly deprovisioned, updates not reflected, attribute mismatches or skipped updates, multiple group members removed after a PATCH meant to remove one user, and inability to change user status. Its fix is a compatibility flag, `aadOptscim062020`, appended as a query parameter to the Tenant URL in the Entra provisioning settings. If your leavers process depends on Entra deprovisioning reaching MAS, you want that article before your next audit, not after.

### LDAP: still the incumbent

For shops that have not moved to SCIM, LDAP synchronisation remains the lifecycle engine. IBM's synchronisation tables are worth knowing: **Insert** adds a user and sets up an IdP issuer, entitlement and application access; **Update** does *not* touch entitlement or application access; **Delete** *deactivates* the MAS user when the LDAP entry disappears; and groups are always updated but **never deleted** by the sync. That last point surprises auditors. Our internal notes also record that LDAP connections must use LDAPS with TLS, and that MAS 9.1 allows multiple LDAP servers. Part 3 turns these into a leaver-test you can run.

## 🛂 Layer 3: Authorisation — Humans, Integrations and Now Agents

Everything that talks to MAS has an identity, and everything with an identity has a blast radius.

| Identity type | Credential | Where the permission lives | Common mistake |
|---|---|---|---|
| Human, interactive | SAML/OIDC/LDAP/local login | Security groups, AppPoints entitlement tier | Everyone in one broad group "to start" |
| Integration (MIF, ETL, reporting) | API key exchanged for a token | The user the key is tied to, plus security groups | One shared key across ten integrations |
| Administrator tooling (CLI, automation) | API key with system admin permission | Suite-level admin role | Key stored in a pipeline variable with no rotation |
| AI agent via MCP | Service identity / token (to be confirmed) | Whatever you scope it to | Letting the agent inherit a human's rights |

Our internal field guidance recommends **one API key per integration endpoint**, never shared keys. That is a good rule and an easy one to audit. Part 3 builds the inventory and the rotation routine.

MAS 9.2 also moves some authorisation surfaces. According to IBM's 9.2 material as captured in our factbase, the security groups **Sites** and **Object structures** tabs now live in suite security (Suite → Access and usage → Security groups), and Manage user settings such as default site and storeroom move to the suite **Users** page. If your runbooks tell people to "go to Security Groups in Manage," they are going to be out of date after the upgrade.

Separately, a quiet but security-relevant 9.2 detail: the installer's **administrative permission modes** (cluster, namespaced, minimal). Installing from OperatorHub defaults to minimal mode, but IBM states the mode cannot be changed during an upgrade, and the `mas upgrade` CLI sets **cluster mode** when going from 9.1 to 9.2, inheriting the 9.1 configuration. If your security review approved minimal permissions, check what your upgraded cluster actually has.

## 🔄 The 9.2 Identity Migration You're Probably Treating as a Version Bump

If you are planning 9.1 to 9.2, read this section before the maintenance window is booked.

IBM's upgrade documentation says that starting in 9.2, user and group data for authentication is stored in the **system relational database**, eliminating duplicated user data and the synchronisation process between suite applications. In plain terms: the MongoDB-held user store you knew is replaced, and "user synchronisation" between suite apps is removed.

| What changes | Before (9.1) | After (9.2) |
|---|---|---|
| Where users and groups live | MongoDB collections plus per-app copies | System relational database |
| Cross-app user sync | Required between suite applications | Removed for all applications |
| Old Mongo collections | In use | Renamed `User_pre_upgrade_91_backup` and `Group_pre_upgrade_91_backup`, unused, removable |
| User/group management APIs deprecated in 9.1 | Present | Removed; use the newer user management APIs |
| Custom system email templates | As customised | Not migrated; reapply manually |
| Migration mechanism | n/a | Pre-upgrade datamodel-migration job updates authentication mappings and syncs SCIM fields including `externalId` |

IBM's pre-upgrade instructions are concrete: run the Integrity Checker before the upgrade (via the Tools API, or `validate_integ.sh` inside the `maxinst` pod), resolve the reported issues, and after the upgrade check the `<instance_id>-datamodelmigration` job log under Workloads → Pods in OpenShift and confirm every user can log in.

Note the interplay with a Core patch: **DT501598**, fixed in Core 9.2.6 (18 September 2026), describes MAXUSER fields being overwritten during a 9.1 to 9.2 upgrade when MASISSUER is NULL. If your Manage users were created before issuer values were reliably populated, a MASISSUER audit belongs in your pre-upgrade checklist. Part 4 gives you the query pattern and the validation script.

Two claims you will see elsewhere, which we have *not* verified on IBM pages and therefore treat as third-party: that the classic User application is deprecated in 9.2, and that AppPoint calculation changes by security group. Part 4 tests both against IBM documentation and says plainly what we find.

## 🩹 Layer 4: Patching — The October 2026 Test

You can't harden what you can't patch quickly. MAS's patch mechanics are different from 7.6 fix packs, and the October 2026 bulletins exercised every part of them.

### Reading the releases page

IBM's MAS releases-information page lists Core builds with a type and date. Taken together, the October entries show the pattern:

| Core line | 7 Oct 2026 (interim) | 29 Sep 2026 (standard) | 18 Sep 2026 (interim) | Notes |
|---|---|---|---|---|
| 9.2 | 9.2.8 | 9.2.7 | 9.2.6 | 9.2.4 and 9.2.5 "reserved for internal use" |
| 9.1 | 9.1.27 | 9.1.26 | 9.1.25 | 9.1.23 and 9.1.24 reserved |
| 9.0 | 9.0.33 | 9.0.32 | 9.0.31 | 9.0.30 reserved |

Three lessons sit in that table. First, **interim builds exist for urgent fixes** and arrive between the standard monthly releases; the 7 October interim carried the login-service fix across three lines at once. Second, **version numbers skip**: "reserved for internal use" means a gap is not a missing release you forgot to install. Third, **component versions are independent**: Manage 9.2.4 (29 September) ships with Core 9.2.7 and AI Service 9.2.3, and AI Service's 9.2.3 is a different artifact from Core's 9.2.3 (27 August). Part 5 shows how to build a version-skew table for your own environments.

### CVE-2026-105052 in detail

| Item | Value | Source |
|---|---|---|
| Component | MAS login service (CoreIdp login) | IBM bulletin; third-party tracker names the component |
| Weakness | Path traversal, CWE-22 | IBM |
| CVSS 3.1 base | 7.5 | IBM |
| Vector | `AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N` | IBM |
| Affected | MAS 8.10, 8.11, 9.0, 9.1, 9.2 | IBM |
| Fixed | Core 9.0.33, 9.1.27, 9.2.8 or later | IBM |
| 8.10 / 8.11 | CoreIdp login 3.2.201 / 4.0.179 via image-tag override | IBM |
| Bulletin published | 3 October 2026 (modified 14 October) | IBM |
| Known exploitation | Not listed in CISA KEV per a third-party tracker | Third-party |

For 8.10 and 8.11 estates that cannot upgrade immediately, IBM's workaround edits the coreidp custom resource in OpenShift (Administration → CustomResourceDefinitions → coreidp) and adds the login image tag under `spec.settings`. After you save, the CoreIdp Entity Manager operator recreates the `coreidp-login` deployment. The sentence to memorise is IBM's warning not to remove the override until you have applied the October 2026 monthly update or later; removing it earlier reverts you to the vulnerable image.

```bash
# Illustrative checks after applying the 8.10/8.11 workaround (names depend on your instance)
oc get coreidp -A
oc get deployment -A | grep coreidp-login
oc get coreidp <instance> -n <core-namespace> -o jsonpath='{.spec.settings.imageTags}'
```

> ⚠️ **Lifecycle collision:** 8.7, 8.8 and 8.9 went out of support on 30 April 2026. This bulletin lists 8.10 and 8.11 as the oldest affected versions and gives them a workaround. We found no equivalent fix for 8.9 and earlier, and unsupported versions do not receive one. If you still run those, your security position and your support position are the same problem; see the [lifecycle series](/blog/mas-lifecycle-series-index).

### CVE-2026-90920 and the AI Service lesson

| Weakness | Code injection, CWE-94 | IBM |

There is a wider lesson here. AI Service is the component that lets Manage talk to large language models. Many sites installed it as a pilot and forgot it. A pilot component with a 9.8 critical flaw and no workaround is how a proof of concept becomes an incident. The question to ask is not "have we patched AI Service?" but "do we know every optional component installed on every cluster, and who owns it?"

We also note a third-party tracker lists an **IoT** denial-of-service CVE and sibling AI Service DoS CVEs from the same period. We did not read an IBM bulletin for the IoT item, so Part 5 carries it as open rather than repeating scores we cannot source.

### The cadence behind it

Catalog releases are monthly: v9-261007 is the most recent we have confirmed, with 261029, 261126 and 261224 scheduled according to the knowledge base. The IBM CLI documents which OpenShift versions each catalog supports: catalogs v9-260924 and later support OCP 4.18 to 4.22, and v9-260827 was the last with OCP 4.16. Cluster-level hardening is moving as well: the ansible-devops 37.15 to 37.21 line made Kafka passwords FIPS-style (32 characters) and added the CIS OWASP ruleset, which is the sort of change that rewards teams who read release notes rather than wait for an incident.

## 🤖 Layer 3.5: AI Agents and the MCP Server

Here is the newest layer, and the one with the least documentation.

IBM's 12 August 2026 article on agentic workflows in Maximo Assistant says that in 9.2 you can integrate external agents and tools with Maximo's agents and tools through the **Maximo MCP server**, and describes AI-assisted actions that create, update and modify records, for example changing work order status, creating follow-up work orders and creating service requests. It also says "you will also be able to use any of your automation scripts as custom tools," which is future tense, announced and not shipped. Reading the page carefully, it **does not describe human approval steps or permission scoping** for these write actions.

That is not a criticism of IBM; it's a marketing-adjacent article, not a security guide. It is a warning about *your* design responsibilities:

| Design question | Why it matters | Where we'll answer it |
|---|---|---|
| What identity does the agent act as? | Inheriting a human's identity makes audit trails meaningless | Part 6 |
| What is the smallest security group that does the job? | An agent that can read work orders should not be able to change status | Part 6 |
| Can its credential be rotated without redeploying? | Long-lived tokens leak | Parts 3, 6 |
| Is every write recorded with the agent's own identity? | Needed for post-incident review | Part 6 |
| Which actions need a human in the loop? | "Trusted autonomy" is not "human-free" | Part 6 |

The same REST API facts apply. IBM's developer documentation describes exchanging a Maximo API key for a time-limited token that is sent in a request header on later calls. Whatever MCP does underneath, assume the API-key and token mechanics matter, and test rather than assume.

> 💡 **Key insight:** The AI Service CVE and the MCP server are the same story from two angles. The more MAS exposes to automated callers, the more your security posture depends on identity hygiene and patch speed, not on the cleverness of the AI.

## 🔟 The Ten Commandments of MAS Security Operations

1. **Name the layer before you name the fix.** Authentication, lifecycle, authorisation and patching fail separately.
2. **MFA is an IdP policy.** If a path into MAS bypasses the IdP, it bypasses MFA.
3. **Disable what you don't use.** Local accounts, unused IdPs and pilot components are attack surface.
4. **Every credential has an owner and an expiry.** A non-expiring token is a decision, not a default.
5. **Test the leaver, not the joiner.** Provisioning that works proves nothing about deprovisioning.
6. **One key, one integration.** Shared admin keys erase accountability.
7. **Treat the upgrade as an identity migration.** Run the Integrity Checker before 9.2, not after.
8. **Know your component versions.** Core, Manage and AI Service count separately.
9. **Interim builds are for emergencies; have a path for them.** Do not wait for the monthly cycle.
10. **Agents are identities.** Give them their own, scope them narrowly and log every write.

## ❓ Frequently Asked Questions

**Does Maximo Application Suite have its own MFA, or do I need my identity provider?**
MFA is applied by your SAML identity provider, per IBM Developer's article. MAS trusts the assertion. Local accounts and plain LDAP binds get no extra factor, and we found no confirmed IBM answer for MFA without an IdP.

**Which MAS versions are affected by the October 2026 login-service vulnerability, and what do I install?**
CVE-2026-105052 affects 8.10, 8.11, 9.0, 9.1 and 9.2. Fixed in Core 9.0.33, 9.1.27 and 9.2.8 or later (7 October 2026). For 8.10/8.11, override the CoreIdp login image tag to 3.2.201 or 4.0.179 and keep it until you have taken the October 2026 monthly update or later.

**Is the Maximo AI Service code-injection CVE real, and is there an IBM bulletin?**
Yes. IBM published it on 5 October 2026: CVE-2026-90920, CWE-94, CVSS 9.8, affecting AI Service 9.1.0 and 9.2.0. Upgrade to 9.1.19 or 9.2.3 or later; no workaround is listed. AI Service versions are independent of Core versions.

**What actually changes for users and groups when I upgrade from MAS 9.1 to 9.2?**
User and group data moves into the system relational database, user sync between suite applications is removed, and a pre-upgrade migration job maps authentication data including SCIM `externalId`. Run the Integrity Checker first, and check DT501598 (MAXUSER overwritten when MASISSUER is NULL).

**Do AI agents that connect to MAS through MCP need a different security model from human users?**
They need the same controls applied more strictly. IBM's article describes write actions through the MCP server but not approval steps or permission scoping, so give each agent its own identity, a least-privilege security group, a rotatable credential and its own audit trail.
