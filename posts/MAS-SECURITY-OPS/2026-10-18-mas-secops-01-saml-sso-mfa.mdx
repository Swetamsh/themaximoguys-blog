# SAML SSO and MFA in MAS: Why MFA Lives in Your Identity Provider

> 🎯 **Who this is for:** MAS administrators and identity engineers who have been asked some version of "can we turn on MFA for Maximo?" and who need a clear answer, a working SAML configuration and a troubleshooting path when logins fail or crawl. Part 1 of the [MAS Security Operations series](/blog/mas-secops-series-index).

## 🔥 The Ticket That Starts Every SAML Project

The request usually arrives from a security review: *"Our policy says every application with production data needs multi-factor authentication. Please enable MFA on Maximo."*

You open the Suite administration page. You look through Configurations, Users, Authentication. You search the documentation. And you don't find a toggle that says "Require MFA."

You haven't missed it. In the IBM material we could read, it isn't there. IBM Developer's article on single sign-on and multi-factor authentication for MAS describes the architecture plainly: MAS is the SAML service provider, your identity provider decides whether a second factor is needed, and MAS trusts the assertion that comes back. MFA is something your IdP does *to* a login before MAS ever hears about it.

That sounds like a limitation. It's actually a design decision with consequences you need to understand before you tell the security team "yes":

- Your MFA strength is the IdP's MFA strength. Phishing-resistant factors, conditional access and risk policies all come from the IdP.
- Any road into MAS that doesn't cross the IdP doesn't get MFA. Local accounts. LDAP binds. API keys. Dedicated login pages.
- The quality of your SAML configuration, especially NameID and user mapping, now decides whether people can log in at all.

> 💡 **Key insight:** In MAS, "enable MFA" is not a configuration task. It is an architecture task: make the IdP the only interactive door, then enforce the policy there.

This post is Layer 1 of the four-layer model from the [series guide](/blog/mas-secops-series-index): authentication. Everything below is labelled by how we verified it. IBM Docs and IBM Support pages we read directly are stated as fact; IBM pages that were gated or only partially visible are described as such; partner and community claims are marked.

## 🧭 What MAS Authentication Actually Offers

Start with the menu of options, because "SAML" is only one entry on it.

IBM's authentication documentation lists local (MongoDB-backed) users, LDAP, SAML and, from 9.1, OpenID Connect. Regardless of where authentication happens, IBM states that access management and authorization privileges stay in MAS. Your IdP says *who you are*; MAS still decides *what you may do*.

| Option | Where the password check happens | MFA possible? | Introduced / notes |
|---|---|---|---|
| Local (MongoDB) | MAS itself | No MFA control in the documentation we read | Original option; 9.2 moves user data to the system relational database (see Part 4) |
| LDAP | Your directory, via MAS's LDAP bind | Only whatever the directory enforces; there is no interactive second factor on a plain bind | Multiple options side by side from 8.11 |
| SAML 2.0 | Your IdP | **Yes, at the IdP** | Multiple SAML/LDAP IdPs via API from 9.0; UI from 9.2 |
| OIDC | Your OpenID provider | Yes, at the provider | Documented from 9.1; see the OIDC section below |
| API key | No password; a key exchanged for a token | No | Used for integrations and automation (Part 3) |

Three version facts from IBM Docs are worth pinning to the wall:

1. **8.11:** you can configure local, SAML or LDAP to give users several login options and choose one as the default. IBM also notes that from 8.11, a user created without an authentication type cannot access MAS at all.
2. **9.0:** multiple identity providers *of the same type* (for example two SAML IdPs) can be configured through the API. SAML initiated logout appears. When you upgrade users from Maximo Asset Management 7.6 you can choose local or SCIM ownership for SAML users.
3. **9.2:** multiple identity providers can be configured in the Suite administration UI. IBM still recommends the API route for automation, scripting and bulk configuration.

## 🏗️ How a SAML Login Flows Through MAS

Before the steps, the picture. MAS acts as a SAML **service provider (SP)**. Your IdP is the authority. When a user opens any MAS endpoint, an internal OIDC process in MAS kicks in and, depending on your default-IdP settings, sends the browser to the IdP.

```text
 SP-INITIATED LOGIN
 ┌─────────┐  1 open Manage URL   ┌────────────────────┐
 │ Browser │─────────────────────▶│ MAS (auth host)    │
 └────┬────┘                      │ coreidp-login      │
      │  2 redirect with          └─────────┬──────────┘
      │    SAML AuthnRequest                │
      ▼                                     │
 ┌──────────────────────────┐               │
 │ Identity provider (IdP)  │               │
 │  • password / SSO session│               │
 │  • MFA policy ◀── HERE   │               │
 │  • conditional access    │               │
 └────────────┬─────────────┘               │
              │ 3 signed SAML assertion     │
              │   (NameID = user identifier)│
              ▼                             ▼
 ┌────────────────────────────────────────────────────┐
 │ MAS validates signature, matches NameID to a MAS   │
 │ user whose authentication type is SAML, then       │
 │ issues its own session → Manage / Monitor / etc.   │
 └────────────────────────────────────────────────────┘
```

Two flavours exist, and IBM documents both:

| Flow | Starts at | What happens | Best for |
|---|---|---|---|
| **SP-initiated** | A MAS URL (bookmark, link, mobile) | MAS shows its login page (user clicks Continue) or, with seamless login, redirects straight to the IdP | New deployments; IBM Developer recommends it for greenfield projects for better security |
| **IdP-initiated** | A tile in the IdP portal | The IdP posts an assertion; a `relayState` parameter can drop the user directly into an application | Portal-centric organisations; deep links into Manage |

If the user already has a MAS session, the application just opens. If the user already has an IdP session, the IdP skips the password and may skip the second factor too, depending on your policy. That last sentence is the heart of the MFA discussion.

## 🛠️ Setting Up SAML: The Suite Administration UI

This is the path IBM documents in the Suite administration UI. The exact labels may shift slightly between releases; the structure does not.

**Before you start**, agree three things with your IdP administrator: the **service provider name** (a short identifier that becomes part of your SP URLs), the **NameID format** (see the next section) and whether you want **initiated logout** (single logout).

1. **Open the SAML page.** In Suite administration, choose *Configurations* from the side navigation and then *SAML authentication*.
2. **Create the SP information.**
   - Give it a **display name** (this is what users see as a login option).
   - Enter your preferred **service provider name**.
   - Choose a **name identifier format**.
   - Optionally tick **Enable initiated logout** (available from MAS 9.0). If you do, you must also enable single logout on the IdP side.
3. **Generate and download the SP metadata file.** If you later change the service provider name or the user identifier format, IBM says you must save and generate the metadata again and re-register it with the IdP.
4. **Register MAS in the IdP.** Upload the metadata XML, or copy values from it, into a new enterprise application or SAML app in the IdP. If you enabled initiated logout, add the single logout URL, which is the single-logout service in the metadata, in the pattern `https://auth.<domain>/ibm/saml20/<saml_name>/slo`.
5. **Download the IdP metadata XML** from the IdP.
6. **Upload it back into MAS** on the SAML authentication page and save.
7. **Make the users real.** Create or synchronise users whose authentication type is **SAML** (next section).

IBM Developer's article describes the same exchange as five hand-offs between the MAS administrator and the IdP administrator: SP metadata out, SP application created and certificate imported at the IdP, IdP metadata back, upload, confirm. In practice the slowest step is not technical. It's the two administrators being different people in different teams, so put both on one call.

### The Entra ID variant

Microsoft publishes a tutorial for Maximo Application Suite in the Entra gallery (last updated by Microsoft in June 2026, with screenshots from MAS 8.9). The pieces that matter:

- In Entra: *Enterprise apps → Maximo Application Suite → Single sign-on → SAML*. If you upload the SP metadata file, **Identifier** and **Reply URL** populate automatically; if not, Microsoft's note says to fill them manually and contact IBM support for the values.
- For SP-initiated mode, set the **Sign on URL** to `https://<workspace_id>.<mas_application>.<mas_domain>`.
- Download the **Federation Metadata XML** and upload it to the MAS SAML page.
- In MAS, Microsoft's tutorial selects **emailAddress** as the name-ID format.
- Create the test user in Suite administration with authentication type **SAML**, and put the **UPN** in the Display Name and Primary email fields, because Microsoft's guidance is that they must match what Entra sends.

> ⚠️ That tutorial is the vendor's recipe for its own side. The IBM Docs page remains the source of truth for what MAS expects. When the two seem to disagree, trust the one describing the system you are changing.

## ⚙️ Setting Up SAML Through the API

From 9.0 the API is how you configure multiple SAML IdPs, and from 9.2 it's still IBM's recommended route for automation and bulk work. IBM's page lists these steps:

1. Generate an API key with **system admin permission** and use its access token.
2. Create the IdP with a `PUT` to `https://api.<masDomain>/config/saml/<idpId>` and a JSON body with `spInitiatedLogout`, `displayName`, `issuer`, `serviceProviderName` and `nameIDFormat`.
3. Download the generated SAML configuration XML.
4. Wait a few minutes, then open `https://auth.<masDomain>/ibm/saml20/<serviceProviderName>/samlmetadata`. IBM warns this URL can take a few minutes to appear.
5. Upload that file to your IdP, then download the IdP's metadata.
6. Upload the IdP metadata with a `PUT` to `https://api.<masDomain>/config/saml/<idpId>/metadata` as multipart form field `file`.
7. Wait for the operator to reconcile and the UI to refresh.

```bash
# Illustrative only: placeholders, never real tokens in tickets or shell history.
# The auth header name and token exchange are described in IBM's API key documentation.
curl -s -X PUT "https://api.${MAS_DOMAIN}/config/saml/${IDP_ID}" \
  -H "Content-Type: application/json" \
  -H "${MAS_AUTH_HEADER}" \
  -d '{
        "displayName": "Corporate SSO",
        "serviceProviderName": "corp-sso",
        "issuer": "https://sts.example.com/idp-entity-id",
        "nameIDFormat": "email",
        "spInitiatedLogout": true
      }'
```

**Check the `nameIDFormat` value against IBM's list before you send it.** The documentation page lists these accepted values: `customize`, `email`, `encrypted`, `entity`, `kerberos`, `persistent`, `unspecified`, `windowsDomainQualifiedName` and `x509SubjectName`. The body above is a pattern, not a copy-paste: confirm every value against IBM's page for your release.

Two operational notes from the same page. Changes are not instant, because an operator reconciles them. And the IBM examples use `--insecure` to skip certificate verification; do not carry that into a production runbook.

## 🪪 NameID and User Mapping: Where Most SAML Projects Actually Fail

Here is the sentence that explains half of all SAML tickets: **SAML uses its own ID to link to MAS users.** IBM's authentication documentation says so directly. The signed assertion carries a NameID; MAS looks for a user whose identifier matches that NameID *and* whose authentication type is SAML. No match, no login, even though the IdP just proved who you are.

IBM Developer lists the NameID choices this way:

| NameID format | How the user maps | Use when |
|---|---|---|
| Email address | The same user logs in at the IdP and MAS; the identifier is the email | Emails are unique, stable and already your Maximo user identifier |
| Persistent | An opaque IdP-issued ID; a different MAS user can correspond to it | Emails change (marriage, rebrand, mergers) and you want stability |
| Unspecified / customize | You define it | You must match an existing identifier convention exactly |
| Windows domain qualified name | Listed by the article, not explained | Legacy AD estates; test carefully |

> 💡 **Key insight:** Choose the NameID format *before* you create users, and write the mapping on one page: IdP attribute → NameID → MAS user identifier. If you change the format later, IBM says you must regenerate and re-register the SP metadata.

### Three ways users get a SAML identity

| Method | What it does | Watch out for |
|---|---|---|
| **SCIM provisioning** from the IdP (Part 2) | Creates and updates MAS users and groups from the IdP | Token expiry, deprovisioning behaviour |
| **LDAP synchronisation** | Imports users from a directory | Leaver behaviour; LDAPS only (Part 3) |
| **Manual / CSV import** | IBM Developer: bulk import with the CSV user template, setting the issuer to SAML | Easy to forget the authentication type; fine for pilots, poor for lifecycle |

The IBM Community thread we cite later makes the same point from the other side: after SSO is configured, **SAML IDs must be set on the users**, and that doesn't happen automatically unless SCIM or LDAP synchronisation is in place.

### The upgrade trap

IBM Support published (and last modified on 23 June 2026) an article titled around SAML authentication failing after an upgrade to MAS 8.11, because of a UserID/Username mismatch in the database migration. The visible abstract says the coreidp pod logs show lines such as "SAML user maxadmin not found in MAS database" and "User: maxadmin is not a SAML user." The resolution is behind IBM's login wall, so we won't paraphrase it. What you can take from the symptom: **after any upgrade that migrates user data, test a SAML login before you declare victory.** The 9.1 to 9.2 migration is exactly such an event; Part 4 covers its pre-flight checks.

### Special characters and reverse proxies

Two defects from IBM's fixed-known-issues readme for **MAS 9.1.0 (released 24 June 2025)** belong in your mapping checklist:

- **DT423352:** SAML validation failing for user IDs with special characters.
- **DT397993:** SAML not working behind a reverse proxy.

The 9.1.0 page gives titles only, no root causes. If your user IDs contain anything other than letters and digits, or if your auth host sits behind a WAF or load balancer that rewrites headers, test those two cases explicitly on whatever Core version you run.

## 🚪 Default IdP, Seamless Login and the Links You Give Users

Once SAML works, you decide how people *arrive*. IBM describes three global configurations from 8.11:

| Configuration | What users see | Typical use |
|---|---|---|
| SAML configured, **not default** | MAS login page with SAML as an alternative option | Migration phase; mixed populations |
| SAML **default**, seamless login **disabled** | MAS login page with SAML as the primary option | Most organisations after cutover |
| SAML **default**, seamless login **enabled** | No MAS login page; browser goes straight to the IdP | Strict SSO shops |

The Suite custom resource controls this with `spec.sso.defaultIDP` and `spec.sso.seamlessLogin`. In the UI, IBM's path is Suite administration → Users → Authentication tab → Default login behavior.

> ⚠️ **A compliance gotcha from IBM's own page:** if you enable seamless login, the login page is never shown. If you must display a federal-style security banner or system notification on the login page, keep seamless login **disabled**, or users will never see the message.

### Deep links and dedicated pages

- **IdP-initiated with a different default:** if another IdP is your default but you still want seamless IdP-initiated SAML, IBM documents a separate endpoint for the `relayState`: `https://auth.<masdomain>/idplogin/idpinitiated`, with `appid`, `wsid` and `apppath` parameters. IBM's example sends users to Manage in workspace `main` with `?appid=manage&wsid=main`.
- **Dedicated login pages:** `https://auth.<masdomain>/idplogin/loginpage?idp=saml:default-saml` shows only the SAML option. IBM is firm that this is an alternative mechanism, **not** a way to implement seamless login: "for SAML seamless integration, you must set SAML as default and seamless instead of using a SAML dedicated login page."
- **A fixed defect:** **DT380909**, "Dedicated SAML login endpoint does not work when seamless login is enabled," is listed in IBM's MAS 9.0.0 fixed-issues page. If you see that on an older 8.x build, that's your explanation.

Dedicated pages matter for MFA in one more way: the `idp=local` variant shows a local-password page. If local accounts still exist, that URL still works unless you've removed the accounts.

## 🔐 MFA: Mapping Every Door Into MAS

Now the part the security team actually cares about. Here is IBM Developer's model of MFA in MAS, restated as a control map.

At login, MAS starts the SAML flow for users whose authentication type is SAML. The IdP then decides whether to challenge based on its session state and policy. Steps in the flow are marked optional in IBM's description precisely because they depend on whether the user has an active IdP session or whether policy demands a fresh factor.

Choosing the second factor, per the same article, depends on whether Maximo is exposed to the internet or only the intranet, what your IdP supports, and user readiness. That's the IdP team's decision, not a MAS option.

### The door-by-door table

| Door into MAS | Passes through IdP? | MFA enforced by IdP? | Action |
|---|---|---|---|
| Browser, SAML default + seamless | Yes | Yes, by policy | Target state |
| Browser, SAML default, not seamless | Yes (user clicks) | Yes if the user picks SAML | Set seamless or train users |
| Browser, **local** password (`idp=local`) | **No** | **No** | Disable local users or restrict to a documented break-glass account |
| Browser, **LDAP** password | **No** | **No** (LDAP bind) | Remove LDAP as a login option if you only need it for sync |
| IdP portal tile (IdP-initiated) | Yes | Yes | Fine; use the `idpinitiated` endpoint with `relayState` |
| REST client with **API key** | **No** | **No** | Scope and rotate keys; Part 3 |
| Mobile (Maximo Mobile) | Depends on configuration | Depends | Test; IBM has a support article on mobile SAML login errors |
| Another IdP configured (9.0+) | Yes, for that IdP | Per that IdP | Inventory every IdP; each has its own policy owner |
| Self-registration (9.0+) | Depends on selected IdP | Depends | Review whether you need it |

Notice what this table says. SAML with MFA protects the door users walk through. It does nothing for the windows. The most common audit finding we expect from MAS estates is not "SAML is weak"; it is "SAML is strong and local accounts are still enabled."

### The honest limits

- **No IdP, no MFA.** We found a January 2025 IBM Community question asking how to apply MFA to external contractors on MAS 9 without an IdP. In the results we reviewed it has no confirmed answer, and no IBM page we read provides an in-MAS alternative. Treat "MFA for users who cannot use an IdP" as an **open item**, not a missing checkbox.
- **MFA at the IdP is only as good as the IdP session.** A long IdP session means users may not be challenged for a second factor when they open MAS. That's usually the right usability trade-off, but write it down: *MFA at login* and *MFA at sensitive actions* are different things, and MAS gives you no per-action step-up.
- **Initiated logout matters for shared machines.** IBM's 9.0 option logs out current sessions before another user logs in with the same credentials, but only if the IdP is also set up for single logout.

### A practical MFA hardening sequence

1. Put an MFA policy on the IdP application that represents MAS. Prefer phishing-resistant factors for administrators.
2. Switch to SAML default; decide on seamless login (mind the banner issue).
3. Inventory local users, LDAP login, API keys and extra IdPs from the Suite administration pages.
4. Disable or delete what you can; for what remains, document owner, reason and compensating control.
5. Test as a fresh user in a private browser window: you should be challenged at the IdP, never see a MAS password prompt, and land in the right application.
6. Keep the evidence: IdP policy screenshot, MAS default-IdP setting, the user inventory and the test notes.

## 🌐 The OIDC Question: Where IBM's Pages Disagree

You will meet this in vendor calls: *"MAS only supports SAML, so our OIDC-only identity provider won't work."* Our brief for this post pointed to the IBM Manage FAQ as the source of an "external OIDC identity provider gap." Here is what we found when we read the pages.

| Source | What it says | Date signal |
|---|---|---|
| IBM Manage FAQ (`ibm-mas-manage.github.io/faq`) | Lists supported methods as Local IDP, LDAP and SAML; under "EAM to Manage gaps" it lists **"OpenID support in addition to SAML,"** "Support multiple LDAPs" and "Local user security controls parity" as not yet supported | Undated on the page we read |
| IBM Developer SSO + MFA article | "Because Maximo Application Suite supports only SAML 2.0 for single sign-on…" OIDC is mentioned as widely used but not covered | Predates 9.1 as far as we can tell; not dated in the text we read |
| IBM Docs, authentication | Lists OpenID Connect authentication as a method | Current docs |
| IBM Docs, configuring OIDC | "Starting in Maximo Application Suite 9.1, you can configure OpenID Connect (OIDC) authentication" | 9.1+ |

The FAQ's own gap list contains an item we know is now stale: "Support multiple LDAPs" is listed as a gap, yet IBM Docs describe multiple LDAP IdPs from 9.0. That's a good sign the gap list was written for an earlier release and not refreshed. Our reading, flagged as our interpretation:

> The "OIDC gap" is historical for the suite login. From 9.1 IBM documents OIDC configuration. What we could **not** confirm is whether *every* Manage-side flow behaves identically for OIDC-authenticated users, and we found no IBM page that settles it either way. Prove it in your own workspace.

### What IBM Docs say about configuring OIDC (9.1+)

- Register MAS with your OpenID provider using the redirect URL `https://auth.<masdomain>/oidcclient/redirect/default-oidc/`. You receive a client ID and secret.
- In Suite administration, go to Configurations → OIDC authentication.
- Supply a **discovery endpoint** (`/.well-known/openid-configuration`); if you don't, you must provide the issuer identifier, authorization endpoint, token endpoint and JWKS URI.
- Choose the **user identifier** from the token: `sub`, `preferred_username`, `email` or `name`. This is the OIDC twin of the NameID decision above.
- Choose the token endpoint authentication method: Post, Basic or Private key JWT (IBM suggests Basic if you don't know).
- Pick the signature algorithm your provider supports (IBM says the default is typically RS256).

### A decision rule

| Your situation | Recommendation |
|---|---|
| IdP supports SAML 2.0 (nearly all enterprise IdPs do) | Use SAML; it is the best-documented path, with SP/IdP-initiated flows and single logout described in IBM Docs |
| IdP is OIDC-only | Use OIDC from 9.1; run a pilot covering login, Manage, mobile and REST before cut-over; open an IBM case for anything that fails |
| You are on MAS 8.x and OIDC-only | Plan the upgrade or put a SAML-capable broker (Keycloak, for example) in front; IBM Developer lists Keycloak among IdPs that support SAML 2.0 |

## 🐌 Troubleshooting: Failed and Slow SAML Logins

SAML failures arrive as two symptoms: the login **fails** (an error page) or it **drags**. Treat them separately.

### Part A: failures

A September 2025 thread on the IBM Community (Maximo group) captures a clean example. A user configured SSO on MAS 9 and saw **AIUOM0100E: You cannot log in because of a SAML authentication error.** The answers, in order:

1. Check the **coreidp** and **coreapi** pods (coreapi runs three replicas by default, per the reply).
2. Confirm **SAML IDs are set for users**; that isn't automatic without SCIM or LDAP sync.
3. SAML needs exact configuration on both sides, and logs may not carry key details, so **capture the exchange with a SAML tracer** browser extension and decode the request and response XML. The thread's author reported the problem resolved using this approach.

Turn that into a sequence:

| # | Check | How | What it tells you |
|---|---|---|---|
| 1 | Is the user a SAML user in MAS? | Suite administration → Users; check authentication type | "User is not a SAML user" log lines |
| 2 | Does the NameID match? | SAML tracer: read `<NameID>` in the response; compare with the MAS user identifier, including case | Mismatch is the top cause |
| 3 | Does the IdP certificate/metadata match? | Compare the signing cert in IdP metadata with what MAS holds; re-upload after IdP cert rotation | Signature validation failures |
| 4 | Is the SP metadata current? | If you changed SP name or NameID format, regenerate and re-register | IdP rejecting the request |
| 5 | Are clocks in sync? | Compare IdP and cluster time | Assertion "not yet valid" or expired |
| 6 | Is a proxy rewriting things? | Compare the host in the ACS URL with the browser URL | Reverse-proxy failures (see DT397993) |
| 7 | Special characters in the identifier? | Test with a plain-ASCII user | DT423352 pattern |
| 8 | Did an upgrade change user records? | Look for "SAML user … not found in MAS database" in coreidp logs | The 8.11 migration symptom |

Useful commands (namespace and pod names depend on your instance ID; verify before running):

```bash
# Find the identity pods in the Core namespace
oc get pods -n mas-${MAS_INSTANCE_ID}-core | grep -E 'coreidp|coreapi'

# Follow logs while a tester attempts a login
oc logs -n mas-${MAS_INSTANCE_ID}-core -f deploy/coreidp-login --tail=200
```

The `coreidp-login` deployment name comes from IBM's CVE-2026-105052 bulletin material covered in the [series guide](/blog/mas-secops-series-index); confirm the exact names with `oc get deploy` on your cluster.

### Part B: slow logins

"Login is slow" has at least four different owners, so time it before tuning it.

```text
 USER CLICK ──▶ [MAS redirect] ──▶ [IdP: password + MFA + policy] ──▶ [MAS: validate + lookup + session]
                   a                          b                              c
 Measure a, b, c separately with browser developer tools (Network tab, preserve log)
```

| Segment | Typical culprit | Evidence | Who fixes it |
|---|---|---|---|
| a. MAS redirect | Pod restarts, ingress, DNS | Intermittent "Application is not available" | Platform team |
| b. IdP leg | Conditional access evaluation, remote MFA push, risky-sign-in checks | Long time on IdP domain | Identity team |
| c. MAS validation and lookup | User-count growth, missing index, database lookups | Long wait after returning to the auth host | Patch level |

IBM's pages give real anchors for segment a and segment c:

- **Segment a:** an IBM Support article, modified 23 June 2026, is titled around the **coreidp pod crashing and restarting under heavy load**, causing intermittent login failures and an "Application is not available" page. The excerpt we could read gives the symptom but not the cause or the fix, so open the full article with your IBM ID before changing resources.
- **Segment c:** IBM's **MAS 9.1.4 readme (6 October 2025)** lists **DT422664, "Login performance degrades as the number of users grows."** The same page lists ten other fixes, none login-related. An older IBM readme for **MAS 8.8.1** (September 2022) describes removing redundant database lookups and adding a lookup index to improve authentication performance. Different releases, same family of problem: authentication cost that scales with users.
- **Also relevant:** IBM Support has a generic "Logging into Maximo is delayed" note covering Maximo broadly; its body is gated, so we cite it only as a pointer.

What we could **not** find on any IBM page we could read is a SAML-specific slow-login fix. If someone claims there is one, ask for the document. Our rule for this series stands: a performance claim without a source is a guess.

A practical order of operations for a slow-login ticket:

1. Record timing for segments a, b and c for ten logins (cold and warm).
2. If segment b dominates, hand it to the IdP team with the HAR file.
3. If segment c dominates, check your Core version against the DT422664 fix level (9.1.4) and any later monthly interim builds, and read the Core release notes for newer authentication fixes.
4. If segment a shows restarts, collect `oc describe pod` and previous logs for the coreidp pods and open an IBM case referencing the coreidp restart article.

## 🔟 The Ten Commandments of SAML and MFA in MAS

1. **MFA is an IdP policy.** Put it where it can be enforced.
2. **Every door counts.** Local, LDAP, API key, extra IdPs: inventory and justify each.
3. **Decide NameID first.** Then create users. Changing it later means regenerating and re-registering metadata.
4. **A SAML user is a user with the SAML authentication type.** The IdP proving identity is not enough.
5. **Seamless login hides the login page.** Check your banner requirements first.
6. **Never build seamless login out of a dedicated page.** IBM says to use default plus seamless.
7. **Test upgrades with a SAML login.** The 8.11 migration taught us why.
8. **Time the three segments before tuning.** Redirect, IdP, validation: three owners.
9. **Capture the assertion.** A SAML tracer beats guessing from logs.
10. **Label what you verified.** If you only have a vendor's claim, say so in the ticket.

## ❓ Frequently Asked Questions

**Can I turn on MFA inside Maximo Application Suite itself?**
Not in the IBM material we read. MFA is a policy on your SAML IdP; MAS trusts the signed assertion. Anything that bypasses the IdP (local accounts, LDAP binds, API keys) bypasses MFA.

**Does MAS support OIDC identity providers, or only SAML?**
IBM Docs document OIDC authentication from MAS 9.1 (multiple OIDC providers from 9.1 by API, from 9.2 in the UI). The IBM Developer SSO article and the Manage FAQ still say SAML-only or list OpenID as a gap, and we read those as dated. Pilot before you commit.

**Why do some users get AIUOM0100E after SSO is configured?**
Most often the user has no SAML ID in MAS, or the NameID the IdP sends doesn't match the stored identifier. Check the coreidp and coreapi pods and capture the exchange with a SAML tracer extension.

**What is DT423352?**
An IBM defect listed as fixed in the MAS 9.1.0 readme (24 June 2025): SAML validation failing for user IDs with special characters. Test with a real special-character account.

**Our login is slow with SAML. Where do I start?**
Time the redirect, the IdP leg and the MAS validation separately. On large user bases, check for DT422664 (fixed in the 9.1.4 readme dated 6 October 2025), and check coreidp for restarts.
